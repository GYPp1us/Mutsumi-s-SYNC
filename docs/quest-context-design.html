Quest Context — 多角色事项上下文与输入输出调度设计

为"一个复杂事项涉及多个角色"的场景（例：skills/nature-daily-cet4 —— scheduler 触发 → OpenCode 委派 → 群聊发题 → 群成员回复 → 私聊发答案）设计 一致工作记忆 + 清晰角色边界 + 灵活的输入输出调度。本文件为设计探索稿： 提出三个方案（A/B/C），推荐 B，并给出可实验验证的协议细节。

1. 问题定义

1.1 真实场景：nature-daily-cet4

该 Skill 的完整闭环涉及 5 类角色、3 个会话窗口、2 个外部子系统：

Scheduler定时触发（绑定群会话）
Bot pipeline事项协调者
OpenCodedelegate_task / report_task
Bot pipeline读题目文件
群聊 group:123发送题目
群成员 张三回复"选C"
Bot pipeline判定对错
私聊 张三发送答案与解析
事项状态谁已答、对错、进度、去重
SKILL.md 明确标注的当前能力缺口
"When a person asks for the answer in a private conversation, the Bot may read the matching answer file and send it there. When the question originates in a group, the current project has no generic cross-peer send tool: do not silently send the answer to the group or claim a private send. Report this as a runtime capability gap until a generic, server-bound peer-routing primitive is implemented."
此外 BOT.md 要求"多用户间维护一致工作记忆"（谁提交了答案、对错统计、state.json 去重、题目与答案文件配对）， 以及跨会话的身份绑定（群成员 qq:user:X → 私聊 private:X）。

1.2 三个待解问题

#问题现状目标
P1 一致工作记忆：一个事项跨 5 个角色、3 个窗口，bot 必须记得"今日题目是哪篇、谁答对、答案发给了谁、state.json 去重状态" 工作记忆碎片化：self_note 按会话、文件按 output 目录、episodes 按会话；无事项级状态 事项级（Quest）单一工作记忆，任意角色输入可读写
P2 清晰角色边界：同一事项中，群聊公开互动与私聊答案必须严格分离；A 的私聊对 B 不可见、不可路由 audience/visibility 投影（基线）或结构性隔离（USC）；跨会话无"事项内可见性"概念 同一上下文窗口内用格式化角色头规定边界（用户 idea）
P3 输入输出调度：输入可来自 scheduler/opencode/群聊/私聊（fan-in）；一个回合的输出可路由到多个目标（fan-out），且必须可验证、可审计 pipeline 按会话 key 调度（单源单出）；send(target=) 支持跨会话但无白名单、无批量路由 服务端绑定的路由原语：目标白名单 + 逐目标投递验证 + action ledger

2. 核心概念（新术语）

术语含义
Quest（事项）一个跨角色、跨会话的业务单元（如"2026-08-04 的 CET4 题目"）。拥有自己的 id、参与者白名单、共享工作记忆（状态 + 角色头时间线）。一个事项 = 一份上下文。
Role / Participant（角色/参与者）事项内的稳定身份：group:123、private:456、opencode、scheduler:task:7、bot:self。参与者白名单决定输出可路由目标。
Role Header（角色头）平台注入到每条事项时间线消息前的格式化前缀：[conversation|actor|name|time]。模型在同一窗口内靠它区分"谁在说话、消息属于哪个角色通道"。
Quest Timeline（事项时间线）事项的共享历史：全部参与者的 事项级事件按时间排列（题目发布、答题结果、委派回报等），带角色头。是"同一上下文窗口"的载体。
Quest State（事项状态）结构化工作记忆（JSON）：进度、计数、文件路径、绑定关系。由 quest_status 工具读写，模型可查可改，服务端持久化。
Routing Whitelist（路由白名单）参与者集合的投影：模型输出路由目标必须命中白名单 ∪ 当前源，否则平台返回 [Error] 且不投递。安全边界是服务端强制，不靠模型自觉。
Quest Reply（事项回复原语）输出侧新工具：quest_reply(quest_id, targets:[{target, content}], status_update?)，一次调用完成多目标 fan-out；逐目标 NapCat 验证 + 逐目标 action ledger。
Quest Binding（事项绑定）输入事件 → 所属事项的判定：显式（创建时声明会话集合）/ 隐式（群号+时间窗+话题关键词匹配最近活跃事项）/ 定时（任务注册会话再映射事项）。
Per-Role Memory（角色私密记忆）每个私聊/群聊角色保留自己的 USC 窗口（摘要+近期回合），不进入事项时间线；只有事项级事实进入 Quest Timeline。两层记忆 = 共享可见性 + 私密细节。

3. 设计原则

原则 1 — 单窗口 + 格式化角色头（用户 idea 的核心） 一个事项的所有角色事件汇入同一份上下文（Quest Timeline），角色边界由格式化的角色头 + 输出路由白名单规定， 而不是由多套投影状态机隔离。模型看到事项全景（一致性），但输出被白名单钳制（边界）。
原则 2 — 服务端绑定的路由原语（"generic, server-bound peer-routing primitive"） 模型永远不直接指定"发给谁"的自由目标；目标必须来自白名单。投递验证（NapCat status=ok）与审计（action ledger） 全部在服务端完成。这是对现有 send(target=) 的升级而非替代。
原则 3 — 两层记忆分离 事项级信息（题目、进度、结果）进 Quest Timeline；角色级私密细节（张三的答题心情、个人偏好）留在各自 USC 私密窗口。共享与私密的边界是写入时决定的（平台只把事项级事件写入 Timeline），不是请求时过滤。
原则 4 — 保持调度红线 Scheduler 仍是"时间 + prompt"，不新增 quest_id/skill 字段（事项绑定在会话层映射）； Skill 仍是文件；delegate/report 仍是通用委派。Quest 层只做三件事：绑定、记忆、路由。

4. 三个方案

方案 A — 管道拼装（最小改动，先行可用）

不加新上下文结构，只用现有机制拼出 CET4 流程：

  • 新增 quests 表 + 隐式绑定：群聊消息按"群号 + 最近活跃事项 + 关键词"匹配。
  • 工作记忆：沿用 self_note（按会话）+ 文件（state.json）双轨；跨会话一致性靠模型从上下文中拼。
  • 输出路由：现有 send(target=)（工作树已有跨会话逻辑分组），增加目标白名单校验（复用现有 action ledger 记录）。
  • 角色边界：无格式化头；群聊 pipeline 注入"当前群"上下文，私聊答案依赖模型从 send 目标推断。
维度评价
改动量小 仅 binding + 白名单校验
一致工作记忆弱 碎片化，模型需自行拼装；多会话无共享时间线
角色边界中 无格式化头，靠 send 目标与提示词约束
输出调度中 单目标 send；多目标需多次调用（已有 MAX_SENDS_PER_LOOP=5）

方案 B — QuestContext + 角色头 + 路由白名单（推荐）

在 A 之上加入事项级上下文（用户 idea 的完整实现）：

  • Quest Timeline：一个事项一份角色头时间线（共享记忆，复用 USC 的"摘要+窗口"回收机制做长程压缩）。
  • 请求组装：全局 persona（L1）+ Quest Timeline + 状态（L2）+ 当前输入角色头（L3/L4）；当前源角色的私密 USC 窗口按需并入。
  • 输出：quest_reply（批量路由）+ send（特殊消息段），两者都过白名单。
  • 状态：quest_status 工具读写结构化 JSON 状态。
维度评价
改动量中 新表 + QuestContext（约 400 行）+ 路由工具
一致工作记忆强 单一时间线 + 结构化状态；任意角色可读写
角色边界强 格式化头 + 白名单双保险；写入时分层保证私密
输出调度强 批量路由 + 逐目标验证审计

方案 C — 多 Agent 编排（远期，非推荐）

每个角色一个独立 agent 上下文 + 一个协调 agent 分发任务（群聊 agent、私聊 agent、事项协调 agent）。

维度评价
一致性中 协调 agent 单点，需自定义同步协议
成本高 N+1 个上下文常驻，每次触发多轮 LLM
复杂度高 违背"最小通用机制"主线；放弃

结论：与项目"选择能闭环的最小通用机制"的章程冲突，仅作对比记录。

5. 推荐方案 B 详细设计

5.1 数据模型

表字段说明
quests quest_id（主键）、kind（cet4-daily 等）、title、state_json、created_at、archived_at 事项本体；state_json 是模型可读写的结构化工作记忆
quest_participants quest_id、conversation_id、actor_id、role_kind（group/member/private/service/bot）、can_route_to（可路由目标列表）、joined_at 参与者白名单；can_route_to 例如群成员 qq:user:456 声明可路由到 private:456（平台校验该私聊确实存在/授权）
quest_events sequence、quest_id、role_header（格式化头）、content、event_type（trigger/report/outbound/answer/status）、visibility（quest/private）、created_at Quest Timeline（append-first，复用事件思路但只有事项级信息）；visibility=private 的行不进入共享时间线（保留审计）

关键决策：quest_events 只记录事项级事件（题目已发、张三答对、答案已私发）， 不记录张三私聊里的全部聊天内容——私密细节留在其私聊会话自己的 USC 窗口（messages 表）。 这实现了"同一窗口规定角色边界"（共享时间线可见）与"私密不泄露"（写入时分层）的统一。

5.2 输入侧：角色头格式（Role Header）

平台在把事件写入 Quest Timeline 时生成格式化头，模型读到的每一行都是自描述的：

[07:00:00] [scheduler|task:7] 平台定时触发：执行"今日 CET4 题目生成"任务
[07:00:02] [bot:self] 委派 OpenCode：读取 skills/nature-daily-cet4/SKILL.md，目标群 group:123，私答策略=提问者私聊，日期 2026-08-04
[07:05:41] [opencode|run:oc_a1b2] 回报 completed：题目 skills/nature-daily-cet4/output/exercises/2026-08-04-*.md；答案 .../answers/2026-08-04-*.md
[07:06:10] [bot:self] 已读取题目，发送至 group:123 OK（NapCat ok，message_id=...）
[08:12:33] [group:123|qq:user:456|张三] 选C
[08:12:35] [bot:self] 张三（456）回答正确；答案已私聊发送 OK
[09:01:02] [private:456|qq:user:456|张三] 第三题为什么选A？
[09:01:05] [bot:self] 已回复解析（引用题目 passage 第2段）OK
  • 头格式：[conversation_id|actor_id|display_name]，时间由平台前缀。
  • 规则声明（注入 L1 稳定规则）："时间线中每条消息属于其角色头对应的通道；向其他通道复述需经路由工具；私聊内容只属于该私聊参与者。"
  • 边界测试用例（写入实验计划）：同一时间线中，模型必须能回答"张三答对了吗"（共享可见），且当被要求"把张三的私聊问题转发到群里"时拒绝/只能走白名单。

5.3 输出侧：路由协议（quest_reply + 白名单）

工具签名

{
  "name": "quest_reply",
  "parameters": {
    "quest_id":   "string, required, 当前事项 id（来自上下文）",
    "targets":    [{
        "target":   "string, required, private:<数字> 或 group:<数字>（必须命中白名单）",
        "content":  "string, required, 扁平纯文本",
        "segment":  "可选特殊段（markdown_image 等，与 send 共用）"
    }],
    "status_update": "可选 {target, text}，长操作前进度通知",
    "state_patch":   "可选 {key: value}，更新 quest state_json（服务端校验 key 白名单）"
  }
}

服务端行为

  1. 白名单校验：每个 target 必须命中 quest_participants.can_route_to 或等于当前输入源，否则返回 [Error: target 'private:999' is not in quest participant whitelist]，不投递。
  2. 逐目标投递：NapCat HTTP + status=="ok" 才算该目标成功（复用 send_succeeded）。
  3. 逐目标审计：每个目标一条 action ledger 记录（成功/失败、message_id）；outbound 事件按目标会话写入 （复用工作树的跨会话逻辑分组，Episode 不会拉入源私聊事件）。
  4. 状态合并：state_patch 与时间线写入同事务（追加 quest_events 行：[bot:self] 已向 private:456 发送答案 OK）。

与现有 send 的关系

不替换 send：send 保留给特殊消息段（图片/markdown_image/表情/@/reply）， 其 target 同样过白名单（事项管道内）；非事项管道（普通私聊）行为不变。

5.4 事项绑定与生命周期

环节机制
创建显式：模型在任意会话调 quest_start(kind, title, participants_hint)（新工具）或在群聊中确认"开启今日 CET4"；服务端创建 quest + 注册参与者（当前群、当前用户）。
绑定（群聊消息 → 事项）隐式：按 conversation_id 找该群最近的活跃 quest（24h 窗口）+ 可选话题关键词；唯一匹配则汇入，多候选则注入候选列表让模型选择（或回复确认）。
绑定（私聊消息 → 事项）私聊可能是多个事项的参与者（CET4 + 其他）。隐式匹配规则：同会话最近活跃事项优先；模型可主动 quest_list 查询/选择。
定时触发Scheduler 仍只存时间+prompt（红线不变）；到期注入绑定的会话，会话 → 事项映射后进入 Quest pipeline。quest_id 不进 scheduler 数据模型。
委派回报report_task 回报事件按"运行绑定的会话 → 事项"汇入（现有 task-report 队列已绑定会话，映射层加一层）。
归档事项完成后（如当日题目全部判完/次日 0 点）archived_at 置位；时间线冻结，后续输入走新事项或普通管道。

5.5 请求组装（一个事项管道的完整上下文）

L1 · System（全局稳定）persona + runtime + 角色头规则 + 路由规则
与现有一致；新增两段稳定规则："时间线角色头语义"与"输出必须过路由工具/白名单"。
L2 · Quest ContextQuest Timeline（角色头时间线，USC 回收）+ Quest State（JSON）
事项级共享记忆：触发、委派、回报、发布、答题结果、答案投递。长程用"摘要+窗口"回收（复用 SimpleContext）， 摘要提示词强制保留：参与者、题目状态、未完成事项、文件路径映射。
L3 · Per-Role Window（按需）当前输入源角色的 USC 私密窗口
仅当当前输入来自某私聊/群聊且该角色有私密上下文时并入（如张三私聊问"第三题为什么选A"时并入张三的私聊窗口）。 其他参与者的私密窗口绝不进入本请求。
L4 · 当前输入角色头前缀 + 消息文本（或 scheduler/opencode 输入）
与现有 L4 相同，但前缀使用统一角色头格式。

与 USC 实验结论的关系：USC 的"摘要+窗口"直接复用于 Quest Timeline 的长程压缩； 角色头时间线 = USC 窗口 + 每行角色前缀。单窗口 + 格式化头正是上一轮实验"结构性隔离"与 本轮"共享工作记忆"两种诉求的统一：记忆共享（时间线可见），边界强制（白名单路由）。

注意与 AGENTS.md 红线的兼容 Scheduler 记录不加 quest_id/skill 字段（任务 → 会话 → 事项的映射在平台侧完成）； Skill 仍是文件；OpenCode 报告仍只回自然语言。Quest 层不建立"业务步骤 DSL"， 一切业务判断继续由模型在 prompt 中完成。

8. 安全边界与对抗场景

场景机制失败表现（平台侧）
模型想把张三的私聊问题转发到群里目标 group:123 在白名单内（群是参与者）——但内容边界：时间线内私聊角色头的内容被 L1 规则标记为"仅限该角色"；白名单只能防"发错人"，内容泄露需要提示词+示例约束投递成功但泄露私聊内容 → 需要实验测量泄露率（见 §9 实验 2）
模型向非参与者发消息（如 private:999）硬拦截：target 不在白名单 → [Error: ... not in whitelist]，不投递，进 action ledger零投递，模型收到错误可纠正
群成员身份伪造（张三说自己是他人的私聊）路由目标由平台按事件元数据解析（actor_id 来自 NapCat），模型只能引用、不能发明 actor非法 actor_id 直接拒绝
quest_state 被写入垃圾键state_patch 的 key 必须命中 quest_kind 声明的状态 schema（服务端校验）返回 [Error: unknown state key]
事项时间线无限增长USC 摘要+窗口回收；visibility=private 行不投影长程对话 token 恒定
旧事项被误匹配（绑定歧义）多候选注入让模型选择；无匹配则按普通管道处理不误写事项状态
白名单 vs 内容边界的区别（诚实说明） 路由白名单是硬安全（服务端强制，防发错目标）；"把私聊内容复述到群聊"是软边界 （依赖角色头规则 + 模型判断），与当前系统"模型自觉不泄露其他私聊"的信任模型一致。 实验 2 专门量化这个软边界的泄露率。

9. 实验验证计划（可复现，复用现有实验框架）

实验 1：多角色时间线召回与一致性（Quest Timeline Recall）

项设计

对比① 角色头时间线（方案 B）；② 无角色头的平铺时间线（消融：验证角色头的信息增益）；③ 分段式（当前基线：各会话各自投影，无共享时间线）
问题事项级："张三答对了吗/今日题目来自哪篇/答案文件在哪"（期望正确）；私聊级："张三的私人偏好是？"（期望：仅当当前源=张三时正确，其他源应拒答）
度量事项级召回率、跨源私聊泄露率、token 成本（复用 llm.py 的 usage 记账）

对比有白名单声明 vs 无白名单声明（验证白名单对路由正确性的提升）；3 次重复

10. 风险与开放问题

风险/问题分析缓解
单窗口混入多角色后 token 增长快事项级事件比全量聊天少一个数量级（只记结果不记过程），且 USC 回收保证有界写入时只记事项级事件；预算实验验证
软边界（内容复述）依赖模型判断与现状信任模型一致；但群聊+私聊同窗口使"看到了就能复述"风险上升实验 1 测泄露率；必要时时间线中私聊角色的行仅以"角色+摘要"呈现（细节只进 L3）
隐式绑定误判多事项同时活跃时（两个群各一个 CET4）可能串线绑定注入候选列表让模型确认；绑定结果进 quest_events 可审计
OpenCode 回报如何携带事项身份report_task 只回自然语言；事项映射依赖"绑定会话"delegate_task 的 prompt 中写明 quest_id 上下文（自然语言），平台仍按会话映射；或者允许 report 携带结构化 run 元数据（不违反"报告只收自然语言"红线？——需讨论）
与现有 pipeline 的侵入面quest pipeline 是 source 枚举的新变体，普通会话不受影响以新增为主，不改现有路径；QuestContext 与 SimpleContext 同层
是否真的需要独立 quest_events 表也可复用 events 表 + quest_id 列；但 events 的 projection 复杂度会传染独立小表，只做 append + 读窗口，无投影状态机（保持 USC 哲学）
