# 2026-10-18 重构决定与旧版归档

本文件记录本轮已明确选择的方向与消息表示。它是新版本的实现依据，不将尚未落地的行为写成当前生产能力；冻结的 Python 语义见 [V3 设计](../archive/v3/docs/current-design.md)，V4 契约见 [当前架构](current-design.md)。

## 已确定的选择

| 项目 | 决定 |
| --- | --- |
| 运行时 | 分阶段迁移 Rust；借鉴 pi 的小循环、原生工具回合与拦截边界，不将完整 TypeScript SDK 变成中心运行时的必经依赖。 |
| 开局判断 | Jev 对每次入站做一次分类；非常简短的情绪交流选择可维护的预制回复，复杂请求交给生成模型。 |
| 门禁 | 当前实际动作前做一次独立、无副作用的 dry-run；参数或相关事实改变后重新审查。审查过程不进入主上下文。 |
| Markdown 图片 | md2svg + resvg 放在独立常驻 worker；通过有限队列、资源预算与异常重启管理。 |
| 跨会话发送 | 格式化 assistant content 声明目标与内容，由统一执行器发送。没有明确选定目标，dry-run 打回；不自动补成来源会话。 |
| 旧版运行 | 先形成并验证可恢复归档，再停止并禁用 HZ 旧服务。归档可不包含聊天历史。 |
| 图片与表情组合 | 使用消息段数组进行行内编排。一个 content 内以外层 JSON 的 `messages` 数组拆分多条消息，每条的 `segments` 数组编排文字、表情与图片；模型选择混排或分条。 |

## Jev 分类与用户维护的预制回复

Jev 返回的是候选选择与概率，不直接自由生成新的台词。这里把“直接简短回复”落实为：选择用户配置中的模板或模板组，宿主按受限占位符生成发送提议，然后走统一 dry-run 和发送执行器。

```text
真实入站事件先落库
    → 一次 Jev 开局分类
        → 明确的简短交流：选择预制回复
        → 需要处理的任务、歧义、分类失败：交给生成模型
        → 合理静默：记录这次决定
    → 任何对外消息都明确目标并经过当前动作的 dry-run
    → 真实回执和实际发言写回事件账本
```

这调整了上一轮“所有输入默认同时启动主模型和快速生成模型”的建议。模板已足够时无需再调用生成模型；复杂任务是否需要额外的快速意图生成，留作有证据支持后再增加的能力。

分类看到必要的近期往来、当前来源与角色关系、真实活动状态、输入文本，以及媒体描述和媒体 ID。Jev 本身不接受图片；表情接龙判断使用媒体管线的文本描述，不能只因输入含图片就当作无意义交流。

“晚安，明天提醒我开会”仍然是任务；用户正在表达真实困难时也不能因出现问候词就套用轻松台词。没有合适模板、分类不确定、相关材料缺失或接口失败时回到生成模型，不丢弃原任务。

维护入口建议先使用独立的 `quick-replies.yaml`。字段包括：稳定模板 ID、类别与适用说明、是否启用、文字/表情/媒体片段、可用称呼占位符、避免重复的选用设置。模板是回复数据，不执行脚本，不成为 system 指令，也不增加动作授权。固定人设仍由 `system-prompts.yaml` 维护。

```yaml
# 说明用示例；本轮没有创建或启用这份运行时配置。
version: 1
templates:
  - id: morning_01
    category: morning_greeting
    enabled: true
    description: 只有简单早安问候，没有附加请求
    target_binding: source_conversation
    messages:
      - segments:
          - type: text
            text: "早安呀，{address}～"
  - id: night_01
    category: night_greeting
    enabled: true
    description: 只有简单晚安道别，没有附加任务
    target_binding: source_conversation
    messages:
      - segments:
          - type: text
            text: "晚安，早点休息～"
```

`target_binding` 是模板显式声明的选择，实例化时必须解析成事件中真实存在的目标引用，再提交 dry-run。不能在目标缺失时由发送器兜底。媒体模板只能引用现存有效的 `media_id`；文字表情可以直接使用 Unicode 字符。热重载先验证完整新文件，通过后原子替换；错误配置保留上一份有效版本并给维护者可读诊断。

开局类别和候选模板可以在同一次请求中分别提问，但它们的答案相互独立。不能假设同一次请求里的第二个问题已经知道第一个问题的结果；只有数据确实需要由前一个答案才能构造时才增加请求。

官方依据：[System One](https://docs.typesafe.ai/concepts/system-one)、[问题原语](https://docs.typesafe.ai/primitives)。置信度与性能需要按中文、角色关系和实际模板做本项目验证，本轮没有声称已达到某个延迟或准确率。

## 格式化 content 与发送执行器

采用一个统一的出站消息表示，生成模型和模板实例化都产生这种表示。每轮 assistant `content` 都可以是完整 JSON 对象，包括同轮存在 `tool_calls` 的情况：`messages` 的每项是一条独立发送消息；该项的 `segments` 则按顺序编排消息内的内容。`to_self` 保留简短的主观内心增量，不是可见消息或原始思考过程。

下面的 `target_project_group`、`media_example` 是说明用占位引用；实际输出必须选择运行时提供的真实对象。两项 `messages` 分别形成两条消息，不使用管道符、换行或文字内容猜测消息边界。

```json
{
  "to_self": "",
  "messages": [
    {
      "target_ref": "target_project_group",
      "segments": [
        {"type": "text", "text": "你看这张图："},
        {"type": "image", "media_id": "media_example"},
        {"type": "text", "text": "这里需要调整。"}
      ]
    },
    {
      "target_ref": "target_project_group",
      "segments": [
        {"type": "text", "text": "我再核对一下其他位置。"}
      ]
    }
  ]
}
```

模型选择的目标来自真实对象目录。发送账号由宿主授权与当前角色绑定，不能由任意正文自称替换。会话目标、@ 对象、引用来源和被转述作者分别核对。

没有 `target_ref`、引用无法解析、目标与内容或真实要求冲突，都在 dry-run 入口返回明确问题；能确定性发现的字段错误先校验，再做语义判断。拒绝不意味着由门禁自行改目标。只将必要原因交回行动模型修正，审查推演单独留审计。

格式化内容先作为提议保存，只有核实发送成功的文字、受众、媒体和消息 ID 成为实际出站经历。格式化 JSON、未发送草稿和主观内心不能伪装成用户已经看到的 assistant 发言。

文件读取、媒体搜索、Markdown 渲染等工具可以继续存在；渲染生成文件和媒体引用，发送仍由格式化 content 与统一执行器完成。每轮完成后完整解析 content，存在消息提议时经 dry-run 发送，再处理本轮工具；空消息不强制开场，也不额外引入回复模型。工具各自仍需审查，结果与真实发送回执交回模型继续处理。

这明确撤回旧版“带 tool_calls 的 content 不处理”的限制。工具轮 content 与原生调用一起保留供模型衔接，但它声明的消息只有真实发出后才成为对外事实。已成功发送的阶段消息立即落账，不因后续工具失败或取消而消失。

每条消息是一个可独立核实的发送动作。多条消息必须逐条记录回执；前面成功、后面失败时保留这个事实。未知回执不能当作确认失败自动重发。需要在同一轮继续处理回执时，使用真实平台结果继续模型请求；不得伪造一个不存在的 provider tool call。

### 新版 system 中的消息规则

固定 system 负责对齐下面的消息规则；当前 actor、可选目标、媒体引用与真实执行结果仍由事件和临时平台状态提供。协议正文在新版解析器接入时统一落入 `system-prompts.yaml` 的 runtime prompt，不在 Rust 中复制维护。V3 prompt 已保留于 `archive/v3/system-prompts.yaml`，新版协议随解析器一并接入。

1. 每轮 assistant `content` 都可作为发送提议解析，包括同轮有 `tool_calls` 的情况。有 content 时只能输出完整 JSON 对象，不加 Markdown 围栏或区块外文字；工具轮允许空 content 表示没有消息提议。先完整解析，再将消息经 dry-run 发送，随后处理本轮工具。
2. 顶层字段为 `to_self` 与 `messages`。`to_self` 是简短主观内心增量，不向用户发送；只有符合完成与提交条件后才能进入 inner journal。
3. 使用消息段数组进行行内编排。`messages` 的每项表示一条独立消息，`segments` 的每项表示该消息内一个有序内容段。模型可以同条混排，也可以分成多条；内容顺序与消息边界以数组为准。
4. 每条消息都必须显式填写 `target_ref`，包括发往当前会话的普通回复。目标只能选自真实对象目录；字段缺失、引用无效或对象不清楚时，由 dry-run 打回模型补齐，不能擅自选择默认收件人。
5. 文字写入 `text` 段；QQ 内置表情使用有效 `face_id`；图片与表情包使用已有 `media_id`。不得编造对象 ID、媒体引用或资源地址。媒体细节由账本与平台适配器解释。
6. 普通文字段保持适合 QQ 的扁平文字。需要精确排版的富文本先渲染为媒体，再通过图片片段引用。每段文字里的换行和 `|` 都是内容，不触发拆条。
7. 本轮没有可见消息时输出 `messages: []`。不为满足格式而制造空消息、固定确认句或无依据的进展通知。
8. 所有模板回复和生成回复都通过同一 dry-run 与发送执行器。动作参数或相关事实变化后重新判断；通过审查只表示允许尝试，实际成功以真实回执为准。
9. JSON 是提议，发送回执才建立对外事实。未成功发送的草稿、协议字段和 `to_self` 不进入可见 assistant 历史；多条消息的部分成功与未知结果必须如实记录。

接收侧与发送侧使用一致的有序消息结构。执行器先完整解析并校验整个 content，再处理各条动作；流式输出的半截 JSON 不得执行，损坏结构进入有限纠正，不通过字符串拆分猜测发送动作。

## 已确认：同条混排与分条发送

“行内”首先指它在一条消息的有序内容中，不承诺所有客户端把图片压在同一行文字基线上。

同条消息示例：

```text
一条消息 / 一个逻辑发送：
    [文字：早安呀] [QQ 表情] [文字：今天也加油]

一条消息 / 一个逻辑发送：
    [文字：你看这里] [图片 A] [文字：这个位置需要调整]
```

独立图片示例：

```text
第一条消息：[文字：我把图发你]
第二条消息：[图片 A]
第三条消息：[文字：注意右下角]
```

已确定的数据结构是“两层列表”：外层每项对应一条发送消息，内层按顺序列出文字、表情、图片等片段。同条混排或拆成多条是模型当下的选择。独立图片是一条只有一个图片片段的消息，继续使用相同的发送流程。

| 内容 | 原生表示 |
| --- | --- |
| Unicode emoji，如 🙂 | 文字的一部分 |
| QQ 内置小表情 | `face` 与有效表情 ID |
| 图片或 GIF 表情包 | 图片片段与真实 `media_id`；由适配器按原媒体能力发送 |
| 商城表情 | 保留原生类型与资源引用，按实际 NapCat 能力适配 |
| 独立图片 | 一条只包含图片片段的消息 |
| 精确排版长文、公式、图表 | md2svg/resvg 产生图片，再引用该媒体 |

普通图片与表情包不必先烘焙进 Markdown 图片；GIF 也不应因为走了静态排版而丢掉动画。

接收也保留原消息边界、消息 ID 与片段顺序。每张图片分别登记媒体和描述，再在原位置投影成描述与媒体引用；失败的识别在该片段标明不可用。当前分类器只保留第一张图片并合并全部文字，新版应避免沿用这个信息损失。

协议依据：[OneBot 消息段数组](https://github.com/botuniverse/onebot-11/blob/master/message/array.md)、[NapCat 消息类型](https://napneko.github.io/develop/msg)。最终 QQ 客户端的显示与商城表情/GIF 行为需要实际账号验收，本轮没有进行真实发送试验。
