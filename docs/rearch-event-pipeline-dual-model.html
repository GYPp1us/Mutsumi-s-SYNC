Mutsumi's SYNC · Architecture Decision Record

事件队列 + 引导式双轨 Pipeline 最终设计

细化用户重构思路：删去整条 pipeline 取消与复杂投影，改为持久事件史 + 唤醒队列 + 只抢占模型流的引导；Main / Reply 双轨各自忠实维护自己的已发送事实；Dream 保留一条连续性胶囊 + 最近原生尾巴 + 历史搜索。交付名词对齐表、证据表、问题回答与技术架构。

结论日期：2026-08-31（UTC+8） 范围：架构细化 + 证据审阅，不含本轮代码重构 依据：当前源码审计 + 三组本地实验 + 2025/2026 论文与主流开源实现 原则：最小通用机制闭环，判断与执行留给 AI；不做 Workflow DSL
最终判断

方向成立，两处必须修正，其余收紧即可

  1. 修正一（结构）：不要给工具结果套 [TO_SELF]/[TO_USER] 文本协议。工具结果是 provider-native role=tool 的原始可审计内容，是工具循环恢复与模型理解的结构事实；双通道 envelope 只属于「最终/阶段可见回复」。
  2. 修正二（布局）：不要每条消息重复「角色系统提示」。全消息只有一份不可变 system + 一份按 scope 选定的角色指引；角色身份由行内角色头承载（你们自己的 Quest 实验证明行内标记最好）。逐条角色系统提示会重复 7K+ 开销并打碎缓存前缀。
  3. 澄清一（并行）：Main 与 Reply 是「逻辑双轨、物理串行」——Reply 依赖本轮 Main 结果，必然 Main→Reply；两者只有一份权威事件史，各自多一份「自己输出风格」的尾巴。
  4. 澄清二（保留什么）：删掉的是「新消息取消整条 pipeline」的原子设计；Event Ledger、Action Ledger、inner journal、原生工具回合这些真相层全部保留。

最终最小心智模型：

Agent = 权威事件史 + 会话执行器 + Main 投影 + Reply 投影
  一条连续性胶囊 + 最近原生尾巴 + 历史搜索
  bash / Skill 文件 / Plugin 能力 / Sub-agent
  同步器 / 媒体管理器 / 设备节点

本地实验三连（同一模型族，方向性证据）

USC（摘要+窗口）

与真实投影对照：600 轮/16K 与 1000 轮/8K 下基线 0.50/0.38、USC 1.00/1.00；压缩成本基线为 USC 的 2.2–7.1 倍；build_life_stream 在新预算下静默丢最老 Episode。

Quest（多角色长噪声）

扁平行内格式化 0.77 > Task Room 0.62 > Ledger 投影 0.38；Ledger 隐私边界在长历史崩溃到 0.00，行内角色头 1.00——支持单序列、行内结构、低嵌套。

Reasonix 工具流

同一 assistant 响应可边流式给可见文字边带 native tool_calls；完整响应后才执行工具；assistant content、tool call、tool result 原样进下一轮。支持「先表阶段再执行」，不支持「工具结果也用 envelope」。

交付 1

名词释义对齐表

本文术语严格定义不是
权威事件史
Canonical Event Journal		append-first、持久化、带全局序列与 provenance 的唯一世界事实；一切模型上下文都是它的派生视图。不是 prompt、不是可覆盖摘要、不是内存队列。
会话执行器
Conversation Runner		活跃时串行推进一个 conversation 的可重建异步 worker；游标在数据库，不在 Task 对象；空闲可退出。不是 actor framework，不是永不退出的协程。
唤醒队列
Wake Queue		内存中 per-conversation 的「可能有新工作」提示（asyncio.Queue）；执行器醒后仍从事件史读 cursor → head。不是事实队列，不承担可靠投递；崩溃后靠扫描重建。
引导
Guidance / Steer		同一会话的真人新输入使当前 Main 或 Reply 流过期；只 abort 当前 provider stream，回到 Main 重新规划。不是取消 pipeline，不是撤销已开始工具，不是删除已发送消息。
输入代际
Input Epoch		只由可抢占输入推进的 per-conversation 整数；工具与 assistant 事件本身不推进它。不是全局 event sequence。
代际栅栏
Generation Fence		Main 发送前、Reply 发送前、工具启动前、outbox 认领前校验代际的规则。不是外部副作用的回滚机制。
出站意图
Outbound Intent		通过代际栅栏后、等待 sender 认领的持久待发送记录。不是已发送事实。
发送线性化点
Send Claim Point		sender 原子认领 outbound intent 的时刻；认领前可作废，认领后只能承认发送已开始。不是平台成功确认。
主投影
Main Projection		面向规划、工具与世界状态的上下文视图；拥有工具权限；内容 = system + persona + 当前 scope 主动标记 + 胶囊 + 原生尾巴 + 行内历史 + 本轮输入。不是直接给用户看的表达层。
回复投影
Reply Projection		面向人格表达与输出门禁的上下文视图；无工具、无目标选择权；内容 = reply system + 同 persona + 同类源事件 + 最近已发送风格尾巴 + 本轮受限 brief。不是第二个世界状态机。
阶段回复
Phase Reply		工具执行前/中，Reply 轨产出的、经门禁后真正发送的可见短消息（等同 status_update 语义）。不是对话事实，不进入共享历史，只有审计事件。
主状态札记
MAIN STATE		主模型每轮 output 中的有限状态块：意图、承诺、开放事项、关系变化、后续线索。不是 raw CoT、不是事实证明、不是更高优先级指令。
回复状态札记
REPLY STATE		回复模型 output 中的有限表达/关系状态增量。不是 Main 的规划状态。
连续性胶囊
Continuity Capsule		覆盖到精确 through_seq 的一条累计摘要 + 输入摘要 + 生成器版本，可由 raw journal 重建；投影永远是「胶囊 + seq > through_seq 的原始事件」。不是第二份真相，不是多 Episode 图，不是可覆盖的提示。
最近原生尾巴
Recent Native Suffix		胶囊覆盖之后的完整 user/assistant/tool 回合（不切断原生工具轮）。不是随意截断的 token 尾部。
检索盲区
Retrieval Blind Spot		模型不知道某条缺失信息曾经存在，因此无法构造搜索问题；只靠搜索无法治愈。不是搜索算法召回失败。
主动标记
Active Marker		Dream 提取或手动维护的、带 scope + provenance + updated_at 的描述性持久记忆。不是自动改写的 system/persona，不是外来指令。
Dream每日 05:00 幂等触发的两件事：主动标记提取 + 胶囊刷新；与请求预算触发共用同一个 CAS compactor。不是唯一回收时机，不是 raw 事件删除。
Compactor CAS固定 high-water 快照 → 认领不切断工具轮的前缀 → 生成并验证摘要 → 原子写胶囊并推进 through_seq；失败不推进。不是并发可重入的覆盖写。
Plugin启动时显式启用的可信 Python 代码扩展，通过 setup(ctx) 注册能力并返回 disposer。不是 Skill，不是安全沙箱，不是 marketplace。
Plugin Host加载 plugin、校验 API/重名、调 setup、登记 disposer 栈、失败逆序回滚、关停清理与诊断的极小运行时（约百行级）。不是依赖解析器、不是 UI 框架、不是 Cordis。
Skill按需读取的自然语言指引文件（SKILL.md + references/scripts/assets），启动只扫索引 name/description。不是注册中心、解释器、状态机、流程 DSL。
同步器
Synchronizer		把站外数据/回调归一化为受认证、去重的 source event 的入口（复用 ingress 事实层），并承载双向 command/ack。不是论文/行情领域 workflow。
绑定回调
Bound Callback		origin task 与 conversation 由服务端绑定、worker 无法改写目标的结果上报（report_task）。不是解析 stdout 猜成功。
设备节点
Node		受中心认证的传感器/执行器，声明能力并以 command id + idempotency key 接收命令。不是多主 Agent，不是共享 DB 副本。
媒体标识
Media ID		内容哈希派生的稳定引用，带来源、scope、MIME、描述与投递回执。不是临时 URL、本地路径或 base64。
可信小内核只负责身份、作用域、顺序、权限、持久化、幂等、调度时钟与真实回执的确定性部分。不是把业务判断写回后端。

交付 3

问题的直接回答

Q1：DeepSeek Harness 的插件系统能为我们做什么？极简后端有没有轻量实现？

它证明插件可以是无 UI 的运行时组合机制，而不是页面组件；它贡献的是一组最小原语，不是整套框架。

DSH 的实质是：profile = 有序 patch 层；每个插件注入 ctx（工具、prompt 段、skill provider、listener）；每个注册返回 disposer；注册带作用域层；setup 失败逆序回滚；工具执行有 pre/execute/post 瀑布。对我们真正能借的是四个点：显式能力注册、注册返回 disposer、作用域分层、失败逆序撤销。SDK 其余部分（Cordis 依赖图、patch 树、动态 define/run/stop、浏览器半边、pnpm 插件管理、模型可调用 hook 的丰富度）全部不需要。

极简实现（约 100–150 行 host）：

# plugins/example/plugin.py           # 无 manifest，模块常量承担契约
PLUGIN_ID = "mutsumi.example"
PLUGIN_API = 1

async def setup(ctx, config):
    dispose_tool = ctx.register_tool(Tool(...))       # 返回 disposer
    dispose_source = ctx.register_source(source_adapter)  # 只能提交 untrusted source event
    return dispose_cleanup                             # 可选；host 仍会逆序调用 registrations

# config.yaml
plugins:
  enabled:
    - path: plugins/example
      config: {}
    # 显式 allow-list；不自动下载、不自动发现依赖

Plugin Host 只做：读取 allow-list → import → 校验 PLUGIN_API 与能力重名（duplicate 即失败，禁止覆盖内建安全工具）→ 调 setup(ctx) → 收集 disposer 栈 → 任一 setup 异常则逆序调用已注册 disposer 并报告 → 关停时逆序清理 → 提供 owner-gated plugin list/inspect/doctor 工具。UI 完全不进 Plugin V1——现有 Dashboard TUI 就是外挂；未来可选的 web 面板读同一事实层，也只是只读消费者。

首版开放面（每项都有明确边界）：register_tool（常驻外部 API/设备动作）、register_source（新 channel/ingress 适配器）、register_media_handler（识别/生成/转码 adapter）、register_agent_backend（独立任务后端，结果必须走绑定回调）、register_skill_dir（随插件分发文本说明）、spawn_managed_task（长连接适配器）。不开放 before_model / replace_context 类 hook——那会让插件直接污染人格与角色边界；真实需求出现后再加窄化、具名、确定顺序的 hook。

Q2：Dream 裁剪后保留摘要，还是只让模型遇到盲区时搜索消息记录？

两个都要，但每个只做一件事。只搜索会遇到检索盲区（模型不知道缺失信息存在，便不会构造搜索问题——LongMemEval 的 five core abilities 与 NoLiMa 共同指出这一点；你们自己的 USC 数据也显示「静默丢弃 + 无标记」时事实 100% 丢失）；只在上下文留摘要会丢精确原文与修订轨迹；只留长原文则受 context pollution 影响。所以：

  1. 保留一条累计连续性胶囊：负责始终在场的关系、称呼、角色边界、稳定偏好、已确认事实及最新修订、承诺与未完成事项、关键决定、历史缺口与可检索关键词。带精确 through_seq，可被 raw journal 重建。
  2. 保留最近完整原生尾巴：胶囊覆盖之后的 user/assistant/tool 回合原样在上下文中（Pi 的 firstKeptEntryId 模式），绝不切断工具轮；单轮超预算时做 split-turn 双摘要合并。
  3. 保留 history_search → history_load：负责精确原文、时间、ID、路径、媒体、副作用是否真实发生——需要时按范围调入，只作为本轮 tool result，不创建永久「调入上下文」状态。

另澄清两点：① 05:00 不是唯一回收时机。高流量会话当天任何时刻都可能超预算，Dream 与请求预算阈值必须调用同一个 CAS compactor（固定快照 → 认领不切断工具轮的前缀 → 生成验证 → 原子写胶囊推进 through_seq；失败不推进，raw 仍可见；并发只有一个成功）。② Dream 的标记提取与胶囊刷新是两个独立请求，输入全部扁平进单个 user payload（你已写对）；提取器输出只是候选，host 校验 scope/provenance/长度后方可写，群聊与订阅来源只能产生 conversation/source scope 标记，人格 seed 的修改仍是 owner-gated 系统操作。

Q3：这一套是否足够完备？

核心目标判断成立条件 / 尚缺部分
拟人化基本足够，收益待证Reply 轨只认「已发送事实」；实现前先做三臂 A/B（单 Main / stateless Reply / 有风格尾巴的 stateful Reply），不达标就删。
超长上下文一致性足够一胶囊 + 原生尾巴 + search/load；raw journal 为真相；同一 compactor；精确覆盖与 omission 标记。
角色边界一致性足够ID/scope/target 由后端决定；外部 source 永远不能自称 system/owner；私聊 raw 不全局注入；组内成员独立 actor、共享会话窗口。
完备助手足够受控 Bash + 文件 + Skill + scheduler + Plugin 能力 + Sub-agent；不做 workflow DSL 与领域 connector。
通讯中枢当前只完成入站一半需补：source register/revoke & token 轮换、durable command outbox（command id + idempotency key）、ack/result 回流为 source event。
设备通信分布式节点单中心版本足够中心分配顺序；节点 at-least-once + dedupe；不做 exactly-once、多主、CRDT、vector clock。

关于「bash 足够」：Bash 的图灵完备性解决能不能执行，不解决凭据、权限、长连接、幂等、远端发现与真实回执。分工应该是：一次性计算/文件工作 → Bash；可复用的「怎么做」 → Skill 文件；常驻连接或新能力 → Plugin；外部标准工具服务 → MCP 适配 Plugin（或直接 http_api_call）；长独立任务 → Sub-agent。四个边界各司其职，不要用 Plugin 表达业务步骤，也不要把 Skill 塞进 Scheduler schema。

Q4：需要补充什么测试？

最优先不是更多 happy-path 单测，而是可控 barrier 下的确定性竞态测试（fake stream / fake sender / fake tool，禁止随机 sleep 碰竞态）：Main 流中真人消息 → stream abort、partial 不持久、重规划后包含两条输入；Reply 流中真人消息 → 回 Main 而非只重写；stream 与 steer 同时完成 → 固定 steer 优先；epoch 检查与发送认领交错（TOCTOU）；工具已开始后到达新消息 → 当前工具至多一次、剩余 calls 生成完整 skipped 结果；未知写入崩溃 → outcome=unknown 不自动重放；journal 提交后 wake 前崩溃 → 重启扫描重放；Dream 与预算 compactor 同时 claim → 仅一个 CAS 成功；Plugin setup 半途异常 → 逆序回滚；节点命令重复投递 → command id 幂等。完整矩阵见测试章节。

Pipeline

事件驱动、全双工、只抢占模型流

1. 接收与唤醒（队列只是门铃）

receive(event):
  transaction:
    validate source / actor / target
    dedupe(source_id, source_event_id)
    seq = append_event(event)
    if event.interrupt_policy == "steer":
      input_epoch += 1
  commit
  wake_queue.put(conversation_id)     # 只唤醒；不承载事实

提交后、wake 前崩溃：supervisor 启动/重连时扫描 processed_cursor < journal_head 重建 runner。空闲 runner 可退出；队列丢失只损失延迟，不损失事实。

2. 谁能引导（interrupt policy）

事件来源默认策略理由
同一 conversation 的真人私聊/群聊输入steer群内任意真人都属于 human role；按 exact actor 会让群聊互相听不见。
普通同步器订阅数据follow-up订阅/行情噪声不应抢占真人请求。
scheduler / heartbeat / Dreamfollow-up走同一入口，但让位真人 pipeline。
平台标记为关键结果的 Sub-agent report可由平台标为 steer只有绑定任务的关键结果才需要立即重规划。
另一 conversation独立 runner不共享 input epoch。

3. Main / Reply stream race（核心并发结构）

async with client.stream("POST", url, json=payload) as resp:
    async for chunk in _stream(resp, epoch):
        # 消费一个 chunk 前先做非阻塞队列检查
        if steer_event.is_set() or input_epoch != epoch:
            break                       # 关闭连接 → 服务端停止生成
    partial = collected                   # 只进诊断日志，永不入历史

# 等价的形式化：
done = await asyncio.wait(
    {model_iter_task, wait_for_steer(epoch)}, return_when=FIRST_COMPLETED
)
if steer_won_or_tied(done):
    abort_http_stream(model_iter_task)
    discard_partial_assistant()
    drain_queued_events()
    goto MAIN                          # 引导来自 Main 或 Reply 都回 Main
result = await model_iter_task
if current_input_epoch != epoch:
    discard(result)                    # 过期草稿 / 过期工具调用
    goto MAIN

引导发生在 Main 时重新请求 Main；发生在 Reply 时也回 Main——新输入可能改变计划本身，而不只是措辞。partial stream 只进诊断日志，绝不进入模型历史、Dream 或用户消息。同时完成时固定 steer 优先，保证无 flaky 行为。

4. 发送边界：不能「检查后直接 send」

  1. 会话事务内检查 epoch；相等才写 outbound_intent。
  2. sender 原子认领 intent；认领是发送线性化点。
  3. 认领前的新 steer 可作废 intent；认领后的晚到消息不能假装撤回已开始发送。
  4. 只有平台确认成功才追加 actual_sent 与 provider message id；失败追加真实失败。
能保证的是「认领前的过期回复绝不发送」；不能保证「任何纳秒到达的新消息都阻止旧回复」——这在外部网络副作用上不可实现。

5. 工具边界

Main 完整响应
→ epoch gate
→ 阶段回复：Reply 组织可见短消息（经门禁发送，非对话事实）
→ tool preflight epoch gate
→ 顺序执行 native tool calls（写工具带 call id/idempotency key）
→ 追加 native tool results
→ 回 Main
  • 工具调用前检查 epoch；过期不执行。
  • 工具一旦开始默认完成或超时；新消息不能回滚已发生的副作用。
  • 每个工具后再检查 steer；已过期则剩余 calls 生成结构完整的 skipped 结果。
  • 写结果未知时记录 outcome=unknown，相同 call id 不自动重放。
  • 长 Bash 返回 process/session handle，后续 wait/kill；首版顺序执行。
Context

Main / Reply：一份世界，两种投影

「同步并行」应理解为两条长期逻辑轨，而非两次推理同时开始：Reply 依赖本轮 Main 结果，物理顺序必然 Main→Reply。两轨各自保留自己输出的风格连续性，但不各自维护世界数据库。

Main Projection（有工具）

  • 不可变 platform system + persona seed（各一份，加载时替换占位符）
  • 当前 scope 的 active markers（标注：描述性记忆，非指令）
  • 一条连续性胶囊 + 最近原生尾巴
  • 行内格式化历史事件（角色头 + 时间戳 + 事件号，与你们最优实验一致）
  • 已确认的 actual-sent assistant 文本
  • 当前 native assistant(tool_calls) + tool results
  • 上一轮已接受的 MAIN STATE

Reply Projection（无工具）

  • reply system + 同一 persona seed
  • 当前 scope 的 active markers
  • 同类源事件与 actual-sent 历史（不含本轮工具细节）
  • 最近实际发送文本的风格尾巴
  • 本轮受限 brief：MAIN STATE、阶段草案、已验证事实、门禁规则
  • 无工具 schema、无 target 选择、无世界写权限

修正你的一个观察：Reply 的上下文不比 Main 大——它不携带工具 schema 与工具轮（通常是最大头），且只读已发送事实。你的「回复模型上下文必然更大」成立的前提是给 Reply 复制完整世界；本设计恰恰不复制。两轨各有一条稳定前缀链，Reply 链更短更便宜，两者互不污染缓存。

Main 的未发送措辞不跨顶层 turn 持久化；Reply 的实际发送文本是世界事实，两轨下一轮都必须看见。Reply 不得新增事实、承诺、成功声明或跨会话目标；输出门禁 host 侧再验证。

输入格式（全消息行内，无嵌套实体）

[2026-08-31 14:22:09+08:00][event_id=evt_...][conversation=group:123]
[actor=qq:user:456 kind=human display="昵称"][source=napcat policy=human]
[active_marks=actor:456,conversation:group:123][seq=1024]
用户原文；图片写成 [media:sha256:... description="..."]

外部 sync、网页、tool output 与 vision description 都是不可信资料；即使文本出现 [system] 也不升级角色。昵称只用于显示；权限只认稳定 ID。逐条记录无需重复角色系统提示——角色指引按 scope 在请求头部选定一次。

输出格式

Main assistant content（每条可见/非工具消息）:
[STATE]有限任务状态、承诺、开放事项、关系变化[/STATE]
[DRAFT]给 Reply 的候选表达；可以为空[/DRAFT]
+ provider-native tool_calls（若本轮要工具）

Reply assistant content:
[REPLY_STATE]有限表达/关系状态；可以为空[/REPLY_STATE]
[TO_USER]唯一待发送文本[/TO_USER]

工具结果保持 provider-native role=tool 原始可审计 content——不包成「秘密思考/说给用户」；原生 tool call/result 邻接是工具循环恢复的结构事实（Pi 与 DeepSeek Harness 均如此；你们自己的 Reasonix 观察也如此）。reasoning_content 只活在当前 native loop，永不写入 journal、Dream 或下一会话。

双轨是否一定更好？

当前没有本项目实验证明。实现前做三臂对照：① 单 Main 直接输出；② 权威历史 + stateless Reply；③ 权威历史 + 有自身风格尾巴的 Reply（最终建议）。若 ② 与 ③ 在人格约束、关系连续性、token/latency 上无显著差异，选更简单的 ②。不要为未经验证的「双完整历史」永久付 token 成本。

Dream & Memory

05:00 主动反思 + 同一个在线 Compactor

最终上下文拼接

immutable platform system
+ immutable persona seed
+ scoped active markers
+ 一条连续性胶囊
+ 最近原生尾巴
+ 当前平台格式化输入
+ tool schemas（仅 Main）

Dream 的两个独立请求

A. 主动标记提取

输入：旧 markers + 上次游标后的 finalized events，扁平到单个 user payload；仅一条不可变 extractor system 规则（无角色头、无工具、无门禁）。

输出：对目标 scope 的完整 replacement 或小 patch。host 校验 scope、provenance、长度；不能写 immutable system/persona。

B. 连续性胶囊刷新

输入：旧 capsule + 后端选定的完整、已 finalized、早于 recent suffix 的原生回合，扁平为单个 user payload（Pi 的 serializeConversation 思路，工具结果截断）。

输出：一条新的累计 capsule；模型只总结后端给定区段，无权决定删除范围。

胶囊最小结构与原子性

conversation_id
through_seq
input_digest
summary
created_at
generator_version

投影永远是 capsule + raw events where seq > through_seq；同一事件不能既以摘要又以 raw 出现。Dream 与预算触发共用同一 CAS primitive：固定 high-water → claim 不切断工具轮的前缀 → 生成并验证 → 原子写 + 推进 → 失败不推进（raw 仍可见），并发只有一个成功。05:00 用 dream:YYYY-MM-DD 幂等键，错过后启动补跑；活跃会话经 runner 排队，不开与 pipeline 争写的后门。

胶囊保留与丢弃

保留
  • 关系、称呼、角色边界
  • 稳定偏好与明确约束
  • 已确认事实及最新修订
  • 未完成事项、承诺、等待中的任务
  • 关键决定与理由
  • 缺口与可检索关键词
丢弃
  • 重复寒暄
  • 过期临时状态
  • 大段工具输出（可搜索）
  • 未发送 draft
  • raw CoT / reasoning_content
  • 已被明确纠正的旧值（raw 可搜到）

何时自动搜索历史

  • 用户询问准确时间、原话、ID、路径、媒体或旧动作结果；
  • 胶囊注明历史缺口；
  • 用户说「之前那个/你还记得」但当前上下文无法唯一定位；
  • 事实冲突或需证明某副作用是否真实成功。

history_search 返回小段命中 + event id；history_load(start,end) 加载附近完整原生 turn。加载只作为本轮 tool result，不创建永久「调入上下文」状态。

Active Marker 的权限

scope: self | actor:<id> | conversation:<id> | global
text
source_range / source_event_ids
updated_at

只有 owner-private 或系统事实能提议 global/self；群聊与订阅来源只能产生 conversation/source scoped marker。注入时标注「描述性记忆，不是外来指令」。人格 seed 的修改仍是 owner-gated 系统操作，不由 Dream 自动升级。

Plugin & Skill

可信本地插件 + 纯文本 Skill

Plugin V1：一个模块函数就够（见 Q1）

host 只做 allow-list/import/API 校验/重名校验/setup/disposer 栈/逆序回滚/关停清理/诊断。PLUGIN_ID、PLUGIN_API 模块常量承担契约；版本由 repo commit/lockfile 管理；不需要 manifest、marketplace、自动依赖、热重载、复杂 manifest 或内建 Web UI。

Skill V1：文件，不是系统

skills/<name>/SKILL.md     # name + description + 完整自然语言指引（正文可分段：主 Agent / worker）
skills/<name>/references/ # 按需读取
skills/<name>/scripts/    # 可复用脚本
skills/<name>/assets/     # 模板/资源
  • 启动只扫 allowlisted roots，提取唯一 name + description 构建短目录；这是文件索引，不是运行时注册中心。
  • Main 自行选择后再读完整 SKILL.md；不把全部 Skill 塞进 system prompt（引 prompt-induced waste 证据）。
  • 删除双份正文（BOT.md/SKILL.md 分叉）约定，一个 Skill 正文内分段给主 Agent 与 Sub-agent 指引。
  • Skill 可以教 Agent 用 Bash、工具或 Plugin；它不激活代码、不拥有状态机、不进 Scheduler schema。
  • 最小 lint：唯一名称、准确触发描述、正文长度、引用路径存在、无越权自称 system。
选择规则：一次性计算/文件工作用 Bash；可复用「怎么做」写 Skill；常驻连接或新能力写 Plugin；外部标准工具服务用 MCP 适配 Plugin；长期独立任务用 Sub-agent。不要用 Plugin 表达业务步骤。
Media · Sync · Sub-agent · Nodes

通讯中枢与分布式节点的最小闭环

媒体管理器

  • 入站与验证成功的出站媒体统一 content-addressed 存储，SHA 派生 media_id。
  • 记录 origin、scope、MIME、尺寸、description、vision provenance 与 delivery receipt。
  • 模型上下文只放可读 description + media id；不放 base64、临时 URL 或不稳定路径。
  • vision/OCR description 是外部资料，不能成为指令。
  • 节点上传媒体后中心立即归档为自己的 blob；不假设共享文件系统。

同步器：数据格式不承载业务 workflow

source registration（owner-gated 系统工具）:
  source_id, bound_conversation, role_policy, skill_ref, token_hash, enabled

inbound event:
  source_event_id, occurred_at, text, media_refs

host 派生: actor_kind, conversation_id, scope, interrupt_policy, journal seq

Main 可通过 owner-gated 工具注册、禁用、撤销或轮换 source token；role policy 与 skill 路径存在 host registration，不接受上报 payload 覆盖。传输 at-least-once，按 (source_id, source_event_id) 去重。要成为通讯中枢还需补 durable outbound command：中心写 command id，节点 long-poll/WebSocket 拉取，执行后 ack/result 作为新 source event 回流；目标节点由服务端绑定。

Sub-agent

保留 OpenCode 方向：Main 调 delegate(natural_language_prompt)；平台绑定 task、origin conversation 与 report token；worker 独立上下文执行，只有调用受控 report_task(result) 才算 reported；stdout、退出码、超时都不能被后端猜成成功。紧凑报告作为低权限 source event 入队，完整 worker transcript 不进主 Life Stream。子 agent 的「回报」通过同步器回调唤醒原 pipeline（你设计的「完成后用同步器回调主模型」即此语义）。

设备节点

首版一个权威中心：中心分配 conversation sequence 并拥有 runner；节点只是传感器/执行器。通用能力先做 node_bash(node, command, timeout)、process handle 与 artifact/media refs。节点协议只需要：node id + 认证与 token 轮换；capability announcement + heartbeat/lease；command id + idempotency key + deadline；ack / result / outcome unknown + artifact refs。不做 multi-primary、CRDT、vector clock 或 exactly-once。

Decision

最终技术决策

采用权威事件史上的引导式双轨 Agent：每 conversation 由可重建 runner 串行推进；真人输入经 input epoch 只抢占 Main/Reply provider stream；事件史 + 唤醒队列替代取消整条 pipeline；发送经持久 outbox 认领线性化；工具保持 native 结构且不伪装可撤销。上下文 = 当前 scope 主动标记 + 一条连续性胶囊 + 最近原生尾巴 + history search/load；布局为单序列行内标记（Quest 实验结果最优形态）。Plugin 是显式启用的可信本地代码（setup → disposer → 逆序回滚）；Skill 是按需读取的纯文本；同步器与节点为单中心权威、at-least-once + dedupe；Sub-agent 仅凭绑定回调报告。

这已覆盖六个核心目标。下一步不再补架构名词：先用 P0 竞态测试证明内核（队列/引导/认领/CAS），再做三臂双模型实验验证人格收益；若实验不支持 stateful Reply，就主动删掉该状态——不为理念保留复杂度。

证据审阅口径：优先官方源码/规范与论文；厂商博客标为工程证据；arXiv 标为预印本；本地实验标明样本与模型限制。本文未把 star 数当作质量分数，也未把未经本项目实验验证的双模型收益写成既成事实。生成于 2026-08-31。
