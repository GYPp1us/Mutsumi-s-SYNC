2.3 experiment/context-v2 — USC 上下文基准（2026-08-04，当前分支）

提出 Unified Simple Context (USC)：每个会话只维护「一条累积摘要 + 一个有界原始回合窗口」， 放弃全局账本、Episode 覆盖/前沿验证、audience/visibility 状态机与三重 legacy 兼容路径； 回收在写入时进行（旧摘要 + 新片段 → 新摘要的单次 LLM 合并，强制「用户事实清单」段落）。 实现 src/mutsumi_sync/context_v2.py ≈300 行，对照的基线是真实生产投影代码 （MessageStore + episodes + build_life_stream，≈2300 行）。

分支同时完成了三件基线 major 修复（只帮助基线、不偏向 USC）： F1 上下文超限时诚实失败（ContextBudgetError，此前只打日志仍发超限请求）； F2 Episode 摘要 max_tokens 500 → 4000/8000 + 空内容重试—— 修复前推理模型下压缩 100% 失败，生产端到端不可用； F3 消息/合并摘要 max_tokens 提升 + 删除死代码 _recycle_window_if_needed。

进度：完整基准已跑完（8 事实 × 3 时间深度 × 5 个 (规模,预算) 条件 × 2 次重复 + 多用户一致性实验），18 个结果 JSON 已归档；论文风格报告 docs/experiments/context-v2-comparison.md 完成。结果见 §4.1。

关键文件：src/mutsumi_sync/context_v2.py · experiments/context_v2/*（run_recall.py / run_consistency.py / baseline_ctx.py / results/*.json）· docs/experiments/context-v2-comparison.md

2.4 codex/context-v3-experiment — Quest Context 多角色实验（2026-08-05）

把问题从「单会话召回」推进到「多角色事项」（Project Atlas：群聊 + Alice/Bob/Carol 三条私聊 + OpenCode Worker 回报 + scheduler 定时 + fan-out 投递；用例即 skills/nature-daily-cet4）。 设计探索稿（docs/quest-context-design.html）提出四路线：A 地址化邮箱 / B 黑板 + 私人透镜（推荐）/ C 全角色格式化单窗口（用户方案）/ D 当前 Ledger。 实验对三条可实现路线（ledger_projection / task_room_usc / formatted_llm） 做了短场景（9 用例、无噪声、2 次全量）与长场景（320 条噪声 + 28 条核心事实、13 用例、regraded 汇总）。

5. 综合对比结论

结论一：两个独立实验收敛于同一判断——复杂度与收益不匹配 USC 基准（单会话超长历史）与 Quest 实验（多角色长噪声）用完全不同的场景和实验设计， 各自独立地证明：复杂投影机制的信息瓶颈不在元数据完备性，而在压缩层提示词、预算粒度与稳定性。 Ledger 投影 ≈2300 行 vs USC ≈300 行；成本 2–7 倍；且在基线自身的边界预算上（8K/1000 轮）和长噪声下 （boundary 0.00）出现结构性失败。设计文档「有界投影不得伪装成完整覆盖」的红线被 build_life_stream 的静默丢 Episode 行为实际违反——模型完全不知道更早历史存在过。
结论二：后端控制面不可省，且是两者共识 Quest 设计稿的六字段（task_ref / source / target / visibility / dedupe+status / artifact_ref）与 USC 建议保留的「TO_SELF/TO_USER 协议、inner journal、status_update、staging 语义」同属一类： 身份、可见性过滤、目标校验、幂等、真实回执必须由服务端强制，实验证明模型在长历史下对此不可靠 （ledger 边界崩溃、send 误用、fan-out 失配均源于把控制面交给模型）。
结论三：模型面对的布局应该极简，两个设计给出同族答案 USC 的「一条摘要 + 有界窗口」与 Quest 的「单窗口 + 每行内联 <ROLE_RECORD> 角色头」是同族方案： 都是单一序列、行内结构化、无嵌套实体。差异只在回收方式（写入时串行合并 vs 不回收/提示词承载）。 Quest 明确建议「Room/投影不应成为模型必须理解的结构」；USC 的串行累积摘要恰好弥补 formatted 方案缺回收的短板。
结论四：分歧点与判据 唯一实质分歧是 Ledger 的去留：USC 主张上下文路径完全不读 Ledger（降级为审计）； Quest 主张 Ledger 保留审计/恢复价值但模型布局改 formatted。判据（尚未实验）： memory_search 与 Episode 的检索断层、恢复重建、以及跨会话溯源审计在生产中的真实价值。 两个方案都不否认 Ledger 的审计价值，分歧只是「模型输入路径」是否还走投影。
结论五：实验自身暴露的生产缺陷清单（与设计路线无关，均应修复） ① Episode 摘要 max_tokens 不足（F2，已修于实验分支，未合并）； ② Episode 静默丢弃无 omission 标记（§5.1）； ③ 请求时压缩不稳定（空摘要 → 压缩中断）； ④ memory_search 与 Episode/工具结果互不可见（implementation-guide §9-2）； ⑤ messages 双写与「只读兼容」宣称矛盾（implementation-guide §9-1）； ⑥ delegate prompt 三要素缺失是三个设计的共同短板（L1 规则层可修）。
