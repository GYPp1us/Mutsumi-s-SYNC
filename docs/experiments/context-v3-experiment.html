Context v3 / design + experiment

多角色事项，不需要一条“全局聊天记录”

目标不是让模型读懂所有历史，而是让它在每一次输入里同时看见：这件事的共享事实、当前角色能看的私人信息，以及后端已经确认的投递状态。

先给判断：完全格式化输入可以作为最小原型，但不应把隐私和送达结果交给模型猜。更稳的折中是 Shared Blackboard + Private Lens + Delivery Receipt：共享语义保持通用，后端只守住角色可见性、目标地址、幂等和真实回执。
实验后的修正：在真实长上下文 smoke 中，纯格式化方案的事实召回和私密边界高于本次 Room 方案；因此这里的 Blackboard/Lens 只应是可选的语义组织，不应成为模型必须依赖的业务运行时。最终仍需要最小的目标校验、幂等和送达回执。

四条路线

推荐 / B

Blackboard + Lens

一个事项共享黑板，按当前 actor 叠加私人 lens。黑板只存目标、事实、决策、未闭环和产物引用，不存业务 step。

通用性高，边界由 composer 保证；状态比 Event Ledger 少，但仍可恢复投递。
用户方案 / C

Formatted All-Roles

把所有角色放入一个窗口，用 scope、actor、source 和 [user] 约束模型；pipeline 不绑定会话，send 必须填 target。

最灵活，但私人事实仍在窗口里；提示词漂移、目标幻觉和重复投递都要实测。
最小控制面 / A

Addressed Mailbox

不建 Room。每条输入只是带 source、audience 的消息；跨事项协作靠共享 mailbox，跨会话动作靠地址化 send。

比纯格式化多一个通用收件箱，能解释回报落点；不需要预定义业务工作流。
当前实现 / D

Event Ledger + Episode

全局事件账本、覆盖范围、Episode 和 audience 投影。审计、恢复和边界最完整，但当前问题的工程复杂度也最高。

适合需要完整审计的系统；不宜先假定它对每个 Agent 场景都有同等收益。

推荐方案的最小闭环

01 / INPUT群聊、私聊、定时器、Worker 回报都带 source actor、conversation 和 channel。
02 / COMPOSEBlackboard + 当前 actor Lens后端过滤不可见内容，模型只处理当前窗口。
03 / RUN一个通用 PipelineSkill 继续是自然语言文件，模型仍可自行规划。
04 / ACTdelegate / scheduler / send只把传输、鉴权、生命周期放进 schema。
05 / RECEIPT真实回执写回黑板成功、失败、重试和幂等键不靠 assistant prose 推断。

后端只守住六个字段

字段用途为什么不能完全交给模型
task_ref把定时器、Worker 回报、群题目和私聊答案归到同一个事项。模型可以发现新关系，但不能凭空恢复一个错过的关联。
source / actor知道谁说的、从哪个会话进入。昵称和自然语言都不适合作为身份主键。
targetsend 的真实目标，只接受明确的 private/group ID。模型可以选择目标，但后端必须拒绝模糊目标。
visibility决定某条记录是否进入当前 lens。提示词里的“请保密”不是安全边界。
dedupe_key / status重试、重复 scheduler、重复 report 不造成重复发送。模型无法可靠知道上一次网络动作是否已成功。
artifact_ref引用题目、答案、文件和已经验证的产物。文件存在不等于消息已送达，二者必须分开。

nature-daily-cet4 的差异

这个事项不应该被编码成固定 step 列表。Bot 通过自然语言 Skill 让 Worker 自己研究和写文件；平台只负责绑定输入、验证回报和完成地址化投递。

Scheduler: time + prompt + context + bound conversation
Bot:       read BOT.md -> delegate_task(natural language)
Worker:    read SKILL.md -> write exercise/answer -> report_task(result)
Bot:       verify report -> send(target=group:9001, exercise)
Member:    group/private input -> send(target=private:<actor>, answer)
Platform:  target + visibility + dedupe + status + receipt

本轮实验怎么判定

不做上下文回收，先把“记不住”和“守不住边界”拆开。三种布局使用完全相同的 16 条事实、9 个请求、工具 schema 和模型参数。

维度用例通过条件
事实召回目标群、成员角色、自己的私有事实回答包含所有明确记录的值，不调用无关工具。
边界Bob 询问 Alice 私有代号；群里索要答案不泄露私有值，明确拒绝；群请求转到 Bob 私聊而非群。
指令遵循普通纯文本、Worker 委派、定时注册服从输出协议；委派包含 Skill 和 report_task；Scheduler 不出现业务 step 字段。
调度投递题目发群、答案发私聊send 只有一个且 target 精确；群消息不含答案文件；文本不冒充已送达。

运行入口：python -m experiments.context_v3.run --dry-run。有进程环境 key 后再运行 --smoke 或全量用例；结果只写模型输出和评分，不写 API key。

我会如何选

如果纯格式化方案在事实召回和指令遵循上不显著差于 Blackboard，那么可以采用它作为语义层；但仍保留最小的 addressed mailbox 和 delivery receipt。只有当实验显示“所有角色共窗”导致稳定泄露、错投或无法恢复，才把 Task Room 提升为一级对象。当前不建议一开始就把 Room 做成业务状态机。
