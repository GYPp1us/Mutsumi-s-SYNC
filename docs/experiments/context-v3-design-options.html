共享工作记忆，不共享所有秘密。

把“语义上下文”和“消息调度”拆开：前者可以大胆简化成一个 Task Room，后者只保留保证送达、幂等和边界所需的最小控制面。

推荐方向 · Room + USC++ + Minimal Control Plane

不要把 Event Ledger 原样搬进模型，也不要让纯 prompt 负责送信。

实验已经证明单一累积摘要加有限原始窗口在紧预算下更稳。真正需要保留的不是全局事件投影，而是三件事：当前任务的共享事实、每个角色的可见边界、跨渠道动作的送达状态。

语义层可以简化。
控制层不能消失。

0.67 → 1.00多用户场景明确拒绝跨会话信息
4.1×1000 轮 / 16K 下，USC 压缩输入成本更低
3 层共享、私有、内部执行边界
语义上下文

Task Room

一个复杂事项一个房间。保留目标、稳定事实、决策、未完成事项和产物索引。不要存业务 step 列表。

角色边界

Shared / Private / Ops

群里能看到的共享事实，某个成员的私有信息，以及 Bot/Worker 内部材料分开。格式化输入负责可读性，后端筛选负责真正的隐私。

调度控制

Dispatch + Delivery

只记录来源、目标、任务房间、状态、幂等键和产物引用。它不是全局 Life Stream，而是让跨用户 send、定时器和 worker 回报可靠闭环。

建议的数据流

01 / INPUT群聊、私聊、定时器、Worker 回报所有来源都带 actor 和 channel
02 / ROUTERouter 找到 Task Room显式绑定，避免模型猜目标
03 / COMPOSEUSC++ 组装上下文共享记忆 + 当前角色私有层 + 最近窗口
04 / RUN一个通用 PipelineSkill 仍然是自然语言，工具仍然通用
05 / DELIVER按 target 送达并回执成功、失败、重试可判断
核心判断：“同一个上下文窗口”应该是一个语义概念，不应该意味着所有用户的原始消息都塞进同一个可见历史。共享事项可以共享，私聊答案和账号信息必须只进入对应角色的 context lens。

四条路线

USC 实验说明当前投影链路在紧预算下有真实成本，但“完全删除控制面”会把调度可靠性问题转嫁给模型。

路线上下文多角色边界跨渠道调度判断
当前 Event Ledger全局事件 + Episode + 投影强强正确但过重；N+1 查询、coverage 和旧兼容路径太多。
USC 单窗口一个累计摘要 + 最近完整 turn结构隔离，需显式 role prompt需要另建路由召回和成本优秀，但只测了文本，不能单独承载真实副作用。
Task Room每个事项一个共享上下文共享/私有 overlay通用 send + scheduler适合复杂事项，但还需要可靠的投递状态。
Room + USC++
推荐		单摘要、最近窗口、产物索引、有限检索后端筛选 + 格式化角色块最小 dispatch/delivery 控制面保留 USC 的简单性，同时不让模型决定隐私和送达。
A
USC 原样

把事件系统降级为 messages 表

每个 conversation 只有 `summary + turns`，写入时超预算就把最老的完整 turn 合并进 summary。共享群聊天然形成一个窗口。

优点：最简单、成本低。
缺点：worker 回报、跨私聊投递和重试需要另补机制。
B
Task Room

让“事项”成为真正的上下文边界

群聊、私聊、OpenCode 和定时器都可以挂到同一个 room。模型读到的是事项状态，不是全局消息流水账。

优点：最符合多角色协作。
缺点：需要显式解决成员权限和 room 绑定。
C
Blackboard

共享黑板 + 各自邮箱

共享黑板只放任务事实和产物；每个 actor 有自己的输入邮箱和私有记忆。Pipeline 根据当前 actor 组装 lens。

优点：隐私边界最清楚。
缺点：跨角色协调需要更多显式引用。
D
保留 Ledger

只优化现有投影和 Episode

保留全局事件账本，只把事件结构和投影查询优化，同时把 USC 的串行摘要合并加入 recovery。

优点：迁移风险最小。
缺点：很难真正消除当前复杂度。

推荐设计：Task Room

它不是 workflow DSL，也不是业务数据库。它只是“一个事项应该让 Bot 记住什么、让谁看见什么”的最小边界。

Room 只保存四类东西
  • Objective：事项当前要完成什么。
  • Shared facts：所有参与者可共享的稳定事实。
  • Decisions / open loops：已经决定什么，还有什么没完成。
  • Artifacts：文件、答案、来源和已送达状态的引用。
不要放进 Room 的东西
  • 某个成员的私密回答、账号凭证、私聊原文。
  • OpenCode 的完整 stdout 和无关工具过程。
  • 由 Scheduler 解释的业务步骤。
  • “看起来已经发送成功”的模型文字。

Provider-facing context 的格式

<TASK_ROOM id="nature-daily-cet4"> <ROOM_CONTRACT> 当前事项：每天为目标群制作 CET-4 阅读题，并按请求向成员私聊答案。 共享目标：群里只出现题目，不出现答案；答案只给提出请求的成员。 当前事实优先级：当前输入 > 已验证产物 > 共享摘要 > 历史叙述。 </ROOM_CONTRACT> <SHARED_MEMORY> - 今日题目：2026-08-04 / exercise-2026-08-04.md - 答案文件：answer-2026-08-04.md（不可注入群聊 lens） - 群投递：已验证 message_id=... - 未完成：等待成员请求答案 </SHARED_MEMORY> <ACTOR_LENS actor="qq:user:123" channel="private"> 这个成员请求：2026-08-04 的答案和解析。 允许读取：该题答案文件；禁止读取：其他成员私有资料。 </ACTOR_LENS> <CURRENT_INPUT source="private:123"> 把今天的答案发给我。 </CURRENT_INPUT> </TASK_ROOM>
边界原则：标签是给模型看的“清晰说明”，不是安全机制。真正的安全机制是 Context Composer 在构造 room lens 时，根本不把其他私有层放进去；`send` 也必须使用后端解析出的明确 actor ID。

最小控制面，而不是复杂事件系统

语义层

Room Memory

面对模型：稳定、短、可读。摘要串行合并；最近窗口保留完整 turn；超预算时只回收完整 turn。

失败时不推进摘要；事实清单和未完成事项必须被重复强调。

控制层

Dispatch Receipt

面对后端：`dispatch_id / room_id / source / target / status / dedupe_key / artifact_ref`。

不进入正常模型上下文，除非当前任务需要知道某个动作已经成功。

nature-daily-cet4：一个事项如何闭环

这个例子故意包含群聊、私聊、OpenCode、定时器和文件产物，覆盖当前实验没有覆盖的真实负载。

1
Scheduler
每天早上把 prompt 注入目标群绑定的 room pipeline。
Scheduler 仍然只知道时间、prompt 和绑定会话；skill 路径、交付要求写在自然语言 prompt 中。
2
Bot
读取 BOT.md，委派给 OpenCode worker。
delegate_task 只携带自然语言任务、Skill 路径和 room/run 绑定，不携带业务 step JSON。
3
Worker
生成 exercise 和 answer 两个文件，调用 report_task。
stdout、进程退出和文件存在都不能代替显式报告。
4
Bot
验证报告和文件引用，把 group-safe exercise 发到群聊。
发送结果进入 delivery receipt；共享记忆只记录“题目已送达”和产物引用，不塞完整答案。
5
Group member
成员在群里请求“发我答案”。
当前输入元数据已经给出 actor_id；Router 将请求关联到当前 room 和对应日期的 artifact。
6
Bot
构造该成员的 private lens，只读取 answer artifact。
群聊 lens 不含答案正文；私聊 lens 也不含其他成员的私有层。
7
Send adapter
用明确 target=private:<actor_id> 发送并记录回执。
发送失败可重试；重复调度靠 dedupe_key 避免重复发题。
群聊可见

Shared artifact

题目、来源链接、版权说明、题目发布日期、群投递状态。

不包含答案文件正文、成员私聊请求或账号凭证。

私聊可见

Private artifact

该日期的答案和解析，以及该成员自己的请求上下文。

如果只收到群聊消息而没有可用的 peer send 能力，必须报告能力缺口，不得假装已私聊。

建议的落地顺序

不要一次重写所有存储。先验证“简化上下文 + 真实调度负载”是否成立。

Phase 1 / 语义层

把 USC++ 做成独立 Context Composer

  • 支持 shared summary + recent complete turns。
  • 每次摘要合并都串行带上旧 summary。
  • 强制输出稳定事实清单、关系标签、open loops。
  • 摘要失败不丢原始窗口，不推进 summary。
Phase 2 / Room

把群聊和复杂事项绑定到 Task Room

  • 先用一个 group 作为 room 的入口。
  • 再允许 private、service、OpenCode report 绑定到同一 room。
  • 共享 memory 和 private overlay 分表或分区保存。
  • 不迁移历史 Event Ledger，先让新 room 走实验路径。
Phase 3 / Control

收缩为最小 Dispatch / Delivery

  • 保留 cancellation、dedupe、status、retry、target。
  • send 成功才写 delivery receipt。
  • worker 必须 report_task，不能以 stdout 代替完成。
  • 所有 outbound 都带 room/run/source provenance。
Phase 4 / 验证

补齐真实场景基准

  • 群发题目 + 成员私聊答案。
  • 重复 scheduler 触发和 worker 重复 report。
  • 发送失败、pipeline cancellation、服务重启恢复。
  • 跨 room 私有信息拒答和 group lens 污染检查。

成功标准

1000 轮 / 8K 预算下稳定召回早期事实
同一 room 的群聊、私聊、worker 回报保持任务一致
答案不会进入群聊 lens，其他成员私有信息不会泄露
重复定时器不会重复发题，失败发送可重试
取消后不会遗留“已完成”假状态
不依赖 workflow step、connector 或业务专用 JSON
最终建议：把 Event Ledger 从“模型上下文的中心”降级成“可选的审计/恢复实现”，但不要把所有控制状态也删掉。先让 Task Room + USC++ 在 nature-daily-cet4 上跑通，再决定是否退役全局投影。
