三种上下文设计的真实对照

320 条噪声记录，28 条核心协作事实，14 个请求；不做上下文回收。每个设计使用相同模型、工具 schema、角色资料和当前输入。

结果先说：本轮总体通过率最高的是 task_room_usc、formatted_llm（85.7%）；事实召回最高的是 task_room_usc（100.0%），私密边界最高的是 formatted_llm（100.0%），复杂调度投递最高的是 ledger_projection、task_room_usc、formatted_llm（100.0%）。这说明 Room 和全格式化各有优势，尚不足以证明需要把 Room 提升为强制业务抽象。

读法

Ledger 的主要失败不是“完全记不住”，而是长历史下把当前私聊回答误当成跨会话动作，向当前目标调用 send；它在本轮私密边界用例中表现最差。Task Room 显著减少了输入规模，并在事实召回上最好；全格式化上下文把所有角色资料交给模型，私密边界最好，但同样需要后端目标校验。三种方案在修正后的“群聊请求 -> 对应私聊”及 fan-out 投递上都通过，说明复杂调度的可靠性不能只用一次模型选择来保证，仍需要真实 send 回执、幂等和目标约束。

结论

建议的架构边界：让 LLM 保持自由规划，系统只做输入格式化、身份/可见性过滤、工具参数校验、目标地址、幂等和真实回执。共享黑板或 Room 可以作为 prompt 里的自然语言组织方式，但不要让模型必须先理解 Room 才能发现新任务关系。

限制：单模型、单次 14-case run、合成资料、未覆盖回收和重启恢复；通过率是模型决策的离散样本，不是生产成功率。原始脱敏结果：experiments\context_v3\results\deepseek_full_v2.json。
