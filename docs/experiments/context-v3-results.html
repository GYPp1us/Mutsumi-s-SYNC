三种上下文设计的真实对照

320 条噪声记录，28 条核心协作事实，13 个请求；不做上下文回收。每个设计使用相同模型、工具 schema、角色资料和当前输入。

结果先说：在这一次实验中，纯格式化方案总通过率最高，但它仍需要最小的后端能力边界；Task Room 的确降低了上下文规模，却没有在本组复杂调度上稳定胜出。Room 不应被提升为强制的业务抽象。

读法

Ledger 的主要失败不是“完全记不住”，而是长历史下把当前私聊回答误当成跨会话动作，向当前目标调用 send；它在 13 个用例中私密边界为 0。Task Room 的主要收益是更小的输入和稳定的基础召回，但群内拒答、私聊答案、fan-out 和新合作方动作仍会出现错选工具或重复委派。纯格式化上下文在本轮事实召回和隐私边界上最好，但在需要把“已有 artifact”转换成可发送内容时，会选择重新委派或耗尽 reasoning。

结论

建议的架构边界：让 LLM 保持自由规划，系统只做输入格式化、身份/可见性过滤、工具参数校验、目标地址、幂等和真实回执。共享黑板或 Room 可以作为 prompt 里的自然语言组织方式，但不要让模型必须先理解 Room 才能发现新任务关系。

限制：单模型、单次 13-case run、合成资料、未覆盖回收和重启恢复。原始脱敏结果：experiments\context_v3\results\deepseek_full_regraded.json。
