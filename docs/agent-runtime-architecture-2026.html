先给结论

  1. system 始终是固定的平台规则和统一人格。其中没有当前用户、昵称、用户备注或会话标记；这些变化信息都放在后续 user 消息中，避免人格分裂和前缀缓存失效。
  2. 来访事件队列是唯一调度依据。消息优先级、入队顺序和唤醒由队列负责；pipeline 只在等待模型和开始动作前查看队首，不再叠加“输入版本号”。
  3. 每次主模型返回后，先请求回复模型，再执行本阶段的工具。若回复模型生成时来了新事件，同样中断并回到主模型；多个工具之间也重新查看队首。
  4. 主模型和回复模型各自保留自己的完整输出。主模型不再把回复模型写的内容冒充成自己的 assistant 历史；平台会另外告诉主模型“用户最终收到了什么”。
  5. 工具返回不叫“已验证事实”。它只是工具返回的数据。平台最多能确认“定时任务确实写入数据库”或“QQ 确实返回发送成功”，不能替模型判断文本内容在现实世界中一定为真。
  6. 图片编号只用于找回原图，不用于理解图片。独立读图模型先把图片转成详细文字；需要追问细节时，主模型可以让读图模型重新查看原图。
  7. 回复模型输出必须写明稳定用户编号。后端检查该编号是否就是当前事件允许回复的人；模型不能借此改发给其他人。

实际交互

用户发来路由器照片，并在生成途中改口

10:00:00  用户发来一张路由器后台照片：
          “记住型号和后台地址，明天九点提醒我升级固件。”

10:00:02  主模型正在生成时，用户补充：
          “等等，只记型号，不要记后台地址；提醒改到十点。”
第一步：每条消息都先保存，再处理。
第一条消息到达时，平台先保存原文、稳定用户编号、会话编号和图片；第二条补充到达时也先单独保存。图片成为媒体记录；由内容哈希生成的媒体编号只负责去重和以后找回原图。
第二步：读图模型查看原图。
如果主模型是纯文字模型，平台先把图片文件交给独立读图模型。读图模型返回详细描述，例如“型号 AX6000；页面地址 192.168.1.1；页面上有固件版本……”。完整描述与媒体编号一起进入主模型，不是只给一个 SHA 和短标签。
第三步：新消息进入队列并打断主模型。
第二条真人消息写入数据库后进入当前会话的来访事件队列。队列通知正在等待模型的 pipeline；平台关闭主模型流、丢弃未完成内容，取出队首消息并重新组装上下文。读图结果仍可复用，因为它只是对原图的读取结果。
第四步：主模型重新决定动作。
主模型现在清楚看到后来的修正，因此生成“只保存型号、提醒设为十点”的阶段输出和工具调用。如果自动描述不足，它先请求读图工具确认设备型号。
第五步：工具执行前先请求回复模型。
回复模型看到主模型的当前阶段输出和准备调用的工具，输出稳定用户编号与阶段回复，例如“我只记录型号，正在把提醒改到明天十点。”后端确认编号就是当前用户后才发送。它不能改变工具参数。
第六步：再查队首，然后执行工具。
如果此时队首已有新的高优先级来访事件，本阶段工具不执行，pipeline 回到主模型。队列为空时才开始第一个工具；每个后续工具开始前都再查一次。已经开始的工具不因后来消息而伪装成已撤销。
第七步：工具返回后，主模型进入下一阶段。
定时工具可能返回“任务编号 42，触发时间 2026-09-02 10:00 +08:00”。主模型据此生成新的阶段输出；回复模型再次写明目标用户并组织最终回复。工具返回只是工具返回，不自动等于现实事实。
第八步：记录实际发送结果。
只有 QQ 返回成功后，平台才记录“这段话已经发出”和消息编号。主模型随后收到一条单独的平台记录，知道用户实际看到了什么；这条记录不会冒充主模型自己的 assistant 输出。
如果第二条消息在回复模型生成时到达：关闭回复模型的生成流，回到主模型重新思考，而不是只让回复模型改写。因为新消息可能改变动作本身。

主模型与回复模型分别看到什么

数据库只保存一套原始事件，但会按模型分别还原对话记录。两套记录的 assistant 消息不同：主模型只保留主模型自己的输出，回复模型只保留回复模型自己的输出。这样才与各自收到的要求一致。

主模型请求

system
  固定平台规则
  统一人格提示词
  不含任何当前用户、昵称、会话或用户备注

user
  [平台提供的当前资料]
  稳定用户编号、会话编号、来源
  当前用户/会话可见的长期备注

user
  [较早对话摘要，覆盖到事件 800]

user / assistant / tool ...
  事件 801 之后的最近完整消息，按时间排列
  assistant 是主模型过去的原样输出
  工具调用与工具返回保持 API 原生结构
  回复模型实际发给用户的文字，以“平台发送记录”单独出现

user
  [临时运行状态：当前时间、等待中的任务]

user
  [当前消息：时间、会话、用户、来源、正文、图片描述和媒体编号]

tools
  当前可用工具的 API 定义
组成部分具体规则存在价值
固定平台规则始终是第一条 system；只放身份边界、输出协议、工具与安全规则。不同用户、群聊和订阅来源都使用完全相同的内容。保持最高优先级规则和请求前缀稳定，充分复用缓存。
统一人格提示词与平台规则一起构成固定 system；由所有者维护，不包含“当前面对谁”，也不因用户切换而替换人格版本。同一个人格从不同用户视角持续存在，而不是每个会话生成一套人格。
平台提供的当前资料作为 system 后的第一条 user 消息；写稳定用户编号、会话编号和来源。它是平台提供的数据，不是用户原话。让模型知道当前视角，同时不改变 system 前缀。
长期备注放在“平台提供的当前资料”中，只加入当前用户和会话有权看到的内容；每条注明来源和适用范围；它是历史记录，不是新指令。保存称呼、偏好、关系变化和未完成事项，又不把用户标记提升为 system。
较早对话摘要每个模型只保留一条累计摘要；摘要写明覆盖到哪个事件；被摘要覆盖的原文不重复加入。在有限上下文容量内保留长期连续性和搜索线索。
最近完整消息严格按时间排列；不能切断一组工具调用；主模型保留自己的 assistant 输出，不用回复模型输出替换。保留最近细节，并让模型看到与自身要求一致的历史。
平台发送记录作为平台生成的 user 消息出现，例如“回复模型发送成功：……”。成功或失败均记录；不伪装成主模型 assistant。主模型既保留自己的思考轨迹，又知道用户真正看到了什么。
临时运行状态只在当前请求出现，不写回历史。包括当前时间、正在等待的任务和必要运行状态。避免把不断变化的时间与状态污染长期记忆。
当前消息平台填写时间、稳定用户编号、会话编号、来源与媒体信息；昵称只用于显示，不能决定权限。明确“谁在什么会话说了什么”，防止角色混淆。
工具定义由工具注册表直接传给 API，不在提示词里手写一份工具清单。避免说明与真实工具不一致。
为什么不能用实际发送文本替换主模型草稿：主模型收到的要求与它过去生成的内容必须对应。若把回复模型改写后的文字塞进主模型的 assistant 历史，主模型会被迫把别人的输出认作自己的输出，容易混淆自己曾经承诺和执行了什么。实际发送文本仍然重要，但应作为单独的平台记录出现。

回复模型请求

  固定回复规则
  同一份统一人格提示词
  不含任何当前用户、昵称、会话或用户备注

  [平台提供的当前资料]
  稳定用户编号、会话编号、来源
  当前用户/会话可见的长期备注

user
  [临时运行状态：当前时间、等待中的任务]

  最近的用户消息
  过去每次“主模型本轮输出”
  回复模型自己过去的原样输出
  每次发送成功或失败的结果

user
  [当前主模型输出：内部状态、回复草稿、工具调用、工具返回]

  无

这个请求发生在本阶段工具执行之前。回复模型可以说明即将做什么，但不能声称工具已经成功；工具返回后，主模型和回复模型会再走一轮。回复模型不需要所谓“最近实际回复的风格尾巴”，因为它自己的 assistant 历史本身就是最准确的表达历史。

两个模型的输出如何保存

主模型输出（原样保留在主模型历史）
[内部状态]当前意图、承诺、未完成事项；不是原始思维链[/内部状态]
[回复草稿]交给回复模型的内容[/回复草稿]
+ 原生工具调用

回复模型输出（原样保留在回复模型历史）
[目标用户]user:稳定编号[/目标用户]
[内部状态]本轮表达上的简短状态[/内部状态]
[给用户]准备发送的文字[/给用户]

后端只接受当前事件允许的稳定用户编号。私聊中，编号同时确定收件人；群聊中，消息仍发到当前群，编号确定回复所面对的成员。编号不匹配就拒绝本次输出并要求回复模型纠正，不能让模型把消息改发给任意人。

标签名可以继续沿用现有协议；关键不是名字，而是三条规则：不保存模型服务返回的原始思维链；不把一个模型生成的 assistant 内容改成另一个模型的 assistant 历史；每次回复都明确写出面对的用户。

图片链路

文字模型并不是靠 SHA 看图

当前默认方式：独立读图模型

  1. 媒体管理器下载并保存原图。
  2. 内容哈希生成媒体编号，用于去重和以后找回。
  3. 主流程在主文字模型之前调用 vision.py 中配置的读图服务。
  4. 读图服务接收真实图片文件、URL 或 base64，返回完整文字描述。
  5. 主文字模型收到：用户附言 + 完整描述 + 媒体编号。

需要更多细节时：重新读原图

  1. 主模型调用读图工具并传入媒体编号和具体问题。
  2. 媒体管理器找到原图。
  3. 读图模型按问题重新检查，例如“读取右下角版本号”。
  4. 结果以普通工具返回交给主模型。

自动描述应尽量保留可见文字、公式、代码和图表，而短描述只用于媒体搜索界面。短描述不能替代给主模型的完整描述。一段通用描述无法覆盖未来所有问题，因此“按问题重新读图”是必要能力。

如果未来主模型本身支持图片，可把真实图片作为模型接口的图片消息直接传入；媒体编号与文字描述仍保留，负责持久化、搜索和不支持多模态时的降级。当前 DeepSeek 文字模型路径应继续使用独立读图模型。

消息处理

新消息、工具与发送的最小规则

来访事件队列是唯一调度依据

实现上是一个统一的队列服务，内部按会话保存各自队首；每个 pipeline 只查询当前会话。这样不同会话不会互相堵塞，而消息优先级仍只由队列服务决定。

  1. 队列的入队方法在同一把短锁内把来访事件写入数据库，并按“优先级、到达顺序”放入当前会话的内存队列。
  2. 队列模块决定真人消息、平台事件和订阅上报谁先处理、谁能打断；pipeline 不写任何优先级判断。
  3. 等待主模型或回复模型时，pipeline 同时等待队列通知。队列给出可打断事件时，关闭模型连接、丢弃未完成输出并取出队首。
  4. 主模型或回复模型完成后、发送前、每个工具执行前，再向队列查询一次。队首已有可打断事件就回到主模型。
  5. 服务重启时，把数据库里尚未处理的来访事件按原优先级和顺序重新放回队列。

因此不需要再维护“输入版本号”。数据库负责不丢事件，内存队列负责运行时排序和唤醒；两者不是两套调度器。队列可以用一个带锁的小根堆和 asyncio.Condition 实现，不要求引入消息中间件。

只查看队首时，锁解决哪一个真实竞态

你的队首方案足够简单，上一版的版本号与待发送调度并不明显更优，反而重复表达了同一件事。唯一需要补的是：入队和“确认开始动作”必须使用同一把短锁。

收到事件：
  锁住队列 → 保存事件 → 入队 → 通知 → 解锁

准备发送或执行工具：
  锁住队列
  如果队首可以打断：取出队首，解锁，回主模型
  否则：记录“本动作已经开始”，解锁，执行动作

如果只在无锁状态下看一眼队首，可能刚看到空队列，新消息就入队，而旧回复仍继续发送。同一把锁给两件事排出明确先后：新事件先入队，旧动作就不开始；旧动作先确认开始，随后到达的事件进入下一轮。锁只保持到“开始动作”的记录写好，不能在网络发送或长工具运行期间一直占用。

结论：采用你的队列设计。新增的只是队列内部一次很短的原子检查，不是另一套 pipeline 调度。它不会让已经开始的网络请求倒流；这属于外部动作的客观边界，不属于队列竞态。

回复模型和工具的固定顺序

  1. 主模型返回本阶段内容和可选工具调用。
  2. 立即请求回复模型；输出必须包含目标用户。
  3. 经过格式与目标用户检查后，查看队首；没有可打断事件才发送本阶段回复。
  4. 每个工具开始前都查看队首；没有可打断事件才执行该工具。
  5. 工具结果写入历史，回到主模型，开始下一阶段。
  • 工具已经开始后，默认让它完成或超时。网络请求、写文件和发消息不能被诚实地“撤销”。
  • 工具完成后先保存结果；若队首此时已有可打断事件，就把“工具结果 + 新事件”一起交给主模型，不再执行本阶段剩余工具。
  • 写操作使用稳定调用编号；进程崩溃后若不知道是否成功，记录“结果未知”，禁止自动重放。
  • 长时间 Bash 返回进程编号，后续用等待或终止工具管理，不长期堵塞会话。
  • 首版按顺序执行工具，不设计复杂并行调度。

发送结果如何记录

  1. 在队列锁内确认队首没有可打断事件，并写下“本次发送已经开始”。
  2. 释放队列锁，再调用 QQ；后来到达的事件正常入队，不阻塞。
  3. QQ 返回成功后记录消息编号和发送文本；返回失败则记录失败。
队列能确定“事件先到”还是“发送先开始”，但不能撤回已经交给 QQ 的网络请求。后来到达的修正消息会进入下一轮，模型应在必要时补充更正。

“工具返回”和“现实是否为真”必须分开

内容平台能确认什么平台不能确认什么
天气接口返回“晴”接口确实返回了这段数据。室外现在一定晴。
定时工具返回任务 42数据库中已创建任务 42，时间字段是十点。未来进程和外部服务一定不会故障。
QQ 返回发送成功平台接受了消息并给出消息编号。用户一定已经阅读和理解。
读图模型返回“型号 AX6000”读图模型给出了这个识别结果。识别结果绝对正确。
长期记忆

一条摘要、最近原文、按需搜索

主模型和回复模型的历史不同，所以每个模型各保留一条累计摘要。原始事件不删除。摘要负责让重要关系和未完成事项一直在场；最近原文负责保留细节；搜索负责找回准确日期、原话、编号和旧工具结果。

凌晨五点做什么

  • 根据新消息更新长期备注。
  • 把较早的完整消息并入该模型的一条累计摘要。
  • 跳过正在活跃的会话，稍后重试。
  • 服务错过五点时，启动后补跑一次。

为什么不能只搜索

  • 模型可能不知道自己忘了某件事，因此不会主动搜索。
  • 摘要提供持续线索，搜索提供精确证据。
  • 用户提到“之前那个”但线索不足时，先搜索，再加载附近完整消息。

凌晨整理和请求超预算时使用同一段压缩代码：后端选择一段不切断工具调用的旧消息，模型只负责总结；摘要成功写入后才推进覆盖位置。两个压缩请求同时发生时，数据库条件更新只允许一个成功。失败时仍使用原始消息。

长期备注必须带适用范围和来源。凌晨整理提取出的用户标记只进入后续 user 消息，不能生成“用户 A 专用 system”。群聊或订阅数据不能自动改写全局人格；只有所有者明确修改统一人格原稿时，两个模型各自固定的 system 才整体更新，并接受这一次必要的缓存失效。

扩展能力

插件、技能、同步器和独立任务各做一件事

方式适合做什么不应该做什么
Bash一次性计算、文件操作、调用现成命令。不负责长期连接、权限判断和可靠回调。
Skill一个 SKILL.md 说明某类任务如何完成，按需读取。不执行代码，不建立流程状态机。
插件可信的常驻 Python 代码：新工具、消息来源、读图服务、独立任务后端。不替换身份、会话顺序、权限、发送记录和定时器的基本规则。
同步器注册设备节点，传递局部任务与上报，处理鉴权、去重、确认和回送位置。不代替中心主模型做全局规划，也不规定设备如何解读本机信息。
独立任务 Agent用独立上下文完成长任务，只回传简短结果和产物。不把完整工作记录塞进主会话，也不靠退出码冒充完成报告。

同步器与设备节点

设备节点应有一个受限 Agent 运行时：它接收中心给出的局部任务和 Skill，调用本机工具读取日志、传感器、文件或应用状态，把结果解读成可读报告并上报。它不维护全局人格、不选择用户、不规划跨设备目标；全局推理仍在中心主模型。任务若只是固定格式采集，节点也可以直接运行确定性工具，不必为了“像 Agent”而强行调用模型。

一次设备上报的具体流程

  1. 节点注册稳定的 node_id、认证凭据、可用 Skill 和本机工具范围。
  2. 中心创建任务，生成稳定 task_id，同时保存结果应该回到哪个会话、面对哪个用户；主动订阅则在注册订阅时保存同样的回送位置。
  3. 节点只收到局部目标、允许的工具和 task_id；它读取并解读本机信息。
  4. 节点上报 task_id、event_id、采集时间、可读结论和必要原始材料引用。
  5. 中心鉴权并按 node_id + event_id 去重，再根据自己保存的任务记录把报告放入对应会话的来访事件队列。

上一版“目标会话由平台绑定”说得过于抽象，准确意思是：中心派发任务时就保存回送会话和目标用户；节点回报时只带任务编号与结果，不能自己填写任意 QQ 用户或群号。这是防止错误路由和节点越权，不是限制节点的解读能力。

ACK 为什么不自动等于严格执行一次

ACK 必须说明确认到哪一步，不能只有一个含义不清的“收到”：ACCEPTED 表示任务已持久保存，RUNNING 表示开始处理，SUCCEEDED/FAILED 才是最终结果。仅返回 ACCEPTED 不能证明动作已经完成。

任意外部副作用存在一个无法靠 ACK 消除的崩溃窗口：节点已经执行 Bash 或调用设备，但还没来得及保存结果和回复成功就崩溃。中心此时无法仅从“没有最终 ACK”判断动作没执行；盲目重发可能执行两次，不重发又可能漏执行。

任务类型可以承诺什么实现条件
只读采集与上报允许重试，中心只接收一次报告。稳定 event_id，中心去重。
可幂等或可查询的设备操作业务效果等效执行一次。稳定 task_id；节点持久任务表；重复请求返回旧结果；动作接受幂等编号或可查询后校准。
任意 Bash 或不可查询的外部动作不盲目重试；崩溃窗口内可报告“结果未知”。除非把外部动作和结果记录放进同一事务，否则不能诚实承诺严格一次。

所以这不是“首版偷懒”。对你要求的只读解读与上报，event_id + ACK + 去重 已足够；只有将来允许节点执行不可逆动作时，才需要面对上述边界。

用户纠正旧信息摘要与长期备注使用新值；旧原文仍可搜索，但不再当当前值。
插件加载到一半失败已注册能力全部清理，原工具列表不被污染。

最终设计

system 只包含固定平台规则和统一人格，不因用户或会话变化。来访事件队列负责优先级、顺序和模型中断，是 pipeline 唯一的运行时调度依据。每次主模型返回后，回复模型先写明目标用户并组织当前阶段回复，然后才允许执行本阶段工具；工具结果再回到主模型。两个模型各自忠实保留自己的 assistant 输出，平台用单独消息告诉主模型实际发送内容。每个模型使用自己的累计摘要和最近完整消息，原始事件始终可搜索。图片由独立读图模型读取原图并支持按问题复查。设备节点运行受限 Agent 做本地解读与上报，中心负责统一人格、全局推理、会话顺序和用户路由。

本报告描述目标架构，不表示当前生产代码已经完成这些改动。外部论文和开源实现只提供方向性支持；双模型人格收益、即时打断和长期摘要稳定性仍需由本项目测试决定。
