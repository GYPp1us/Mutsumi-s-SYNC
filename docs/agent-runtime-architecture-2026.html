从一次真实交互讲清重构设计

本版删除了上一版中不必要的专有名词，纠正了“已验证事实”和“风格尾巴”两处错误，并具体说明图片如何被读图模型处理、主模型与回复模型分别看到什么。

修订日期：2026-09-01 仍坚持：自然语言 + Bash + Skill 不增加工作流语言

先给结论

  1. 用户的新消息只打断正在生成的模型请求，不取消整条处理流程，也不假装撤销已经开始的工具操作。
  2. 主模型和回复模型各自保留自己的完整输出。主模型不再把回复模型写的内容冒充成自己的 assistant 历史；平台会另外告诉主模型“用户最终收到了什么”。
  3. 工具返回不叫“已验证事实”。它只是工具返回的数据。平台最多能确认“定时任务确实写入数据库”或“QQ 确实返回发送成功”，不能替模型判断文本内容在现实世界中一定为真。
  4. 图片编号只用于找回原图，不用于理解图片。独立读图模型先把图片转成详细文字；需要追问细节时，主模型可以让读图模型重新查看原图。
  5. 每个模型的上下文都是：固定规则 + 人格 + 长期备注 + 一条旧对话摘要 + 最近完整消息 + 当前输入。主模型另外有工具；回复模型没有工具。

实际交互

用户发来路由器照片，并在生成途中改口

10:00:00  用户发来一张路由器后台照片：
          “记住型号和后台地址，明天九点提醒我升级固件。”

10:00:02  主模型正在生成时，用户补充：
          “等等，只记型号，不要记后台地址；提醒改到十点。”
第一步：先保存，再处理。
平台保存两条原始消息、稳定用户编号、会话编号和图片。图片被保存为媒体记录；由内容哈希生成的媒体编号只负责去重和以后找回原图。
第二步：读图模型查看原图。
如果主模型是纯文字模型，平台先把图片文件交给独立读图模型。读图模型返回详细描述，例如“型号 AX6000；页面地址 192.168.1.1；页面上有固件版本……”。完整描述与媒体编号一起进入主模型，不是只给一个 SHA 和短标签。
第三步：新消息打断主模型。
第二条真人消息到达后，会话的“输入版本号”增加。平台关闭正在生成的主模型流，丢弃未完成内容，然后用两条消息重新组装上下文。读图结果仍可复用，因为它只是对原图的读取结果。
第四步：主模型重新决定动作。
主模型现在清楚看到后来的修正，因此只保存型号，不保存后台地址，并把提醒时间设为十点。如果自动描述不足，它可调用读图工具，要求“只确认设备型号”，工具会再次把原图交给读图模型。
第五步：工具返回后，主模型继续。
定时工具可能返回“任务编号 42，触发时间 2026-09-02 10:00 +08:00”。这叫工具返回，不叫“已验证事实”。平台可以确认数据库中确实创建了任务 42，但不能因此证明照片里型号文字一定正确。
第六步：回复模型组织措辞。
回复模型收到主模型本轮的完整输出和工具返回，结合自己过去的回复历史，写出：“好，只记型号。提醒改到明天十点，后台地址不会保存。”它没有工具，也不能改变提醒时间或发送目标。
第七步：记录实际发送结果。
只有 QQ 返回成功后，平台才记录“这段话已经发出”和消息编号。主模型随后收到一条单独的平台记录，知道用户实际看到了什么；这条记录不会冒充主模型自己的 assistant 输出。
如果第二条消息在回复模型生成时到达：关闭回复模型的生成流，回到主模型重新思考，而不是只让回复模型改写。因为新消息可能改变动作本身。
上下文拼接

主模型与回复模型分别看到什么

数据库只保存一套原始事件，但会按模型分别还原对话记录。两套记录的 assistant 消息不同：主模型只保留主模型自己的输出，回复模型只保留回复模型自己的输出。这样才与各自收到的要求一致。

主模型请求

system
  固定平台规则
  人格提示词
  当前用户/会话可见的长期备注

user
  [较早对话摘要，覆盖到事件 800]

user / assistant / tool ...
  事件 801 之后的最近完整消息，按时间排列
  assistant 是主模型过去的原样输出
  工具调用与工具返回保持 API 原生结构
  回复模型实际发给用户的文字，以“平台发送记录”单独出现

user
  [临时运行状态：当前时间、等待中的任务]

user
  [当前消息：时间、会话、用户、来源、正文、图片描述和媒体编号]

tools
  当前可用工具的 API 定义
组成部分具体规则存在价值
固定平台规则始终是第一条 system；只放身份边界、输出协议、工具与安全规则。外部消息不能修改。让最重要的约束处于最高优先级并保持请求前缀稳定。
人格提示词与平台规则同属 system；由所有者维护，不由群聊、网页或凌晨整理自动改写。维持人格基线。
长期备注只加入当前用户和当前会话有权看到的内容；每条注明来源和适用范围；它是历史记录，不是新指令。保存称呼、偏好、关系变化和未完成事项。
较早对话摘要每个模型只保留一条累计摘要；摘要写明覆盖到哪个事件；被摘要覆盖的原文不重复加入。在有限上下文容量内保留长期连续性和搜索线索。
最近完整消息严格按时间排列；不能切断一组工具调用；主模型保留自己的 assistant 输出，不用回复模型输出替换。保留最近细节，并让模型看到与自身要求一致的历史。
平台发送记录作为平台生成的 user 消息出现，例如“回复模型发送成功：……”。成功或失败均记录；不伪装成主模型 assistant。主模型既保留自己的思考轨迹，又知道用户真正看到了什么。
临时运行状态只在当前请求出现，不写回历史。包括当前时间、正在等待的任务和必要运行状态。避免把不断变化的时间与状态污染长期记忆。
当前消息平台填写时间、稳定用户编号、会话编号、来源与媒体信息；昵称只用于显示，不能决定权限。明确“谁在什么会话说了什么”，防止角色混淆。
工具定义由工具注册表直接传给 API，不在提示词里手写一份工具清单。避免说明与真实工具不一致。
为什么不能用实际发送文本替换主模型草稿：主模型收到的要求与它过去生成的内容必须对应。若把回复模型改写后的文字塞进主模型的 assistant 历史，主模型会被迫把别人的输出认作自己的输出，容易混淆自己曾经承诺和执行了什么。实际发送文本仍然重要，但应作为单独的平台记录出现。

回复模型请求

system
  回复规则
  同一人格提示词
  当前用户/会话可见的长期备注

user
  [回复模型自己的较早对话摘要]

user / assistant ...
  最近的用户消息
  过去每次“主模型本轮输出”
  回复模型自己过去的原样输出
  每次发送成功或失败的结果

user
  [当前主模型输出：内部状态、回复草稿、工具调用、工具返回]

tools
  无

回复模型不需要所谓“最近实际回复的风格尾巴”。它自己的 assistant 历史本身就是最准确的表达历史。单独再截一段“风格尾巴”只会重复信息。

两个模型的输出如何保存

主模型输出（原样保留在主模型历史）
[内部状态]当前意图、承诺、未完成事项；不是原始思维链[/内部状态]
[回复草稿]交给回复模型的内容[/回复草稿]
+ 原生工具调用

回复模型输出（原样保留在回复模型历史）
[内部状态]本轮表达上的简短状态[/内部状态]
[给用户]准备发送的文字[/给用户]

标签名可以继续沿用现有协议；关键不是名字，而是两条规则：不保存模型服务返回的原始思维链；不把一个模型生成的 assistant 内容改成另一个模型的 assistant 历史。

图片链路

文字模型并不是靠 SHA 看图

当前默认方式：独立读图模型

  1. 媒体管理器下载并保存原图。
  2. 内容哈希生成媒体编号，用于去重和以后找回。
  3. 主流程在主文字模型之前调用 vision.py 中配置的读图服务。
  4. 读图服务接收真实图片文件、URL 或 base64，返回完整文字描述。
  5. 主文字模型收到：用户附言 + 完整描述 + 媒体编号。

需要更多细节时：重新读原图

  1. 主模型调用读图工具并传入媒体编号和具体问题。
  2. 媒体管理器找到原图。
  3. 读图模型按问题重新检查，例如“读取右下角版本号”。
  4. 结果以普通工具返回交给主模型。

自动描述应尽量保留可见文字、公式、代码和图表，而短描述只用于媒体搜索界面。短描述不能替代给主模型的完整描述。一段通用描述无法覆盖未来所有问题，因此“按问题重新读图”是必要能力。

如果未来主模型本身支持图片，可把真实图片作为模型接口的图片消息直接传入；媒体编号与文字描述仍保留，负责持久化、搜索和不支持多模态时的降级。当前 DeepSeek 文字模型路径应继续使用独立读图模型。

消息处理

新消息、工具与发送的最小规则

新消息如何打断生成

  1. 每条输入先写数据库，再通知会话处理协程。
  2. 每个会话保存一个只由“可打断输入”增加的版本号。工具返回和模型输出不会增加它。
  3. 等待主模型或回复模型时，同时等待新输入；新输入先到就关闭模型连接并丢弃未完成输出。
  4. 模型与新输入同时完成时，固定让新输入优先，避免随机行为。
  5. 群聊中任何真人的新消息都可打断当前群会话；普通订阅数据默认排队，不抢占真人请求。

内存队列只用于唤醒。进程重启后，处理协程必须从数据库中找出还没有处理的事件，不能把可靠性寄托在 asyncio.Queue。

工具如何处理

  • 工具开始前再次检查输入版本号；已过时的调用不执行。
  • 工具已经开始后，默认让它完成或超时。网络请求、写文件和发消息不能被诚实地“撤销”。
  • 写操作使用稳定调用编号；进程崩溃后若不知道是否成功，记录“结果未知”，禁止自动重放。
  • 长时间 Bash 返回进程编号，后续用等待或终止工具管理，不长期堵塞会话。
  • 首版按顺序执行工具，不设计复杂并行调度。

发送如何避免竞态

不能“检查没有新消息，然后直接发”，因为检查和网络发送之间仍可能插入一条新消息。正确做法是：

  1. 在数据库事务中检查输入版本号，仍一致才写入待发送记录。
  2. 发送器原子认领待发送记录。认领前可以因新消息作废；认领后承认网络发送已经开始。
  3. QQ 返回成功后记录消息编号和发送文本；返回失败则记录失败。
平台只能保证“发送器认领前已经过时的回复不会发出”，不能保证在任意纳秒到达的新消息都能撤回已经开始的网络请求。

“工具返回”和“现实是否为真”必须分开

内容平台能确认什么平台不能确认什么
天气接口返回“晴”接口确实返回了这段数据。室外现在一定晴。
定时工具返回任务 42数据库中已创建任务 42，时间字段是十点。未来进程和外部服务一定不会故障。
QQ 返回发送成功平台接受了消息并给出消息编号。用户一定已经阅读和理解。
读图模型返回“型号 AX6000”读图模型给出了这个识别结果。识别结果绝对正确。
长期记忆

一条摘要、最近原文、按需搜索

主模型和回复模型的历史不同，所以每个模型各保留一条累计摘要。原始事件不删除。摘要负责让重要关系和未完成事项一直在场；最近原文负责保留细节；搜索负责找回准确日期、原话、编号和旧工具结果。

凌晨五点做什么

  • 根据新消息更新长期备注。
  • 把较早的完整消息并入该模型的一条累计摘要。
  • 跳过正在活跃的会话，稍后重试。
  • 服务错过五点时，启动后补跑一次。

为什么不能只搜索

  • 模型可能不知道自己忘了某件事，因此不会主动搜索。
  • 摘要提供持续线索，搜索提供精确证据。
  • 用户提到“之前那个”但线索不足时，先搜索，再加载附近完整消息。

凌晨整理和请求超预算时使用同一段压缩代码：后端选择一段不切断工具调用的旧消息，模型只负责总结；摘要成功写入后才推进覆盖位置。两个压缩请求同时发生时，数据库条件更新只允许一个成功。失败时仍使用原始消息。

长期备注必须带适用范围和来源。群聊或订阅数据不能自动改写全局人格；所有者私聊可以提出全局备注，但固定平台规则和人格原稿仍由所有者明确修改。

扩展能力

插件、技能、同步器和独立任务各做一件事

方式适合做什么不应该做什么
Bash一次性计算、文件操作、调用现成命令。不负责长期连接、权限判断和可靠回调。
Skill一个 SKILL.md 说明某类任务如何完成，按需读取。不执行代码，不建立流程状态机。
插件可信的常驻 Python 代码：新工具、消息来源、读图服务、独立任务后端。不替换身份、会话顺序、权限、发送记录和定时器的基本规则。
同步器接收外部服务事件，发送远端命令，处理确认和结果。不理解论文、行情、日程等业务步骤。
独立任务 Agent用独立上下文完成长任务，只回传简短结果和产物。不把完整工作记录塞进主会话，也不靠退出码冒充完成报告。

最小插件实现

# plugins/example/plugin.py
PLUGIN_ID = "mutsumi.example"
PLUGIN_API = 1

async def setup(api, config):
    api.add_tool(...)
    api.add_message_source(...)
    return cleanup  # 服务退出时调用

配置文件显式列出启用的本地插件。加载时检查编号冲突；注册到一半失败就按相反顺序清理。第一版不做插件市场、自动下载、热更新、复杂依赖图或内建管理页面。DeepSeek Harness 值得借鉴的是“注册能力时同时得到清理办法”，不值得照搬“所有内核都可替换”。

同步器与设备节点

  • 中心服务分配会话顺序；设备节点不成为第二个主脑。
  • 外部来源用稳定事件编号重试，中心按来源编号去重。
  • 远端命令有命令编号、超时、确认和结果；接收方按命令编号避免重复执行。
  • 首版只承诺“至少投递一次并去重”，不宣称网络上的严格一次执行。
  • 独立任务只有调用受控回报工具才算完成；目标会话由平台绑定。
完整性判断

是否覆盖六个核心目标

目标判断关键条件
拟人化基本覆盖，需实验两个模型各自保留自身输出；主模型另外收到实际发送记录；人格效果做三组对照。
超长上下文一致性覆盖每个模型一条摘要 + 最近原文 + 历史搜索；原始事件不删。
角色边界一致性覆盖稳定编号和会话范围由后端决定；外部来源不能自称 system。
完备助手覆盖Bash、文件、Skill、插件工具、定时任务和独立任务。
通讯中枢还需补出站命令来源注册、持久待发送命令、确认与结果回流。
分布式设备单中心方案覆盖中心掌握顺序；节点重试和去重；暂不做多主。

不需要补充工作流语言、知识图谱、多主同步、插件市场或复杂界面。Bash 负责自由执行，Skill 负责方法说明，插件负责常驻能力，后端只守住身份、顺序、权限、持久化和真实操作结果。

测试

最先补什么测试

场景必须成立
主模型生成时来新消息关闭旧流；未完成内容不入历史；旧工具和旧回复均不执行。
回复模型生成时来新消息关闭回复流；不发送；回主模型重新思考。
模型完成与新消息同时发生固定新消息优先，测试不依赖随机 sleep。
新消息发生在发送认领前/后认领前旧回复作废；认领后如实记录已经开始发送。
写工具开始后进程崩溃记录结果未知，不自动重复写。
数据库已写消息但进程尚未唤醒重启后仍能从数据库继续处理。
主模型和回复模型历史各自 assistant 内容与自身实际输出完全一致；主模型通过单独平台记录知道发送文本。
图片自动描述不足主模型可按媒体编号让读图模型重新查看指定细节。
读图错误识别结果标明来自读图模型，不被当成确定现实。
凌晨整理与超预算同时发生只有一个摘要写入成功；覆盖范围不重叠、不漏消息。
用户纠正旧信息摘要与长期备注使用新值；旧原文仍可搜索，但不再当当前值。
插件加载到一半失败已注册能力全部清理，原工具列表不被污染。
外部服务重复上报/节点重复收命令相同事件或命令不会产生两次副作用。
角色隔离私聊 A、私聊 B 和群聊成员的摘要、备注、搜索结果不会串线。

行为实验至少比较三组：主模型直接回复；主模型 + 无历史回复模型；主模型 + 保留自身历史的回复模型。指标包括事实召回、人格一致性、跨角色泄露、错误承诺、旧回复/旧工具执行率、输入量和延迟。若第三组没有稳定收益，就选第二组。

最终设计

采用事件日志驱动的双模型流程：真人新消息可以关闭正在生成的主模型或回复模型请求；主模型负责思考和工具，回复模型只负责表达；两者各自忠实保留自己的 assistant 输出，平台用单独消息告诉主模型实际发送内容。每个模型使用自己的累计摘要和最近完整消息；原始事件始终可搜索。图片先由独立读图模型生成完整描述，并支持按媒体编号再次查看原图。Bash、Skill、插件、同步器和独立任务保持清晰分工，后端只负责身份、顺序、权限、持久化和真实操作结果。

本报告描述目标架构，不表示当前生产代码已经完成这些改动。外部论文和开源实现只提供方向性支持；双模型人格收益、即时打断和长期摘要稳定性仍需由本项目测试决定。
