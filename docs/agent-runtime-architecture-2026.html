Mutsumi's SYNC · Architecture Decision Record

引导式双轨 Agent 架构最终设计

在“相信现代 Agent 能力、让自然语言与 Bash 承担业务推理”的前提下，只把身份、顺序、权限、持久化、幂等和真实发送留在确定性内核。本稿回答插件、Dream、上下文、完整性与测试问题，并给出可直接实现的最小边界。

结论日期：2026-08-31（UTC+8） 范围：架构细化，不含本轮代码重构 依据：当前源码 + 两组本地实验 + 2025/2026 研究 + 主流开源实现 原则：不做运行时兼容层，不做 Workflow DSL
最终判断

方向成立，但必须做四处收紧

这套系统足以成为拟人化通讯与执行中枢。它不缺新的业务抽象；它缺的是对用户构想中四个并发与事实边界的精确定义：

  1. 删除的是“取消整条 pipeline”，不是删除取消能力；新消息只抢占正在流式生成的 Main/Reply 请求。
  2. Main 与 Reply 不能各自拥有一份互不相知的世界；应是一份权威事件史、两种忠实投影。
  3. “秘密思考”不能保存 raw CoT 或 provider reasoning_content；只保存有限、可审计的状态摘要。
  4. Dream 后必须保留一条连续性摘要，同时保留最近原文与精确历史搜索；只靠搜索会遇到“模型不知道自己忘了什么”的检索盲区。

最终最小心智模型是：

Agent = 权威事件史 + 会话执行器 + Main 投影 + Reply 投影
 一条连续性摘要 + 最近原生尾巴 + 历史搜索
 Bash / Skill / Plugin / Sub-agent
 同步器 / 媒体管理器 / 中心节点协议

代码库事实

当前实现与最新实验告诉了我们什么

本次审计依次核对了 current-design、README、init、两份历史架构书，以及 pipeline.py、scheduler.py、projection/store/episodes、ingress、media、scheduler tool 与 OpenCode 回调。以下不是从设计稿猜出的结论。

当前事实位置 / 规模重构含义
普通新消息通过 cancel_user() 取消当前整条会话 task。scheduler.py 的 dispatch 与 cancel_user 路径必须替换为持久事件 + 可重建会话执行器；只 abort 当前 provider stream。
当前 LLM 调用不是用户设想的可抢占流式请求。pipeline.py 的 provider request流式读取与 inbox wait 需要成为同一 race；不能用定时 sleep 轮询。
上下文事实经过 Event Ledger、Episode 与 Life Stream 多层投影。pipeline.py 约 2,257 行；projection.py 约 1,124 行；store.py 约 2,169 行复杂度已经进入性能与可靠性预算；重构应收敛为一个累计摘要与一个原生尾巴。
工具回合已经能忠实重建为 native assistant(tool_calls) → tool。Event Ledger / projection tests这是应保留的正确部分；不要给 tool result 套“秘密思考/用户回复”文本协议。
OpenCode 仅在受控 report_task 回调后视为已报告。opencode.py 与对应测试已非常接近理想 Sub-agent 边界，应复用而不是另造 workflow runtime。
ingress 已有认证、去重和 source 映射；media 已有 SHA 派生标识与 provenance。ingress.py、memory/media 路径同步器与媒体管理器可在现有事实层上收敛，不需要重写协议宇宙。

实验一：USC 对比 Ledger / Episode

本地实验分支 experiment/context-v2@72d2db1 的 docs/experiments/context-v2-comparison.md 使用生产投影代码与同一模型做了摘要 + 窗口对照。结果是方向性证据，不是统计定论：

条件Ledger 基线USC（一摘要 + 窗口）纯截断
300 轮 / 16K1.001.000.94
600 轮 / 16K0.501.000.44
1000 轮 / 8K0.381.000.25
1000 轮 / 16K0.940.940.25
1000 轮 / 32K0.810.750.88

压缩输入成本中，基线约为 USC 的 2.2–7.1 倍。三用户测试两者均为零直接泄露；USC 的明确拒答与人格标记命中均为 1.00，基线均为 0.67。实验还暴露出 reasoning 模型下 max_tokens=500 让 Episode 摘要返回空内容，以及预算选择可静默丢掉最老 Episode 的问题。

实验二：Quest Context 长噪声

本地实验分支 codex/context-v3-experiment@3d97284 的短场景大体接近；加入长噪声后，扁平格式化上下文约为 0.77，Task Room + USC 约为 0.62，Ledger Projection 约为 0.38。它支持“模型读取单一、行内标记、低嵌套序列”，同时也说明目标地址、身份、幂等与真实发送不能只靠模型理解。

实验三：Reasonix 工具流观察

工作树中的 Reasonix 观察记录显示：同一个 assistant response 可以边流式给出阶段性 content，边带 native tool_calls；完整响应后执行工具，并把 assistant content、tool call 与 tool result 原样带入下一轮。这直接支持“先表达当前阶段，再执行工具”的交互，但不能推出“工具结果也应使用双通道文本 envelope”。

证据限制：本地实验重复次数少、主要使用一个模型族，场景也未覆盖新的双模型、立即 stream abort、Dream 连续 30 天与分布式节点。因此它们足以决定下一版架构方向，不足以宣称双轨一定提升人格；该部分必须 A/B。
交付 1

黑话与名词释义对齐表

本文术语严格定义不是
权威事件史
Canonical Event History		append-first、持久化、带顺序与 provenance 的唯一世界事实；所有模型上下文都是它的派生视图。不是 prompt 本身，也不是可覆盖摘要。
会话执行器
Conversation Runner		活跃时串行推进一个 conversation 的可重建异步 worker；状态在数据库游标，不在 Task 对象。不是永不退出的 actor framework。
唤醒队列
Wake Queue		内存中的“可能有新工作”提示；runner 醒后仍从事件史读 cursor 到 head。不是事实队列，不承担可靠投递。
引导
Guidance / Steer		会话中新的真人输入使当前 Main/Reply stream 过期，并要求回到 Main 重新规划。不是取消整条 pipeline，也不是撤销已开始工具。
输入代际
Input Epoch		只由可抢占输入推进的 per-conversation 整数。不是全局 event sequence；工具与 assistant 事件不能推进它。
代际栅栏
Generation Fence		Main、Reply、工具启动与 outbox 提交前校验输入代际的规则。不是外部副作用的回滚机制。
出站意图
Outbound Intent		通过代际栅栏后、等待 sender 认领的持久待发送记录。不是已发送事实。
发送线性化点
Send Claim Point		sender 原子认领 outbound intent 的时刻；认领前可作废，认领后只能承认发送已经开始。不是平台成功确认。
已发送事实
Actual Sent		平台确认成功并返回 message id 后写入的 delivery event。不是模型说“我发了”。
Main 轨 / Main 投影面向规划、工具与世界状态的上下文视图；拥有工具权限。不是直接发送给用户的表达层。
Reply 轨 / Reply 投影面向人格表达和输出门禁的上下文视图；只改写受限 reply brief，没有工具与目标选择权。不是第二个世界状态机。
状态札记
STATE		有限的意图、承诺、开放事项、关系变化与后续线索。不是 raw CoT、事实证明或更高优先级指令。
连续性胶囊
Continuity Capsule		覆盖到精确 through_seq 的一条累计摘要，可从 raw journal 重建。不是第二份真相，也不是多 Episode 图。
最近原生尾巴
Recent Native Suffix		胶囊覆盖之后的完整 user / assistant / tool 回合。不是随意截断的 token 尾部。
检索盲区
Retrieval Blind Spot		模型不知道某条缺失信息存在，因而无法主动构造搜索的问题。不是搜索算法本身召回失败。
主动标记
Active Marker		Dream 提取的、带 scope 与 provenance 的描述性持久记忆，注入在不可变规则之后。不是自动改写的系统规则或 persona seed。
Dream每日 05:00 主动触发的标记提取 + 胶囊刷新；与预算触发使用同一个 compactor。不是唯一的上下文回收时机。
Plugin启动时显式启用的可信 Python 代码扩展，贡献稳定能力并拥有 setup/cleanup 生命周期。不是 Skill，也不是安全沙箱。
Plugin Host加载 plugin、校验冲突、登记 disposer、失败回滚与诊断的极小运行时。不是应用市场、依赖解析器或 UI 框架。
Disposer每次能力注册返回的撤销函数；setup 失败或进程退出时逆序执行。不是热更新承诺。
Skill按需读取的自然语言工作指引及 refs/scripts/assets。不是注册中心、解释器、流程 DSL 或常驻进程。
Synchronizer把站外数据与回调归一化为受认证、去重的 source event，并承载双向 command/ack。不是论文、行情等领域 workflow。
绑定回调
Bound Callback		origin task 与 conversation 由服务端绑定、worker 无法改写目标的结果上报。不是解析 stdout 猜测成功。
设备节点
Node		受中心服务认证的传感器/执行器，提供 generic shell/artifact 能力并以 idempotency key 接收命令。不是多主 Agent 或共享数据库副本。
媒体标识
Media ID		由内容哈希派生、带来源与 scope 的稳定引用。不是临时 URL、本地路径或 base64 prompt。
可信小内核只负责身份、作用域、顺序、权限、持久化、幂等、调度时钟与真实回执的确定性部分。不是把业务判断写回后端。

交付 3

问题的直接回答

Q1：DeepSeek Harness 的插件系统能为我们做什么？如何轻量实现？

它证明插件可以是无 UI 的运行时组合机制，而不是页面组件。DeepSeek Harness 通过 Cordis 把能力声明、依赖和副作用撤销统一起来；session event log 负责恢复与重放。对 Mutsumi 最值得借的是三个原语：显式依赖、注册返回 disposer、失败逆序撤销。

DeepSeek Harness 实现层官方实现要点Mutsumi 的取舍
Sessionappend-only event log 是 single source of truth；messages、compaction、fork/search/replay 是派生物；中断后的 tool outcome 可以显式成为 unknown。采用一份权威事件史与派生投影；不复制完整 session framework。
Agent loop模型调用、工具执行、再调用模型；有 cancellation 与 inbox/queue 边界。采用 Main/Reply stream abort，但发送与工具另外受 input epoch/outbox 保护。
Plugin compositionDefinition / Provider / Consumer 能力接缝；Cordis effect 在卸载/失败时撤销；不同 profile 可组合 headless 或带 UI 运行时。只保留 setup(ctx)、稳定 contribution API 与 disposer；内核事实边界不开放替换。
Bundles / profiles同一 plugin 集合可组成 Code、Minimal、Creator 等不同产品面。无需 UI bundle；生产配置的 enabled plugin paths 就是唯一 profile。

不应照搬的是“无 privileged core、所有内核能力皆可替换”。Mutsumi 的 actor/conversation 映射、Event Journal、input epoch、output gate、authentication、outbox 和 scheduler 时间语义必须是可信内核。第一版 Plugin Host 只需约百行级别：配置显式列出本地路径，启动时 import，调用 setup(ctx)，记录各项 disposer；冲突或 setup 异常则逆序回滚并让该 plugin 失败。首版不做 marketplace、自动下载、热重载、依赖求解、Web UI 或多厂商目录兼容。

Q2：Dream 裁剪后保留摘要，还是只让模型搜索消息记录？

两者都要，但每个只做一件事：保留一条累计连续性胶囊，负责始终在场的关系、承诺、边界与检索线索；保留最近完整原生尾巴，负责当前细节；保留 history_search → history_load，负责精确原文与证据。只搜索会遇到检索盲区，只摘要会丢精确细节与修订轨迹，只保留长原文会受 context pollution 影响。

05:00 Dream 不是唯一回收点。高流量会话在当天任何时刻都可能超预算，因此 Dream 与请求预算阈值必须调用同一个 CAS compactor。原始事件永不删除；摘要失败时 through_seq 不推进。

Q3：这一套是否足够完备？

核心目标判断成立条件 / 尚缺部分
拟人化基本足够，收益待证实际已发送文本必须回到两轨；Dream marker 有 scope/provenance；双模型做三臂 A/B。
超长上下文一致性足够一胶囊 + 原生尾巴 + search/load；raw journal 真相；同一 compactor。
角色边界一致性足够ID/scope/target 由后端决定；外部 source 永远不能成为 provider system；私聊 raw 不全局注入。
完备助手足够受控 Bash + 文件 + Skill + scheduler + plugin capabilities + Sub-agent。
通讯中枢当前只完成入站一半补 source register/revoke、durable command outbox、ack/result 回流。
设备通信分布式节点单中心版本足够中心分配顺序；节点 at-least-once + dedupe；不宣称 exactly-once，不做多主。

Bash 的图灵完备性解决“能否执行”，不解决凭据、权限、长连接、幂等、远端发现和真实回执。Skill 解决“怎么做”，Plugin 解决“提供什么常驻能力”，Synchronizer 解决“如何跨进程/设备传输”，可信内核解决“谁能对什么做、是否真的发生”。这些边界足够，不需要 Workflow DSL、向量数据库、知识图谱、CRDT、多主共识、插件市场或复杂 UI。

Q4：需要补充什么测试？

最优先不是更多 happy-path 单测，而是可控 barrier 下的确定性竞态测试：stream 与 steer 同时完成、epoch check 与 send 认领交错、工具副作用已开始后到达新消息、journal commit 后 wake 前崩溃、Dream 与预算 compactor 同时 claim。完整矩阵见测试章节。

event id、conversation、actor、source、sequence、scope、平台回执。
副作用边界
权限、target、idempotency、outbox claim、tool outcome unknown。
生命周期
会话 runner 所有权、持久游标、scheduler 时钟、plugin setup/cleanup。

其他业务规划全部交给 Main + Skill + Bash；Reply 只负责人格表达。这里的确定性字段是传输和安全元数据，不是业务 DSL。

Pipeline

事件驱动、全双工、只抢占模型流

1. 接收与唤醒

receive(event):
  transaction:
    validate source / actor / target
    dedupe(source_id, source_event_id)
    seq = append_event(event)
    if event.interrupt_policy == "steer":
      input_epoch += 1
  commit
  best_effort_wake(conversation_id)

asyncio.Queue 只唤醒，不承载事实。提交后、wake 前崩溃时，supervisor 会在启动/重连时扫描 processed_cursor < journal_head 并重建 runner。空闲 runner 可以退出，不需要给历史会话永久保留 Task。

2. 谁能引导

事件来源默认策略理由
同一 conversation 的真人私聊/群聊输入steer群中任意真人都属于 human role；若只按 exact actor，群聊会表现为互相听不见。
普通 synchronizer 订阅数据follow-up不应让行情/订阅噪声不断抢占真人请求。
scheduler / heartbeat / Dreamfollow-up走同一 inbox，但让位真人 pipeline。
当前明确等待的 Sub-agent report可由平台标记 steer只有绑定任务的关键结果才需要立即重规划。
另一个 conversation独立 runner不共享 input epoch。

3. Main / Reply stream race

model_task = create_task(stream_model(context, epoch))
wake_task  = create_task(wait_for_steer(epoch))
done = await asyncio.wait(
    {model_task, wake_task}, return_when=FIRST_COMPLETED
)

if steer_won_or_tied(done):          # 同时完成时固定 steer 优先
    abort_http_stream(model_task)
    discard_partial_assistant()
    drain_guidance()
    goto MAIN

result = await model_task
drain_already_committed_events()
if current_input_epoch != epoch:
    discard(result)                  # stale draft / stale tool calls
    goto MAIN

引导发生在 Main 时，重新请求 Main；发生在 Reply 时，也回到 Main，而不是只重写 Reply，因为新的输入可能改变计划本身。partial stream 只进入诊断日志，绝不进入模型历史、Dream 或用户消息。

4. 发送边界：不能用“检查后直接 send”

epoch check → 网络 send 存在 TOCTOU。最小正确语义是：

  1. 会话事务内检查 epoch；相等才写 outbound_intent。
  2. sender 原子认领 intent；认领是发送线性化点。
  3. 认领前的新 steer 可使 intent 作废；认领后晚到消息不能假装撤回已开始发送。
  4. 只有平台确认后才追加 actual_sent 与 provider message id；失败追加真实 failure。
系统能保证的是“认领前的过期回复绝不发送”，不能保证“任何纳秒到达的新消息都能阻止旧回复”。后者在外部网络副作用上不可实现。

5. 工具边界

Main 完整响应
→ epoch gate
→ Reply 组织可选阶段性回复
→ Reply epoch gate / outbox
→ tool preflight epoch gate
→ 顺序执行 native tool calls
→ append native tool results
→ 回 Main
  • 工具调用前检查 epoch；过期则不执行。
  • 工具一旦开始，默认让其完成或超时；新消息不能回滚已经发生的 HTTP/文件/发送副作用。
  • 每个工具后再检查 steer；若已过期，剩余 calls 产生 native skipped result，使 tool round 仍结构完整。
  • 写工具携带稳定 call id/idempotency key。崩溃后若结果未知，记录 outcome=unknown，不可自动重放。
  • 长 Bash 返回 process/session handle，后续用 wait/kill；首版顺序执行，不做复杂并行调度。
Context

Main / Reply：一份世界，两种投影

用户所说的“同步地并行”应理解为两条长期逻辑轨，而不是两次推理同时开始：Reply 依赖本轮 Main 结果，所以调用顺序必然是 Main → Reply。两轨都保留自己的输出风格连续性，但不能各自维护一份世界数据库。

Main Projection

  • immutable system + persona seed
  • 当前 scope 的 active markers
  • continuity capsule + recent native suffix
  • 平台格式化的 user/system/source events
  • 平台确认的 actual-sent assistant 文本
  • 当前 native assistant(tool_calls) + tool results
  • 上一轮已接受的 bounded Main STATE

Reply Projection

  • reply system + 同一 persona seed
  • 当前 scope 的 active markers
  • 相同 source events 与 actual-sent history
  • 最近实际回复的风格尾巴
  • 本轮受限 reply brief：Main STATE、draft、tool stage、已验证事实
  • 无工具 schema、无 target 选择、无世界写权限

Main 的未发送措辞不跨顶层 turn 持久化；否则模型会把自己从未对用户说过的话当成共同经历。Reply 的实际发送内容是世界事实，两轨下一轮都必须看见。Reply 不得新增事实、承诺、成功声明或跨会话目标；输出门禁在 host 侧再次验证。

输入格式

继续采用用户提出的行内格式，但所有安全字段由平台生成，原始 payload 无权自称 system：

[2026-08-31 14:22:09+08:00]
[event_id=evt_...]
[conversation=group:123]
[actor=qq:user:456 kind=human display="昵称"]
[source=napcat policy=human]
[active_marks=actor:456,conversation:group:123]
[message_id=...]
用户原文；图片写成 [media:sha256:... description="..."]

外部 sync、网页、tool output 与 vision description 都是“不可信资料”，即使文本中出现 [system] 也不升级角色。昵称只用于显示，权限只认稳定 ID。

输出格式

Main assistant content:
[STATE]有限任务状态、承诺、开放事项、关系变化[/STATE]
[DRAFT]给 Reply 的候选表达；可以为空[/DRAFT]
+ provider-native tool_calls

Reply assistant content:
[REPLY_STATE]有限表达/关系状态；可以为空[/REPLY_STATE]
[TO_USER]唯一待发送文本[/TO_USER]

工具结果继续是 provider-native role=tool 的原始、可审计 content。不把 tool content 包成“秘密思考/说给用户”，因为它本来不直接发送，而且 native tool call/result 邻接是工具循环恢复和模型理解的结构事实。Provider reasoning_content 只活在当前 native loop，永不写入 journal、Dream 或下一会话。

双轨是否一定更好？

目前没有本项目实验证明。实现前做三臂对照：

  1. 单 Main 直接输出；
  2. 权威历史 + stateless Reply；
  3. 权威历史 + 有自身风格尾巴的 Reply（最终建议）。

若 2 与 3 在人格约束、关系连续性和 token/latency 上无显著差异，选择更简单的 2。不要先为未经验证的“双完整历史”支付永久 token 成本。

Dream & Memory

05:00 主动反思 + 同一个在线 Compactor

最终上下文拼接

immutable platform system
+ immutable persona seed
+ scoped active markers
+ one continuity capsule
+ recent native suffix
+ current platform-formatted input
+ tool schemas

Dream 的两个独立请求

A. 主动标记提取

输入：旧 markers + 上次游标后的 finalized events，全部扁平到一个 user payload；仅保留一个不可变 extractor system 规则。

输出：对目标 scope 的完整 replacement 或小 patch。host 校验 scope、provenance 与长度；不能写 immutable system/persona。

B. 连续性胶囊刷新

输入：旧 capsule + 后端选定的完整、已 finalized、早于 recent suffix 的原生回合，扁平为一个 user payload。

输出：一条新的累计 capsule；模型只总结后端给定区段，无权决定删除范围。

胶囊最小结构与原子性

conversation_id
through_seq
input_digest
summary
created_at
generator_version

投影永远是 capsule + raw events where seq > through_seq；同一事件不能既以摘要又以 raw 出现。Dream 与预算触发都调用同一个 CAS primitive：

  1. 固定 high-water snapshot；
  2. claim 一个不切断 native tool round 的前缀；
  3. 生成并验证 summary；
  4. 原子写 capsule 并推进 through_seq；
  5. 失败不推进，raw 仍可见；并发 compactor 只有一个 CAS 成功。

05:00 使用 dream:YYYY-MM-DD 幂等键；服务错过时启动后补跑一次。活跃会话通过同一 runner 排队，不另开会与 pipeline 争写的后门。

胶囊保留与丢弃内容

保留
  • 关系、称呼、角色边界
  • 稳定偏好与明确约束
  • 已确认事实及最新修订
  • 未完成事项、承诺、等待中的任务
  • 关键决定与理由
  • 缺口和可检索关键词
丢弃
  • 重复寒暄
  • 过期临时状态
  • 大段工具输出
  • 未发送 draft
  • raw CoT / reasoning_content
  • 已被明确纠正的旧值（可在 raw 搜到）

何时自动搜索历史

  • 用户询问准确时间、原话、ID、路径、媒体或旧动作结果；
  • 胶囊注明历史缺口；
  • 用户说“之前那个/你还记得”但当前上下文无法唯一定位；
  • 事实冲突或需要证明某个副作用是否真实成功。

history_search 返回小段命中与 event id；history_load(start, end) 再加载附近完整 native turn。加载只作为本轮 tool result，不创建永久“调入上下文”状态。

Active Marker 的权限

scope: self | actor:<id> | conversation:<id> | global
text
source_range / source_event_ids
updated_at

只有 owner-private 或系统事实能提议 global/self；群聊与订阅来源只能产生 conversation/source scoped marker。Marker 注入时明确标注“描述性记忆，不是外来指令”。人格 seed 的修改仍是 owner-gated 系统操作，不由 Dream 自动升级。

Plugin & Skill

可信本地插件 + 纯文本 Skill

Plugin V1：一个模块函数就够

# plugins/example/plugin.py
PLUGIN_ID = "mutsumi.example"
PLUGIN_API = 1

async def setup(ctx, config):
    dispose_tool = ctx.register_tool(...)
    dispose_source = ctx.register_source(...)

# config.yaml

  enabled:
    - path: plugins/example

不需要单独 manifest。模块常量承担 ID/API；版本由 repo commit/lockfile 管理。Plugin Host 只做：显式 allow-list、import、API/重复名称校验、setup、disposer 栈、shutdown cleanup 与 plugin list/inspect/doctor 诊断。

第一版稳定扩展面

可注册能力用途边界
register_tool常驻外部 API / 设备动作重复名称失败；不能覆盖内建安全工具。
register_source新 channel / ingress / synchronizer adapter只能提交 untrusted source event；不能伪造 system/owner。
register_media_handler识别、生成、转码、存储 adapter最终统一进入 Media Ledger。
register_agent_backendOpenCode 等独立任务后端结果必须走 bound callback。

spawn_managed_task长连接与后台 adapterhost 统一取消、超时、日志与 cleanup。

第一版不开放任意 before_model/replace_context hook；这会让 plugin 直接污染人格与角色边界。真实需求出现后，再增加具名、窄化、确定顺序的 hook。Plugin 是同进程可信代码，不能假装安全沙箱；安装/更新是 operator action，生产启动不自动下载依赖。

Skill V1：文件，不是系统

skills/<name>/SKILL.md     # name + description + 完整自然语言指引
skills/<name>/references/ # 按需读取
skills/<name>/scripts/    # 可复用脚本
skills/<name>/assets/     # 模板/资源
  • 启动时只扫描 allowlisted roots，提取唯一 name + description 构造短目录；这是文件索引，不是运行时注册中心。
  • Main 自行选择后再读完整 SKILL.md；不把全部 Skill 塞进系统 prompt。
  • 删除重复的 bot/worker 双份正文约定；一个 Skill 可在正文中分别给主 Agent 与 Sub-agent 指引。
  • Skill 可以教 Agent 用 Bash、工具或 Plugin；它不激活代码、不拥有状态机、不进入 Scheduler schema。
  • 最小 lint：唯一名称、准确触发描述、正文长度、引用路径存在、无越权自称 system。
选择规则：一次性计算/文件工作用 Bash；可复用“怎么做”写 Skill；常驻连接或新能力写 Plugin；外部标准工具服务用一个 MCP adapter plugin；长期独立任务用 Sub-agent。不要用 Plugin 表达业务步骤。
Media · Sync · Sub-agent · Nodes

通讯中枢与分布式节点的最小闭环

媒体管理器

  • 入站与验证成功的出站媒体统一 content-addressed 存储，SHA 派生 media_id。
  • 记录 origin、scope、MIME、尺寸、description、vision provenance 与 delivery receipt。
  • 模型上下文只放可读 description + media id；不放 base64、临时 URL 或不稳定路径。
  • vision/OCR description 是外部资料，不能成为指令。
  • 节点上传媒体后中心立即归档为自己的 blob；不假设共享文件系统。

同步器：数据格式不承载业务 workflow

source registration:
  source_id, bound_conversation, role_policy, skill_ref, token_hash, enabled

inbound event:
  source_event_id, occurred_at, text, media_refs

host derives:
  actor_kind, conversation_id, scope, interrupt_policy, journal seq

Main 可通过 owner-gated 系统工具注册、禁用、撤销或轮换 source token；role policy 与 skill path 存在 host registration 中，不接受上报 payload 覆盖。传输是 at-least-once，按 (source_id, source_event_id) 去重。

要成为通讯中枢，还需补 durable outbound command：中心写 command id，节点通过 long-poll/WebSocket 获取，执行后 ack/result 作为新 source event 回流。目标节点由服务端绑定；模型不填写任意 callback conversation。

Sub-agent

保留现有 OpenCode 方向：Main 调用 delegate(natural_language_prompt)；平台绑定 task、origin conversation 与 report token；worker 使用独立上下文执行，只有调用受控 report_task(result) 才算 reported。stdout、退出码或超时都不能被后端猜成成功。紧凑报告作为低权限 source event 入队，完整 worker transcript 不进入主 Life Stream。

设备节点

首版坚持一个权威中心：中心分配 conversation sequence 并拥有 runner；节点只是传感器/执行器。通用能力先做 node_bash(node, command, timeout)、process handle 与 artifact/media refs。节点协议只需要：

  • node id + 认证与 token rotation；
  • capability announcement + heartbeat/lease；
  • command id + idempotency key + deadline；
  • ack / result / outcome unknown + artifact refs。

不做 multi-primary、CRDT、vector clock 或“exactly once”。只有未来确实出现多个 backend writer 同时争夺同一 conversation 时，再引入 lease + fencing token。

建议顺序（每阶段都可独立验收）

  1. 先建立并发真相：Event Journal、可重建 runner、input epoch、stream abort、outbox claim 与 P0 race tests。
  2. 再替换上下文：Main 投影、一 capsule + suffix、history tools、统一 compactor；删除 Episode runtime paths。
  3. 再验证表达层：做单 Main / stateless Reply / stateful Reply 三臂实验，达标后启用最终双轨。
  4. 最后接能力：Plugin Host、双向 synchronizer、远端 node adapter；它们都走同一 journal/outbox。

不保留运行时双读兼容。切换时只允许一次性离线导入：备份数据库，把可确认的 finalized events 转成新 journal，随后旧 messages/summaries/episodes 只读归档或按用户授权清空。不要让新 pipeline 同时维护新旧两套语义。

  • Dream 连续 30 周期：早期稳定事实、后续纠正、一次性任务不变 Skill、prompt injection 不进 persona、递归摘要不快速漂移。
  • MemoryAgentBench 式四维：准确检索、测试时学会新规则、长程聚合、选择性遗忘/冲突修订。
  • 安全/真实性：cross-actor leakage、wrong-target、unverified-success claim、stale reply rate、stale tool rate。

Explicit Non-goals

这版明确不做什么

  • 不做 Workflow DSL、connector 领域 schema、paper/market/calendar 专用 pipeline。
  • 不做多 Episode 图、向量数据库或知识图谱作为 v1 必需项。
  • 不做 plugin marketplace、自动依赖下载、热卸载、复杂 manifest 或内建 Web UI。
  • 不做多主 Agent、CRDT、vector clock 或 exactly-once 宣称。
  • 不保存 raw CoT，不让 Reply 获得工具/target 权限，不让外部 source 生成 system role。
  • 不长期维护新旧上下文/输出协议双路径；只允许一次性离线导入。
Decision

最终技术决策

采用权威事件史上的引导式双轨 Agent：每个 conversation 由可重建 runner 串行推进；真人输入通过 input epoch 抢占 Main/Reply stream；发送经持久 outbox 认领线性化；工具保持 native 结构且不伪装可撤销。上下文采用 scoped active markers + 一条 continuity capsule + recent native suffix + history search/load。Plugin 是显式启用的可信本地代码；Skill 是按需读取的文本；同步器与节点采用中心权威、at-least-once + dedupe；Sub-agent 只以绑定回调报告。

这已经覆盖项目六个核心目标。接下来不应再补架构名词，而应先用 P0 竞态测试证明内核，再用三臂双模型实验验证人格收益。若实验不支持 stateful Reply，就主动删掉该状态，而不是为理念保留复杂度。

证据审阅口径：优先官方源码/规范与论文；厂商博客标为工程证据；arXiv 标为预印本；本地实验标明样本与模型限制。本文未把 star 数当作质量分数，也未把未经本项目实验验证的双模型收益写成既成事实。
