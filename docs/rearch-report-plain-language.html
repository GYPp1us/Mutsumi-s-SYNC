Mutsumi's SYNC 重构报告

大白话版：把「事件队列 + 引导 + 双模型」这套想法讲清楚，附上我查到的资料和我的反对意见。2026-08-31。

0. 先说结论

你这套想法整体成立，我认为要做到的话有四处要改：

  1. 工具调用的结果，不要套「内部思考 / 说给用户」的格式。工具结果就是工具结果，原样放回对话里就行。下面第 2 节讲原因。
  2. 不要每条消息前面都贴一份「角色说明」。整套对话只有开头一份固定的系统说明，再加上每人身份写在消息前面一行就够了。下面第 5 节讲原因。
  3. 主模型和回复模型是先后干活，不是同时干活。回复模型得等主模型这轮想完、决定要做什么，才能组织措辞。两条轨各自记住「自己说出去的话」，但共用同一份事实记录。
  4. 回复模型的上下文不会比主模型多，反而更少。它不用背工具清单和工具结果（那是最占地方的部分）。你原稿里说「回复模型占用一定比主模型多」，我觉得反了。

其余的都是细化，下面按你原来的章节顺序讲。

1. 整体思路

一句话：所有发生过的事都记录在案（一条只能追加、不能改的流水账），每次干活只对着一份「从上一条记录读到现在」的拼装结果；谁先到谁先处理，新来的真人消息可以打断正在输出的模型回答，但不能取消已经开工的工具。

系统的骨头：

一条流水账（所有消息、工具调用、发送结果都记在这）
一个会话一个活（一个会话同时只有一个任务在跑，任务可随时重建）
两种看法：主模型（负责想和干） / 回复模型（负责怎么说话）
整理：一条长期摘要 + 最近原始对话 + 查历史工具
干活的：bash / 技能文件 / 插件 / 子任务
对外：同步器 / 媒体管理 / 设备节点

2. 处理流程：事件队列 + 引导

你说的「删掉 pipeline 打断、改成事件队列 + 引导对话」，我完全同意。具体规则如下：

2.1 新消息来了怎么办

  • 消息先写入流水账（先存下来，再谈处理，防丢）。
  • 然后给这个会话递一个「提醒」（就是个门铃，不是数据本身；数据永远以流水账为准）。
  • 会话的活儿被叫醒，从流水账里读「上次处理到哪 → 现在到哪」，接着干。
  • 如果正在等模型输出：真人新消息会打断当前这次模型请求，已输出的半截全部丢掉，重新拼上下文、重新想。
  • 如果工具已经开工：不打断，让当前工具继续跑完；还没开始的工具本轮取消，并如实告诉模型「这几个没做」。
  • 如果正好模型回答和新消息同时完成：固定让新消息赢，避免时灵时不灵。

一个细节：怎么判断「我手里的结果是不是过期的」？给每个会话记一个轮次号：每来一条真人消息，号 +1。模型请求发出时记下当时的号，结果回来后比对，号变了就说明有更新的事，这轮结果作废。工具和模型自己产出的东西不推进这个号，否则会把自己刚干的事误判成过期。

2.2 谁有资格打断

消息来源能不能打断说明
同一会话里的真人（私聊 / 群聊）能群里任何真人都算，否则群里的人会互相「听不见」
同步器推来的普通数据不能行情、订阅之类不该抢真人说话的位子
定时任务 / 心跳 / 凌晨整理不能排队等，真人的事优先
子任务回报（平台标注过重要的）可以标记为能只有关键结果才需要马上重新想
另一个会话的消息各自独立不影响本会话的号

2.3 发送这条线（最容易出错的地方）

「检查完轮次号没错 → 发出去」中间有个空隙：检查完、要发的时候来了新消息，怎么办？

正确做法是分四步，中间有个「待发送清单」：

  1. 会话交易里检查轮次号；没错，就把这条消息写进「待发送清单」。
  2. 发送器来领走清单里这条消息，领走的那一刻就算数。
  3. 领走之前来了新消息，清单里这条可以作废；领走之后才来的消息，不能假装撤回已经发出去的话。
  4. 只有平台确认「发出成功」了，才在流水账里记一条「已发送」；失败了就记真实失败。
能保证的是「还没被领走、已经过期的回复，绝对不发」。不能保证「任何一瞬间到的新消息都能拦住旧回复」——对网络和外部设备来说这事物理上做不到。

3. 凌晨整理（dream）

凌晨 5 点做两件事，两个是独立的两次请求：

3.1 提取长期记忆

  • 把旧记忆条 + 上次整理以来发生的事，全部平铺成一段文字塞给它（不带角色头、不带工具、不带格式包袱），让模型回忆反思。
  • 模型交回「该记住什么」，但这只是建议：系统要检查范围、来源和长度，才允许写进去。
  • 记忆条有四个范围：自己 / 某个特定的人 / 某个会话 / 全局。群聊和订阅来源只能提「会话级」的记忆，不能提「全局」的。
  • 人格的那份种子说明，不允许被凌晨整理自动改写——那是主人的权限。

3.2 刷新长期摘要

  • 把旧的长期摘要 + 系统挑好的、完整的、还没被最近原文覆盖的对话，平铺成一段，让模型重写成新摘要。
  • 模型只总结系统给它的区段，无权自己决定删哪段。

3.3 关于「摘要还是搜索」——两个都要，各干一件事

留什么管什么
一条长期摘要关系、称呼、角色边界、稳定偏好、已确认的事实（含最新修正）、没做完的事、重要的决定、以及「去哪能查到细节」的线索。随时在场。
最近一段原始对话摘要之后发生的完整问答，原样保留，保证细节不丢。
查历史工具精确内容：原话、时间、编号、路径、图片、某件事到底成没成。按需查，查完只当这一轮的资料，不常驻。

为什么不能只留搜索：模型不知道它忘了什么，就不会去问。我们自己的实验里，历史被悄悄丢掉且没提示时，早期事实 100% 丢失；而「不知道丢了什么」这种盲区，搜索是治不了的。反过来只留摘要也不行：精确原文和「当时说的是哪个版本」会丢。所以三样一起留。

顺带两点修正：

  • 凌晨 5 点不是唯一整理时机。聊天多的会话白天也可能超预算，平时发现太长了就用同一套整理程序，规则一样：先记下「进展到哪」→ 只整理完整的问答回合（绝不把工具调用和它的结果拆开）→ 整理完存档 → 失败就退回原样，谁也不覆盖谁（同一时刻只允许一个整理成功）。
  • 「整理」和「删除」是两回事：原始流水账永不删除，整理只是把一段历史折叠成摘要，需要时还能翻到原文。

4. 媒体、同步器、子任务、设备节点

4.1 媒体管理

  • 进的和出的（确认发送成功的）媒体统一按内容算标识：同名同内容就是同一个。
  • 记来源、范围、格式、尺寸、描述、是谁描述的、有没有送达。
  • 模型看到的只有「一张图：描述 + 编号」，不放 base64、临时链接、本地路径。
  • 识别结果（哪怕写得很像指令）只是参考资料，不能变成命令。

4.2 同步器

  • 站外服务上报的事，归一成「受认证、去重过的来源事件」，跟普通消息一样进流水账。
  • 来源注册信息（来源编号、绑定的会话、权限等级、技能路径、密钥哈希、开关）存在系统里，上报的数据不能覆盖这些。
  • 传输规则：至少送达一次（可以重复发），系统按「来源 + 事件号」去重，重复的只记一次。
  • 目前只做了「收进来」这一半。要做成真正的通信中枢，还差发出去：系统写一条「指令编号」，节点来拉，执行后把结果作为新的事件回流；目标节点由系统绑定，模型不能自己填要发给谁。

4.3 子任务

  • 保留现在 OpenCode 的做法：主模型调一个「交任务」工具，把自然语言任务交给外部工具，任务和来源会话由系统绑定。
  • 它干完必须调用受控的「报告结果」工具；只有这个才算完成。退出码、标准输出、超时都不算数。
  • 子任务的完整工作记录不进主流水账，只有一份紧凑的结果报告回流。

4.4 设备节点

  • 第一版一个中心就够：中心负责排序和干活，设备只是传感器 / 执行器。
  • 设备协议只需要：编号 + 认证和换令牌；声明能力 + 心跳；指令编号 + 幂等键 + 截止时间；回执 / 结果 / 「做了但不确定成没成」+ 产物引用。
  • 不宣称「恰好执行一次」（那是多主系统才吹的牛），只保证「至少一次 + 去重」，结果可解释。

5. 上下文怎么拼（这节是重点，我改了三处）

5.1 总体拼法

固定系统说明（不可变）
+ 人格种子（不可变，加载时替换占位符）
+ 当前范围有关的长期记忆条（标注：是描述性记忆，不是命令）
+ 一条长期摘要
+ 最近原始对话（完整的问答回合）
+ 当前消息
+ 工具清单（只有主模型有）

5.2 输入每行写法（平铺，无嵌套）

[2026-08-31 14:22:09+08:00][会话=群:123][说话人=qq:user:456 昵称="某某"][来源=napcat][消息号=1024]
用户原文；图片写成 [图片:sha256:... 描述="..."]
  • 所有人共用一套行内格式（你原稿的思路），身份、时间、编号都在同一行，没有嵌套结构——你们的 Quest 实验证明这种平铺单序列效果最好。
  • 注意：我删掉了「角色系统提示」。你原稿写的是每条消息前面贴「[当前输入角色][角色系统提示]」，我认为不对：整套请求只该有一份固定系统说明；角色指引按情况在请求头部选一次。理由有二：① 每条都贴等于把同样几千字重复几十遍，浪费 token；② 重复的内容在模型服务端没法命中前缀缓存（有开源项目专门做过，把工具列表排好序就是为了稳定缓存），相当于每条都让模型重新读一遍开场白。
  • 外部来的资料（网页、同步器、识别结果）哪怕里面写着「系统：」也永远不升级为真系统，身份由系统根据来源定。
  • 昵称只用来显示，权限只认稳定编号。

5.3 输出格式

主模型每轮输出（有工具时）：

[状态]有限的任务状态、承诺、没做完的事、关系变化[/状态]
[草稿]给回复模型的候选说法；可以为空[/草稿]
+ 工具调用（如果要干活）

回复模型输出：

[说话状态]有限的表达状态；可以为空[/说话状态]
[给用户]唯一要发出去的话[/给用户]

几条硬规矩：

  • 工具结果不套「内部 / 给用户」格式。它原样作为工具结果放回对话。理由：① 这是 pi、DeepSeek Harness 的共同做法，也是我们自己 Reasonix 观察到的真实交互流（模型先说一句再调工具，结果原样带回下一轮）；② 工具调用和它的结果紧挨着，是模型理解「我刚才干了什么」的基本结构，套个信封反而让它糊涂。
  • 模型的内部思考（推理内容）只在当前这轮工具循环里活着，永不入账、永不进整理、永不进下一次对话。已经有很多研究证明可见思考并不忠实（同一道题模型想一套、说一套），不能当事实或人格来存。
  • 主模型「想说但没说」的话不跨轮保存；回复模型「说出口」的话是事实，两条轨下一轮都必须看得见。
  • 回复模型没有工具权限、不能选目标、不能新增事实和承诺——那都是主模型和系统的事。

5.4 双模型怎么组织（对应你原稿的注意段）

你原稿说两条轨是「同步地并行」，我的理解是：逻辑上是两条长期轨，物理上是先后顺序——回复模型依赖这一轮主模型的决定，所以必然先问主模型、再用主模型的结论去组织语言。硬要同时跑，回复模型连「现在进行到哪了」都不知道。

两条轨各带什么：

主模型回复模型
任务想、决定、调用工具把结论说成人话
工具清单有无
工具结果有（当前轮）无
历史系统说明 + 记忆 + 摘要 + 原始对话 + 已发送的事实 + 自己的状态块回复说明 + 同一个人格 + 已发送的历史 + 最近自己说过的风格尾巴 + 这轮的受限简报（主模型的状态、草稿、已验证的事实、门禁规则）
权限工具、发送特殊消息无工具、无目标选择、只负责措辞

所以回复模型的上下文比主模型小（不背工具），而且两条轨各有自己稳定不变的「前半段」，可以在服务端分别连续命中缓存。

最后一句话诚实声明：双模型值不值，现在没有数据。实现前做三组对照：① 只用主模型直接说；② 主模型 + 不带历史的回复模型；③ 主模型 + 带自己说话历史的回复模型。量「像不像」、「关系连不连贯」、「有没有瞎承诺」、「花了多少 token」。②和③没差别的话就选简单的②，别为没验证的想法长期多付钱。

6. 插件和技能

6.1 插件（DeepSeek Harness 的做法能借鉴什么）

我读了 DeepSeek Harness 的本地安装包，它插件系统的实质是：配置文件按顺序叠几层补丁；每个插件往容器里登记工具、提示词、消息来源；每次登记都返回一个「撤销动作」；登记分全局和单会话；谁出错就把之前登记的按逆序撤掉。它还有依赖图、动态加载、浏览器半边、插件市场——这些都不要。

我们能学的就四条：登记的时候能给撤销动作、失败按逆序撤、登记分范围、能力重复时直接报错。

最简实现（约一百来行）：

# plugins/example/plugin.py
PLUGIN_ID = "mutsumi.example"
PLUGIN_API = 1

async def setup(ctx, config):
    undo_tool = ctx.加工具(Tool(...))        # 返回撤销动作
    undo_source = ctx.加消息来源(adapter)     # 只能提交未认证的数据，不能冒充系统
    return undo_清理                        # 可选；加载器仍会逆序调用所有登记
# config.yaml
plugins:
  enabled:
    - path: plugins/example
      config: {}

加载器只干这些事：按配置挑文件 → 导入 → 校验版本号和重名（重名直接失败，禁止覆盖系统的安全工具）→ 调 setup → 收集撤销动作 → 任何一步出错就把已登记的逆序撤掉 → 关停时逆序清理 → 提供「看插件、查插件」的诊断工具。

第一版开放六种能力：加工具（常驻外部接口 / 设备动作）、加消息来源（新通道）、加媒体处理（识别 / 生成 / 转换）、加任务后端（子任务，结果必须走绑定回调）、加技能目录（随插件发文字说明）、开户后台任务（长连接适配器）。不开放「改写模型提示词」的钩子——那会让插件直接污染人格和角色边界。真需要了再加具名、限范围、定顺序的钩子。

第一版明确不做：插件市场、自动装依赖、热卸载、网页界面。插件是可信代码，不是沙箱，装插件是主人的决定。

6.2 技能（Skill）

  • 技能 = 按需读取的文本文件（说明 + 参考资料 + 脚本 + 素材），没有注册中心、解释器、状态机。
  • 启动时只扫一遍目录，建一个「名字 + 一句话说明」的清单；主模型选完了再读全文。清单是文件索引，不是运行时系统。
  • 现在的「主 Agent 说明 / 干活 Agent 说明」两份正文约定删掉，一个技能文件里分两段给两方讲。
  • 技能可以教模型用 bash、工具或插件；它自己不激活代码、不占状态、不进定时任务的数据结构。
  • 简单检查：名字唯一、说明准确、正文不长、引用的路径存在、没有越权自称系统。

选择规则：一次性计算 / 文件活 → bash；可复用的「怎么做」→ 技能文件；常驻连接或新能力 → 插件；外部标准工具服务 → 一个 MCP 转接插件；长期独立任务 → 子任务。别用插件写业务步骤。

7. 工具清单（只留强原语）

类别工具系统负责
系统改配置 / 重启、长期记忆条维护、注册同步来源只有主人能用、格式检查、持久化、重启恢复
角色给某个编号或群添加 / 删除昵称、关系标签维护稳定编号、范围、昵称不参与权限判断
工作读技能、沙箱文件增删改、bash、等 / 停、定时任务目录 / 网络权限、超时、进程句柄；定时任务仍是「时间 + 一句话」
记忆查历史、按区间调入历史范围过滤、区间合法、按完整原生回合返回
通信特殊发送、节点命令、交任务目标绑定、幂等、回执、回调来源

不加论文、行情、日历专用字段。领域步骤写进技能，组合方式让模型自己定，后端只管通用的传输和安全约定。

8. 四个问题的回答（汇总）

问题一：DeepSeek Harness 的插件系统能为我们做什么？怎么轻量实现？

它证明插件可以是没有界面的后台零件（不是页面组件），它真正的价值是四样小东西：登记时给撤销动作、失败按逆序撤、登记分范围、能力重名报错。其余（依赖图、配置树、动态装卸、浏览器半边、市场）都不需要。

轻量实现就是上面 6.1 那一百来行：配置文件列本地路径 → 启动加载 → 调一个 setup → 收集撤销动作 → 出错逆序回滚 → 提供诊断工具。首版不做市场、自动装依赖、热卸载、网页界面；不开放「改写提示词」。

对「即使有 UI 也是外挂的极简后端」：插件系统正好符合——它完全不要求 UI，TUI 或将来的网页界面只是从同一份事实层读数据的旁观者。

问题二：整理之后保留摘要，还是只让模型遇到盲区时搜索？

两个都要，各干一件事。摘要负责「始终在场的」：关系、边界、承诺、重要的已确认事实和它的最新版本、没做完的事、去哪查细节。原始尾巴负责最近细节。搜索负责精确原文和「到底成没成」的证据。只搜索治不了「不知道忘了什么」；只摘要丢精确内容和修订过程；只留原文被长上下文污染拖累。

另外：凌晨 5 点不是唯一时机；整理和预算触发的整理用同一套程序；摘要失败就退回原样；原文永不删除。

问题三：这套系统够不够完备？

目标判断说明
拟人化基本够，收益待验证修复「想说的 vs 说出口的」不一致；双模型要做对照实验，不值得就不上。
超长对话一致性够摘要 + 原文尾巴 + 查历史；原文为真相；同一套整理。
角色边界一致性够身份、范围、目标由系统定；外部数据永不能自称系统；私聊原文不进全局。
完备助手够bash + 文件 + 技能 + 定时 + 插件 + 子任务。不做零碎的业务流程。
通信中枢只完成入站补「指令队列 + 回执回流」才完整。
设备分布式节点单中心够中心分配顺序；节点至少一次 + 去重；不吹「恰好一次」。

关于「bash 足够」：bash 解决能不能做，不解决谁有资格做、到底做了没、做到一半怎么办。后四件事归系统：身份、范围、权限、幂等、真实回执。Bash 干活的自由度 + 这套小内核管边界，就够了。

问题四：需要补什么测试？

最优先是「撞车测试」，用可控制的方式制造冲突（假的模型流、假的发送器、假的工具，不许用随机等待碰运气）：

场景断言
主模型输出到一半来真人消息停了；半截不保存；重新想时包含两条输入；旧工具和旧发送为 0
回复模型输出到一半来真人消息停了；没往待发送清单写东西；回主模型重新想
模型回答和新消息同时到固定新消息赢，没有时灵时不灵
轮次号工具 / 模型自己的产出不推进号，不把自己的结果误判为过期
发送三时刻检查后、写入清单前、领走后分别来新消息：前两种旧话不发，后一种如实已发；只有平台确认才记「已发送」
存完就崩重启后消息照常处理；提醒队列不是数据，丢了只慢不丢事
干活中途崩任务重建，处理进度不越过未处理的事
工具开工前来消息 / 工具干一半来消息前者不执行、如实写「没做」；后者当前工具最多做一次、剩余工具跳过、不谎称撤销
写操作做了但结果未知就崩记「做了没确认」；同号不自动重放
凌晨整理和预算整理撞车只一个成功；无重叠、无重复、无缺口
摘要覆盖范围摘要到第 N 条，原文尾巴第一条严格 >N；不切断工具轮
插件装到一半出错已登记的全部逆序撤销，系统保持原样
重复子任务回报 / 假令牌幂等；拒绝伪造；只唤醒原会话
来源伪装数据自称系统 / 主人 / 目标：被系统字段覆盖，权限不提升

然后是行为与长期实验：重复跑之前的两个长对话实验（加「重启后接上」的用例，至少两个模型）；双模型三组对照；凌晨整理连续 30 天（早期稳定事实、后来修正、注入攻击不进人格、反复摘要不漂移）；记忆四维：找得准、当场学新规矩、长程总结、选择性遗忘（用户纠正旧事实后失效）。

落地顺序（每步都能单独验收）：

  1. 先把「撞车」做对：轮次号、打断模型流、待发送清单、任务守卫，配上上面的 P0 测试。
  2. 再换上下文拼法：平铺行内 + 长期记忆条 + 一条摘要 + 原文尾巴 + 查历史工具。
  3. 再验证表达层：三组双模型对照，达标才启用。
  4. 最后接能力：插件加载器、双向同步器、设备节点适配器，都走同一套账本和清单。

不做运行时双轨兼容：切换时一次性离线迁移（备份 → 把可确认的事实转成新账本 → 旧表只读归档或按授权清空）。
