1. 系统全景

整个系统是一个单一进程的 asyncio 应用：NapCat（QQ 客户端网关）通过 WebSocket 推送消息， MessageReceiver 接收入站，PipelineScheduler 为每个会话维护一个可取消的 pipeline 任务，pipeline() 单函数完成"持久化入站 → 拼上下文 → LLM 工具循环 → 信封解析 → 发送"的完整回合。 所有事实以全局 Event Ledger 为唯一持久事实源，其余表均为投影、缓存或审计。

三个关键不变量

不变量含义
Append-firstevents 表只能追加；普通轮次结束后状态从 received 更新为终态（finalized / cancelled 等），身份与 sequence 不变。
单函数 pipeline所有回合逻辑集中在 pipeline() 一个异步函数中（铁律 1），通过 PipelineDeps 注入全部依赖，函数内部不持有跨回合状态。
新消息取消旧任务同一会话 key 的新输入到达时，Scheduler 用 asyncio.Task.cancel() 取消旧 pipeline 并等待其 cleanup（入站消息已先行持久化，不会消失）。

图片消息的额外路径

图片消息（MessageType.IMAGE）在 pipeline() 内先持久化入站，然后： 下载图片到 Media Ledger（成功 → SHA 派生 media_id；失败 → 保留外部 URL 引用）→ 若配置了 vision provider 则生成文字描述（openai-compatible 或 volcengine-ocr）→ 构造一条合成 user 输入（caption + 描述 + media 引用）→ 进入普通 LLM 流程。 CQ 元数据、临时 URL 和本地路径不进入模型上下文。

外部服务消息的额外路径

ServiceIngress 接收 NapCat 形状的 POST /v1/events（loopback + Bearer token）， 以 uuid5(service_id + message_id) 去重，先持久化为 received 事件再 ACK（HTTP 202）。 每个 service:<id> 拥有独立 FIFO worker 队列，不适用普通同 key 取消规则； 回复通过配置的 ingress.target_user_id（QQ 所有者）发送。重启时从 Ledger 恢复未完成事件。

3.3 投影与上下文

Life Stream生命流（模型面对的历史时间线）
由 build_life_stream() 把 Ledger 投影为 provider 原生消息序列：真人/服务入站为 user （带可读来源前缀），bot 出站为 assistant，完成的工具回合重建为 assistant(tool_calls) + tool。 Episode 在其覆盖区间内替代原始事件。它是"全局账本的受众视图"：只投影当前会话 + 标记 global 的事件。 这是设计中"多个对话窗口共享人格、但私聊互不可见"的实现载体。
src/mutsumi_sync/memory/projection.py:702-1124
Projection（投影）从事实源到模型输入的派生视图
设计术语：任何"从 raw facts 派生、供特定消费方使用"的视图都叫投影。本项目中投影有： Life Stream（模型输入）、Episode（历史恢复单元）、Action Ledger（审计）、TUI 状态（调试）。 文档反复强调"投影不得伪装成完整覆盖"——分页上限外的更早历史必须注入 omission 标记。
src/mutsumi_sync/memory/projection.py（全文件）

每条事件携带 visibility（private/group/global）与 audience（目标会话或 bot:self）。 event_is_context_visible(event, audience_conversation_id) 是模型输入的最小边界： 私聊会话只能看到自己的事件 + 标 global 的事件；群会话共享边界，所有成员可见该群事件。 隐私过滤（Alice 的私聊事实不会进入 Bob 的上下文）是当前设计中少有的、被真实模型实验验证过的行为。

4. 上下文四层结构（Provider 请求布局）

每个 LLM 请求严格按以下顺序组装（_build_context()），这是本项目最核心的设计名词之一： "稳定 system → 历史 Life Stream → 临时平台状态 → 当前来源消息"。

L1 · System Message（稳定系统消息）role: system
provider 原生中文 system 消息 = 平台稳定规则（runtime prompt）+ 人格设定（persona prompt）+ 心跳时追加 Heartbeat Mode Override。两者都来自外部文件 system-prompts.yaml （prompts.system_file），加载时一次性完成身份占位符替换（{{user}} 等）， 不存进 config.yaml；config_manager reload 可热重载。运行时以工具 schema 为准， 提示词不维护工具清单。请求中唯一不被预算回收的固定层。
L2 · Life Stream（历史生命流）role: user / assistant / tool 混合
受众过滤后的全局账本投影（§3.3）：Episode 摘要与原始事件互斥出现；工具回合重建为原生 assistant(tool_calls)+tool；真人/服务入站带可读来源前缀（如 私聊「123456789」｜前辈（qq:user:123456789）｜2026-08-03 20:00:00）。 有遗漏时头部带 omission 标记。这一层同时承担"多窗口人格一致"（bot 自己的 outbound 全局可见于自身上下文） 与"私聊互不可见"（audience 过滤）。
L3 · Platform State（临时平台状态）role: user
当前 UTC+8 时间、会话地址（= 规范化 send target）、来源标记（心跳/定时/任务回报）、 Active Work、Inner Journal（主观历史声明）、Self Note（长期记录）。永不持久化； 与 L4 分离，防止平台信息被模型当成用户话语。
L4 · Current Source Message（当前来源消息）role: user
本轮真实输入：普通用户消息（带来源前缀）、心跳合成输入、定时任务 prompt、OpenCode 报告， 或图片消息的合成输入（caption + vision 描述 + media 引用）。L3/L4 永远保留在请求中， 预算回收只作用于 L2。

6. 生命周期状态机

回合状态（pipeline 返回值 / messages 表 status）

状态含义事件侧
received已持久化、处理中入站事件初始态
responded可见回复已发送成功inbound → finalized，追加 outbound
no_reply故意静默（no_reply 工具）inbound → no_reply
empty模型返回空内容inbound → empty
cancelled被新消息/关闭取消inbound → cancelled（不消失，record 保留）
error异常/预算失败inbound → error，未回复时发送"模型暂时不可用"

事件状态（events 表 status）

入站事件经历 received → finalized / no_reply / empty / cancelled / error； 暂存工具结果行先 pending，cleanup 提交后 finalized。 NON_PROJECTABLE_EVENT_STATUSES = {cancelled, error, no_reply, empty} 不进入模型投影。

定时任务状态

pending → running（claim）→ done / error；paused / cancelled 为人工终态。 运行中被用户输入取消 → defer 1 秒后重试；重启还原 running → pending。

委派任务状态

pending → running → reported → delivered；失败路径 unreported / timeout / cancelled / failed。 重启时未回报的 running/pending 一律诚实标记 unreported（绝不伪造完成）。

7. 子系统速览

Heartbeat（心跳）

每 15 分钟扫私聊、每 3 小时扫群（活跃窗口 24h）。真实 LLM 调用，remember_input=False， 可持久化验证过的主动输出；等待用户回复时抑制再发；有用户 pipeline 时整批让路。允许工具仅 {sticker_search, media_search, send}。

Episode 压缩

选择"从当前前沿开始的连续 finalized 群组"（每回合 ≥1 完整逻辑组），max 160 事件； 输入超预算显式分块 + 合并轮；失败保持原始事件可用且不推进边界。 区间写入用 BEGIN IMMEDIATE + 会话锁防重。

Scheduler（定时）

持久化一次性/间隔/五字段 UTC+8 cron；到期经 _wait_for_conversation_slot 在用户管道之后排队；错过槽跳过不补发；pause/resume/cancel 全生命周期管理。 设计红线：任务记录不含 skill_name/target_group/业务步骤字段。

OpenCode 委派

可选。每次运行独立目录 + 独立 XDG/DB；report_task 插件经原子 link 落盘 （token 校验）；平台轮询接受 → 更新任务行 → 唤醒原会话（重试 3 次、指数退避）。 stdout/退出码仅诊断，不替代回报。

Ingress（服务入口）

标准库 asyncio HTTP/1.1：loopback 强制、Bearer 恒定时间比较、正文限长、仅文本/HTTP(S) 图片段、 uuid5 去重、202 先落库后应答、FIFO worker、重启恢复、优雅取消还原 received。

Media / Vision / Markdown 渲染

入站图片 SHA 登记（下载失败保留外部引用）；vision 支持 openai-compatible 与 volcengine-ocr（HMAC-SHA256 签名表单）；Markdown → PNG 经 Node+Playwright（60s 超时）， 发送成功先登记后删临时文件。

日志与可观测性

标准 mutsumi.* logger 树，双写：append-only NDJSON（logging.stream_store） 与 human-readable 轮转文本（logging.text_file）。 pipeline 关键分支（INIT/MEDIA/CTX_build/LOOP/Exec_Tools/DONE/CANCELLED）经 _report_state 上报 TUI。Dashboard TUI 为调试界面（不保证与生产 registry 一致）。

步骤规则
1. 信封解析parse_final_envelope(content, strict=False)：无任何标记 → 恢复为 空 TO_SELF + 全文 TO_USER；带标记畸形 → 抛错进入重写。
2. TO_SELF 限长> max_entry_chars=1000 → 重写（"只保留新的内在状态增量"）。
3. 输出门禁TO_USER 含标题/表格/代码围栏/链接图片/LaTeX → 拒发 + 重写（可引导 send(markdown_image)）。
4. 发送扁平纯文本经 sender.send 一次发出；成功 → responded + outbound 事件；失败 → error + 动作账本记录。
5. 重写耗尽发送 extract_unambiguous_to_user() 提取的完整 TO_USER 块，或"这次回复格式连续校验失败了，请稍后再试。"——绝不静默丢回合、绝不抢救 TO_SELF。
6. 附加规则管道符 | 为字面量不切分；中间轮 content 永不发送/解析；reasoning_content 仅当前循环内保留；被门禁拒绝的回复不入 outbound、TO_SELF 不可提交。

9. 与设计文档的已知差异（实现事实）

以下为审阅时发现的"文档宣称 ≠ 代码行为"，供后续设计决策参考（不在此文档中裁决对错）。

1. messages 表仍在每回合写入 AGENTS.md 与 docs/current-design.md §5 宣称"一旦会话有 Ledger 行，legacy messages/summaries 为只读兼容数据， 普通 cleanup 不得写入"。实现中 _save_inbound_msg/_update_saved_msg 无条件写 messages 表 （pipeline.py:665, 692），仅 summaries 写入被跳过。双写是事实。
2. memory_search 与 Ledger/Episode 断层 检索仅覆盖 messages 表 FTS；Episode 叙述与工具调用不可检索（store.py:1652）。设计宣称的"长期记忆主干"未贯通。
3. 超限请求仍会被发出 docs §5 称"live pipeline 在每次 provider 调用前做最终硬检查并诚实失败"。 实现中 _build_context 超限只打 error 日志并继续返回消息（pipeline.py:426-431）， 真正的硬失败推迟到工具循环内 _ensure_live_request_budget（ContextBudgetError → 用户收到内部错误文案）。
4. Action Ledger 静默截断 _sanitize_action_result 把结果截断到 2000 字符（无标记）；file_edit 错误截断 400； 审计数据被静默裁剪，与"真实结果入账"主张打折。
5. 死代码仍在 canonical_state 表 + 6 个 store 方法、tools/bot_state.py、 tools/priority_override.py（均未注册）、_recycle_window_if_needed、 MessageWindow.max_size（无效参数，测试专门断言其无效）。
6. 双套压缩机制并存 _build_context 内嵌 _reclaim_ledger_history 与回合级 _compact_context_for_request 做同一件事（大历史请求跑两遍全量投影）； legacy 窗口压缩路径（_window_turn_groups 等）对现行数据不可达。
7. schema 唯一事实源被特判削弱 pipeline 对 send/status_update/no_reply/memory_save/self_note/file_edit 有硬编码名称分支与内联逻辑，provider schema 并非事实上的唯一事实源。
8. 其余一致性良好 隐私边界（audience 过滤）、Episode 精确覆盖、暂存写入原子性、跨会话 send 溯源分组、 服务 FIFO、心跳让路、OpenCode 诚实回报——均有测试覆盖且与文档一致。
