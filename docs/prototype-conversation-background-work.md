# 聊天与后台工作原型

> **设计已暂停沿用：** 固定时间等待短句与固定返回会话不能满足新的目标。这个原型保留为实验记录，不代表下一版方案；后续讨论见[后续暂定方案](agent-orchestration-options-2026-09-08.md)。下面仍如实说明它目前的行为。

这个原型把“眼前怎么回应用户”和“把复杂任务做完”放进两个独立的异步处理过程。后台读文件、等待模型时，聊天仍可继续；程序另行计时，必要时发送预先配置的等待短句。聊天模型可以返回零条、一条或多条消息。

它是[技术路线报告](conversation-and-background-work-2026-09-08.md)的一次可运行实验，入口是 `python -m src.mutsumi_sync.prototype`。目前只处理文本，所有回复显示在本地终端。它复用现有 SQLite 事件存储、工具注册表和输出检查，但使用独立数据库与调度器；生产 QQ 入口和原有 `pipeline()` 的行为保持现状。

## 先运行离线演示

在仓库根目录使用已经安装 `requirements.txt` 的 Python 环境。Windows 可以先激活现有虚拟环境：

```powershell
.\.venv\Scripts\Activate.ps1
python -m src.mutsumi_sync.prototype --demo
```

省略 `--demo` 也是相同的离线演示，不需要模型密钥或 NapCat。演示中的“模型”按脚本返回固定结果，后台 `read_file` 则会真实读取本仓库的 `README.md`。

一次演示依次展示：

1. 接收后台任务，读取项目说明，然后人为暂停后台返回。
2. 后台暂停期间继续闲聊。
3. 返回空消息列表，确认没有发送。
4. 返回两条消息，正文中的 `a | b` 保持原样。
5. 人为卡住一次聊天请求，观察程序独立发送等待短句，再重新生成回复。
6. 释放后台等待，把完成报告交给聊天过程组织台词。

终端中的 `[收件人 #编号]` 是本地发送记录。成功回执表示 `ConsoleSender` 接受并显示了消息，不代表 QQ 送达。

## 自己输入消息

```powershell
python -m src.mutsumi_sync.prototype --interactive
```

此模式仍然离线。可以连续输入，观察新消息与后台任务如何交错：

| 输入 | 假模型的演示行为 |
| --- | --- |
| `/work` | 建立读取 `README.md` 的后台任务。 |
| 普通文字 | 生成一条固定闲聊回复。 |
| `/update 只要简短结论` | 为当前任务追加要求。 |
| `/status` | 查询任务状态。 |
| `/cancel` | 请求停止当前任务尚未开始的动作。 |
| `/silent` | 返回合法空消息列表。 |
| `/multi` | 返回两条独立消息。 |
| `/slow` | 首次使用时模拟聊天模型等待，便于观察等待提示。 |
| `/quit` | 退出交互。 |

这些斜线输入是演示脚本的触发条件，不能用来证明真实模型理解了用户意图。真实模型模式中，只有 `/quit` 由交互程序直接处理；其余文字交给模型理解。

## 使用真实模型，回复仍留在终端

准备本地 `config.yaml`，填写 `model` 和 `identity`，并让 `prompts.system_file` 指向包含本原型提示字段的文件：

```powershell
python -m src.mutsumi_sync.prototype --live-model --config config.yaml --db data/prototype-live/prototype.sqlite3
```

`--live-model` 会进入交互。可以输入“读一下 README.md，告诉我这个项目主要做什么”，然后在后台处理时继续闲聊、追加要求或要求停止。此模式会向配置的模型 API 发送对话与所读取的文件内容，并产生正常的 API 用量。

首版沿用同一组 `model.base_url`、`model.model` 和密钥，分别发起聊天与后台请求，没有增加两套模型配置。接口采用 `/chat/completions`：

| 请求 | 原型发送的配置 |
| --- | --- |
| 聊天 | `thinking: {type: disabled}`，`max_tokens: 1024`。 |
| 后台 | `thinking: {type: enabled}`，`max_tokens: 8192`，使用原有 `reasoning_effort`。 |

配置的 provider 目前只接受 `deepseek` 或 `openai-compatible`。这里的“compatible”不表示兼容所有服务：实际端点还必须支持上述 `thinking` 参数、原生工具调用，以及返回的消息结构。接口拒绝参数会按模型请求失败处理，不会自动换一套请求方式。关闭长思考是否生效、真实回复速度和角色表现都需要在所选模型上测量。

## 常用参数与文件

```powershell
python -m src.mutsumi_sync.prototype --interactive --root . --db data/prototype/session.sqlite3 --wait-seconds 3 --chat-timeout 8
```

| 参数 | 默认值与含义 |
| --- | --- |
| `--config` | `config.example.yaml`；离线模式也读取身份与提示词。 |
| `--db` | `data/prototype/prototype.sqlite3`；只使用原型专用数据库。 |
| `--root` | `.`；后台文件工具的读取根目录。 |
| `--wait-seconds` | `3`；仍无有效回复或静默决定时，尝试发送等待提示。 |
| `--chat-timeout` | `8`；本次聊天处理的总时间预算，必须大于等待阈值。 |

数据库同目录的 `logs/prototype.ndjson` 保存结构化日志，`logs/prototype.log` 保存文字日志；日志是否启用沿用所选配置。`events` 保存原始输入、实际发送结果和工具记录，`prototype_jobs` 保存后台任务及交付状态。切换一个新的 `--db` 路径即可开始独立实验，不必清理原来的数据。请勿把 `--db` 指向生产数据库。

首次使用的数据库会绑定所选 `--root` 和离线／真实模型模式。换项目根目录或切换模式时，要使用新的数据库路径，避免旧任务读到另一个项目或由假模型接手真实任务。非原型的非空数据库，以及已有任务但缺少这份绑定信息的旧实验库，都会被拒绝；上面的真实模型命令因此明确使用另一份数据库。

提示词集中在所选 `system-prompts.yaml`，不写在 Python 中：

| 字段 | 用途 |
| --- | --- |
| `persona` | 聊天角色设定，继续使用原有身份占位符替换。 |
| `prototype_chat` | 聊天、任务交接与消息列表规则。 |
| `prototype_worker` | 后台任务与结果报告规则。 |
| `prototype_wait` | 程序使用的固定等待短句。 |
| `prototype_error` | 聊天失败时使用的短句。 |

四个 `prototype_*` 字段必须存在且非空。自定义旧提示文件需要补齐这些字段；程序不会悄悄回退到生产聊天协议。已有技术路线 HTML 和 Markdown 保留为设计记录，本页描述原型的实际使用范围。

## 程序怎样处理一次对话

```text
用户输入 → 先存事件 → 聊天请求 → 检查消息列表 → 逐条发送
                         ↓
                     保存后台任务
                         ↓
                  思考、只读文件工具
                         ↓
                    保存完成报告 → 再次唤醒聊天

用户输入 → 独立计时 → 仍需等待时尝试发送固定短句
```

聊天每次最多管理一次后台任务，再进入最终回复。同一会话的后台任务顺序执行；新消息可以先进入聊天，程序在下一次后台工具开始前检查是否需要补充或停止。已经开始的动作保留实际结果，不能把“请求停止”理解为撤销既有操作。

收到新输入后，后台尚未开始的动作先暂停，等待聊天处理这次输入。若聊天生成或发送失败，这些动作继续暂停，直到下一次有效聊天处理完成；发送成功的等待提示或失败短句本身不会解除暂停。

后台仅注册两个真实工具：`list_files` 列出目录，`read_file` 读取 UTF-8 文本。读取限制在 `--root` 内；隐藏路径、`config.yaml`、`data`、`node_modules` 等被排除，路径跳转不能越过根目录。单次读取最多 20,000 字符，单次目录列表最多 200 项，截断会在工具结果中说明。没有执行命令、修改文件或直接发消息的后台工具。

任务保存原始输入与来源引用。等待提示导致重新生成或进程重启时，相同会话与同一组原始输入事件引用避免重复建立后台任务；这只是任务创建去重，不保证所有外部操作恰好执行一次。重启后，尚未开始的任务可继续；中断时正在运行的任务标记为 `unknown`，保留尚未确认的工具信息，不自动重做。已经完成但尚未交付的报告仍会保留。

后台工具调用时的 `content` 不发送。后台完成报告也不直接作为台词发送，而是交回聊天模型结合当前场景表达。`reasoning_content` 只在正在运行的后台工具对话中临时保留，不写入持久聊天历史。

每次由后台结果唤醒聊天时，只处理一个任务的交付。这轮未被新输入替代、消息列表非空且每条都确认发送成功，程序就把该任务记为 `delivered`；返回 `[]` 则暂缓交付。这个标记只依据发送结果，程序不判断台词是否真正覆盖了任务结论，内容是否完整仍需检查。

## 静默、多条和等待的边界

聊天最终输出仍有两个区块，但本原型将 `TO_USER` 改为消息列表：

```text
[TO_SELF]留意后台结果。[/TO_SELF]
[TO_USER]{"messages":["嗯，我看看。","你也可以接着说。"]}[/TO_USER]
```

`{"messages":[]}` 表示这次保持静默。每项对应一条消息，最多四条，每条最多 500 字符；不通过分隔符拆句。空白项、额外字段、重复 JSON 键、协议标签泄露、复杂 Markdown 和不完整输出都会被拒绝，修正次数有限，失败不会伪装成主动静默。

等待提示与正式台词使用同一个发送入口。正式回复已经开始，或者模型已经返回合法静默结果，本轮就不再补等待提示。若等待提示先发送成功，后续聊天会看到这条实际发送记录再继续。已经发出的提示不能被晚到的静默决定撤回。

`3 秒`和`8 秒`是当前默认配置，控制程序的计时与取消决定，并不是实际送达保证。事件循环调度、存储、正在进行的发送和外部服务都会影响时间。验证时要分别观察首次发送尝试、首次成功回执，以及第一条包含实际内容的回复，不能只用等待短句判断用户等了多久。

## 已验证的程序行为与仍需实测的部分

离线演示和自动测试适合检查并发顺序、消息列表、持久化、取消边界与发送结果。这些可控输入不能证明真实模型会及时交接任务、总能理解静默要求、自然分条，或稳定保持角色。验证角色效果需要运行真实模型，对复杂请求、闲聊、工具失败、用户改口等场景逐条查看台词。

当前原型未接入 QQ 收发、图片或富文本交付、生产工具全集、生产原有 `pipeline()`、全局历史投影和长期摘要压缩。聊天使用本会话近期事件与任务状态，适合短期实验，不能据此评价长期记忆效果；也没有替代生产服务或部署流程。

从仓库根目录运行测试：

```powershell
python -m pytest tests/ -q
```

实现入口位于 [__main__.py](../src/mutsumi_sync/prototype/__main__.py)，调度与两个处理过程位于 [runtime.py](../src/mutsumi_sync/prototype/runtime.py)，接口与文件工具位于 [adapters.py](../src/mutsumi_sync/prototype/adapters.py)，消息检查与持久任务分别位于 [protocol.py](../src/mutsumi_sync/prototype/protocol.py) 和 [storage.py](../src/mutsumi_sync/prototype/storage.py)。
