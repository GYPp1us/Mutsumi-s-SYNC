# Rust 原型验证记录

日期：2026-10-18，UTC+8。

## 验证范围

- Windows 本机，Rust/Cargo 1.95.0，锁定 Cargo.lock。
- 使用用户已配置的 DeepSeek 专用 API key，仅通过子进程环境注入；调用 `https://api.deepseek.com` 的 `deepseek-flash`。
- 输入全为合成内容，发送器为终端。没有部署服务或发送真实 QQ 消息。

## 真实模型结果

四个场景全部完成：

| 场景 | 主模型轮数 | 终端消息 | 工具成功 | 结果 |
| --- | --- | --- | --- | --- |
| 简短问候 | 1 | 1 | 0 | 成功 |
| 工具轮 content 先回复，再查询时钟并给结果 | 2 | 2 | 1 | 成功；同轮消息先于工具动作 |
| 明确指定 `project_group` | 1 | 1 | 0 | 成功；目标回执核对为指定测试窗口 |
| 从持久化投影续接先前时钟回执 | 1 | 1 | 0 | 成功；没有重复查询 |

第一次完整运行总耗时 19.25 秒，各场景约 2.8–8.5 秒，包含独立审查与网络请求。这是少量功能验证，不是性能、角色质量或安全性评测；Jev 尚未启用，不能将这些数字解释为快速回复性能。

第二次完整复跑时，四个场景也全部完成；历史续接发生一次审查拒绝，模型收到必要原因后自行修正，最终没有再次查询工具。这说明纠正链路可用，也说明少量成功样例不能证明审查器没有误拒绝。

随后用另一种 CLI 提法发现模型把工具调用写进 content 的情况。严格解析正确拒绝，三轮内没有执行副作用；补充 system 中 API 字段位置说明，并反馈具体解析错误后，用同一提法回归成功：2 个主模型回合、2 条终端消息、1 次真实时钟工具执行。没有增加对 content 内伪工具调用的兼容解析。

## 离线与静态验证

运行命令：`cargo test --locked --all-targets`、`cargo clippy --locked --all-targets -- -D warnings`、`cargo fmt --all -- --check`。16 项离线测试全部通过，Clippy（warnings 视为错误）与格式检查通过，CLI 构建成功。离线测试覆盖内容解析、动作门禁、回执持久化、取消和恢复；真实网络测试默认保持忽略，避免普通测试意外花费额度。

V3 归档中的 134 个项目文件继续与冻结前哈希一致；原型没有修改归档实现或恢复 HZ 旧服务。
