## 1. 先看结论

当前仓库不是缺少一个更复杂的工作流，而是同时留下了几代设计记录和几种实验实现。最新方向已经明确：

1. 模型保留完整的行动编排能力。它可以自己决定回复、静默、等待、向哪个人或群发送、是否 @ 某人、是否转发到私聊、是否调用设备或临时组织其他智能体。程序不为每种排列预先写一条业务流程。
2. 即将发生的输出和工具动作由独立审查模型检查。审查覆盖普通发送、目标和发送身份、重定向、bash、子代理启动以及这些动作带来的后续工具调用。审查指出依据和分歧，让行动模型继续查证或改主意，不把审查者变成另一套固定流程。
3. 为解决复杂请求迟迟没有第一句话的问题，原任务继续交给可深入思考的模型；同时把当前请求改写成“此刻根据已有信息，可以自然表达什么打算”的短问题，交给关闭思考的模型。它可以说“我想想”“我找一下”“我试试”“稍等，我去群里问问”，也可以直接回答或保持沉默。短句不是固定 ACK，也不代替完整解题。
4. 已经实际发出的意图进入后续行动的共同事实：记录原话、说话角色、听众、关联用户要求和发送结果。执行模型在下一次真实动作前看到这条事实，可以承接、修正或因用户改口而放弃；“说过要做”不等于“已经做完”。
5. 消息目标选择必须分开判断“谁在发言、谁应看到、通过哪个会话或设备送达、转述谁的哪句话”。模型从真实对象资料中选择对象，不能自己编写或猜地址；独立审查模型在不知道主模型选择的情况下重新解析一次。无法区分且会改变动作时，才询问用户。这个过程优先保证任务完备性，准确率用于发现和压低幻觉，不用规则把模型关进有限流程。

上一版“固定几秒发送等待短句”和“结果固定回到发起会话”的假设已经撤回。原型代码和说明仍可作为对照，但不能再被当作当前架构继续扩展。双模型是否能解决问题也不能靠文档断言，必须通过下面的成对实验验证。

### 4.3 旧上下文实验的可复用结论

- 长噪声历史中，简单的单窗口加格式化角色头表现好于复杂的多层投影；

因此这些结果作为背景输入新实验，不作为新编排方案的验收证据。

## 6. 当前设计需要怎样修改运行时

这部分是给下一位实现 agent 的顺序建议，不是本次清理已经完成的代码变更。

### 6.1 先建立“意图事实”，不要建立业务工作流

快速模型的输出不能直接成为发送动作，也不能只留在日志里。建议在现有事件/动作账本旁增加一条很小的事实记录，至少包含：

- `intent_id`、产生时间、关联的用户输入事件和当前 `pipeline_id`；
- 角色身份、当前会话、可见范围、实际听众；
- 对外原话和快速模型选择的消息列表；
- 独立审查的结论、依据版本和审查时间；
- 发送尝试的结果：确认成功、确认失败或结果不明；
- 它表达的是打算、正在进行还是已经确认完成。后两者不能由模型的措辞猜出来，必须有实际动作结果。

生命周期应是：草稿 → 审查 → 发送尝试 → 真实回执 → 可供后续模型读取的共同事实。发送失败的草稿不进入对外历史；结果不明时记录“不确定”，不要自动换目标重发。这个记录只是让参与者看到同一段真实往来，不是一个包含所有业务分支的状态机。

### 6.2 快速意图调用

在同一条用户输入进入 pipeline 后，启动两个可取消的模型请求：

1. 深入模型：保留全部工具、上下文和思考预算，负责完整任务和后续编排；
2. 快速模型：使用关闭思考的模型和改写后的短请求，看到人设、当前说话者、必要历史、用户原话以及已经发生的进展，只决定“现在有没有一句有依据的自然表达”。

快速模型不读或不写完整任务的秘密推理，不得直接调用工具。它可以返回一条或多条普通消息，也可以返回空列表。输出审查只检查事实、对象、场景和角色，不要求它先解决整道题。深度模型的最终回复已经准备好时，未发送的快速草稿应取消。

### 6.3 后续行动如何读到意图

任何实际动作（最终发送、重定向、bash、子代理、设备操作）开始前，执行侧重新读取从上一次判断到此刻新增的：

- 已确认发送的快速意图原话及其听众；
- 用户新消息或改口；
- 其他模型/子代理已经完成的真实动作及结果；
- 目标对象、会话和设备目录是否发生变化。

旧的动作提议如果没有考虑这些新增事实，不能直接执行。执行侧不必从头重做整个问题，只需对当前一步重新判断。审查模型也看同一批新增事实。这样可以覆盖“快速模型先说、深度模型先准备、用户中途改口、发送结果晚到、群消息后来触发私聊回忆”等先后关系。

### 6.4 目标选择和目标解析

现有 `Peer` 只描述当前 pipeline 的一个私聊或群聊；要支持“把答案发某个群里，然后 @ 某人”、群消息触发后转发私聊以及多设备场景，需要补充真实对象目录和目标选择入口，但不应把它做成按场景枚举的工作流：

1. 行动模型先用语义表达这一步想完成的事，例如“把刚收到的小林回复转给先前私聊的用户”；
2. 目标解析提供可核实的参与者、群、私聊入口、设备、发送身份和关系信息。模型选择对象，地址由目录给出；
3. 独立审查模型在隐藏行动模型的选中结果时，根据同一原话和对象资料独立选择一次，并检查当前群消息是否真的与旧要求有关；
4. 两边对应到同一组具体对象且事实没有变化，才允许调用重定向/发送工具；
5. 分歧先补查历史、参与者关系或设备状态；仍无法区分且会造成错发时，询问用户。不能用“两个模型都说小林”代替具体 ID、会话和设备的核对；
6. 真正发送时保留发送者、会话、@ 对象、引用消息和被转述作者。执行失败反馈给行动模型重新决定，不自动降级到“最方便”的目标。

审查是行动前的一次独立判断，目标目录是事实来源，模型仍可以选择等待、改换计划、发送多条、发送给多个目标或本次不发送。不要为了追求一个准确率数字而删掉这些选择。

### 6.5 审查门禁的范围

统一的门禁接口应能接收“即将发生的动作”和“证据”，返回通过、需要补查或拒绝并说明理由。第一批接入点：

- `send` 的目标、发送身份、@、reply、forward 和消息内容；
- 新的重定向/跨会话发送能力；
- bash、设备调用、文件写入和高影响 HTTP 请求；
- 子代理启动时的原始任务、目标、上下文和重复检查；
- 子代理后续产生的工具动作和对外输出。

门禁不审查内部思考，也不递归审查审查者。它不能偷偷改写目标；如果证据不足，返回具体缺口，让行动模型继续查找或向用户询问。普通安全、低影响的聊天可以使用较轻的审查，以免每个“嗯”都付出一次完整目标推导。

## 7. 实验计划

实验先在离线假发送器和可记录的模型接口上跑，再进入有限真实模型，最后才考虑小范围 QQ 试用。所有实验都保存原始输入、模型版本、提示版本、工具 schema、审查结果、发送回执和评分，不只保存汇总数字。

### 7.1 统一场景库

建立 `experiments/orchestration/`，每个场景使用 YAML/JSON 描述：

- 初始用户消息、说话会话、发送角色和设备；
- 参与者、群、私聊入口、设备及稳定 ID；
- 必须保留的相关历史（包括没有直接引用的群回复）；
- 允许的合理替代行动；
- 目标答案、目标会话、@ 对象、被转述作者和等待条件的人工标注；
- 用户中途改口、目标不可用、发送失败/结果不明等扰动；
- 是否应回复、可接受的消息条数和角色台词要点。

同一场景至少准备四组难度：清楚目标、昵称重名、跨会话隐含关联、多角色多设备。场景不登记“必须调用哪一个工具”，只登记最终意图和事实约束，以免实验提前变成工作流测试。

### 7.2 实验 A：首次意图是否有实际价值

**问题**：关闭思考的快速请求能否更早给出有意义、符合角色的台词，而不是机械 ACK？

**比较组**：

1. 当前单模型提示词（基线）；
2. 同一模型增加“先判断下一步”的提示（提示词对照）；
3. 深入模型 + 快速关闭思考模型 + 输出审查（暂定设计）；
4. 快速模型直接生成、没有审查（定位审查代价的对照）。

**场景**：简单问题、复杂资料查找、工具失败、需要询问群友、用户已经给出答案、暂时无需回应、角色关系亲密/正式、用户中途改口。

**指标**：

- 首次可见内容时间（从收到输入到第一次成功发送）；
- 首次内容是否表达真实下一步，而非空泛确认；
- 人设和当前场景评分；
- “说要做但后续没有任何相关动作”的承诺落空率；
- 沉默是否合理、错误打扰率；
- 完整任务完成率、token、模型调用数和额外延迟。

通过条件应同时看“更早”和“更有用”。如果只是更早地发送固定句子而没有改变任务进展，视为失败；如果快速路径降低复杂任务完成率，也不能接受。

### 7.3 实验 B：发送目标选择

**问题**：在多人、多群、多设备中，模型能否选择正确的发送角色、听众、会话、@ 对象和转述来源？

**核心场景**：

1. 用户私聊：“把答案发项目群，然后 @ 小林。”要求群可见、@ 小林，不得改成小林私聊；
2. 群内有人回复旧问题，但没有引用原消息；模型需要想起先前私聊要求，再把群内消息转给私聊用户；
3. 两个群都有“小林”，一个是项目群成员，一个是无关群成员；
4. 用户在手机私聊发起，电脑负责查资料，结果应发给用户的私聊入口；
5. 用户中途改成“直接告诉设计组”，旧的群发送计划尚未开始；
6. 群消息与旧问题只有主题相似，实际不相关；模型应继续查证或不转发；
7. 目标设备离线、目标入口重复、发送回执结果不明；模型不能自动换到近似对象；
8. 多角色交叉讨论：小林是被转述作者，机器人是发送者，原用户是接收者。

**比较**：当前 `Peer` 单目标能力（明确记录缺口）、行动模型自行选目标、行动模型 + 独立目标审查。审查对照再分“只看行动模型摘要”和“可独立查询历史/目录”，验证第二种是否真的减少共同误判。

**评分**：分别记录发送角色、可见听众、会话 ID、设备/入口、@ ID、引用消息 ID、转述作者和内容是否对应；同时记录全字段一次通过率、各字段准确率、错发严重程度、合理等待/询问率、重复发送率。高风险明确场景的自动发送目标以 99% 作为上线参考目标，但达不到时应增加查证和询问，不应通过删除跨会话、多目标或等待能力来“达标”。

### 7.4 实验 C：独立审查是否抓到问题

**问题**：审查模型能否发现行动模型漏看的目标、身份、范围和事实问题？

**比较**：无审查、只审查普通输出、审查输出和所有高影响工具。每组使用相同的行动模型结果，加入人工构造的错误：重名、旧消息、错误会话、未确认成功、bash 范围过大、重复子代理。

**指标**：错误发现率、误拦截率、行动模型按依据修正的成功率、审查延迟/token、审查后的任务完成率、审查是否把本来可以完成的开放任务变成静默或无休止询问。审查价值是多一次独立发现错误，不是多数票；两个模型共同漏看时要在报告里单独标记。

### 7.5 实验 D：意图事实能否衔接

**问题**：快速模型实际说出的原话，是否在深度模型和子代理下一次动作前真正可见、可承接且不制造虚假完成？

**时序扰动**：快速模型先完成、深度模型先准备、用户先改口、发送中途失败、结果不明、群消息先到、子代理已经开始、完整答案先准备好、快速模型选择沉默。

**断言**：

- 只有确认发送的内容进入共同事实；草稿不会出现在历史或被当作承诺；
- 深度模型不会重复同义开场白，也不会执行已经被新要求取消的旧动作；
- “我去问问”之后如果对方已回答，模型可以直接转达；如果用户改口，模型可以停止尚未开始的动作；
- 已经发生的发送/工具结果不会被新意图抹掉；
- 群内触发的相关消息即使没有引用，也有机会通过历史和参与者关系找回原私聊要求；
- 所有不确定回执都能被后续模型看到，并避免无依据重发。

这组实验先用假模型和假发送器做确定性并发测试，再用真实模型做台词与承接评分。

### 7.6 实验 E：完备性和长任务能力

**问题**：新门禁是否在压低幻觉的同时保住开放式编排能力？

**场景**：三个以上角色轮流发言、多个群和私聊同时存在、两台设备分别查资料和发送、用户多次改口、任务中出现新线索、需要等待后续消息、需要临时启动两个不同方向的子代理，以及没有预先登记的自然追问。

**指标**：最终任务完成率、可接受行动组合覆盖率、遇到新信息后的改计划能力、用户改口响应时间、等待后恢复能力、重复/冲突行动、静默和询问的合理性。不要只统计“是否没有错发”；如果系统通过拒绝所有复杂动作把错误变成零，实验判定为失败。

### 7.7 运行与评分纪律

- 每个场景每个比较组至少重复 10 次；真实模型初筛可以 5 次，但任何上线判断要扩大重复次数并报告区间；
- 固定模型、温度、工具 schema、上下文和随机种子（若 provider 支持），交错运行不同比较组，避免时间段和缓存偏差；
- 先自动检查结构和真实回执，再由两名评分者盲评角色台词、相关性、意图价值和任务完整性；分歧保留原文，不用多数票抹平事实冲突；
- 记录 `time_to_first_attempt`、`time_to_first_success` 和第一条有实际意图的消息，不能把固定等待短句当成“首响时间”；
- 任何自动化评分都要把“正确静默”“合理询问”“多条消息”和“等待”作为合法结果，而不是把非发送一律记为失败；
- 结果目录建议为 `data/archive/experiments/orchestration/<date>/<strategy>/`，主仓库只提交场景、评分规则、汇总报告和可复现脚本，不提交密钥、生产聊天原文或大体积截图。
